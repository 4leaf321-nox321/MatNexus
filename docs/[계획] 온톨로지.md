# [계획] 온톨로지 — 관계를 데이터로 선언한다

2026-09-08. 지금 DB 구조를 온톨로지로 만든다. ReportArchive(RA)의
`[일부] 엔티티그래프_온톨로지_설계.md` 를 참조했다 — **다만 베끼면 안 되는 이유가
있고, 그것이 이 문서의 절반이다.**

---

## 0. RA 에서 그대로 가져올 것 넷

RA 가 이미 값을 치른 판단이다. 이유까지 그쪽 문서에 적혀 있다.

1. **RDB 가 진실의 원천, 그래프는 투영이다.** 관계는 지금처럼 관계형 표에 쓰고,
   그래프 엔진은 거기서 파생한 **읽기 최적화 색인**이다. 그래프가 깨져도 데이터는
   무손실이고 재구축으로 복구된다. 권한·마이그레이션·CRUD 가 전부 그대로 산다.
2. **트래버설을 모듈 하나로 추상화한다.** 그 모듈의 **공개 서명이 안정 계약**이고,
   내부는 재귀 CTE 로 시작한다. 나중에 그래프 엔진으로 갈 때 **그 파일 안만** 바뀐다
   — 이 추상화 경계가 곧 전환 지점이다.
3. **전환 방아쇠는 데이터 규모가 아니다.** (a) 관계 종류의 다양화 (b) 임의 경로
   질의의 빈발 (c) AI 가 질의를 만드는 것. 그 전에 엔진을 깔면 운영 표면만 늘고
   얻는 것이 0이다.
4. **그래프에는 온톨로지만 넣고 코퍼스는 안 넣는다.** RA 는 보고서(수만)를 노드로
   안 넣고 엔티티(수백~수천)만 넣었다 — 섞으면 그래프가 코퍼스 크기만큼 커지는데
   권한 필터는 어차피 RDB 에서 다시 해야 해 이득이 없다.

## 1. RA 를 그대로 베끼면 안 되는 이유

**RA 와 MatNexus 는 데이터 모델의 성격이 반대다.**

| | ReportArchive | MatNexus |
| --- | --- | --- |
| 개체 | `entities` **한 표** + `entity_types`(축) | 표 60개, 각각 제 형태 |
| 관계 | `entity_relations` 한 표 | **외래키 128개** |
| 어휘 | 축이 곧 분류 | 기준정보(축 15 · 값 수만, ADR 0010) |

RA 는 *무엇이든 엔티티*라 관계를 담을 표가 하나면 됐다. MatNexus 는 재료·시료·
시편·시험·곡선·카드·문헌값·장비가 **각자 다른 칸과 규칙을 가진** 표다. 그것을
`entities` 한 표로 뭉개면 지금 있는 것을 전부 잃는다 — 유일 제약, 층 규칙(ADR 0016),
불변/가변 분리, 소프트 삭제, 리비전, 권한.

**그러니 표를 바꾸지 않는다.** 온톨로지화란 여기서 *구조를 갈아엎는 일*이 아니라
**이미 있는 구조의 뜻을 기계가 읽게 만드는 일**이다.

## 2. 이미 절반은 온톨로지다

`vocabulary_terms` 를 **21개 표가 가리킨다.** 기준정보가 이미 하는 일:

| 온톨로지 개념 | MatNexus 에서 |
| --- | --- |
| 클래스 / 축 | `vocabularies`(slug·label·entry_policy) |
| 개체 / 값 | `vocabulary_terms` |
| 상위 클래스 | `vocabularies.parent_slug` (Family→Category→Grade) |
| 상위 개체 | `vocabulary_terms.parent_term_id` |
| 동의어 | 별칭(`term_aliases`) — 「포스코(주)」→「포스코」 |
| 속성 정의 | `base_fields` / `extra_fields` (축·값이 갖는 칸) |
| 정합성 | 어긋남 검사(`drift`) · 병합 · 사용수 |

**이미 있는 것을 다시 만들지 않는다.** 이번 세션에 그 실수를 세 번 했다(기준정보
바인딩·부서 트리·부서 피커). 온톨로지 작업에서 같은 실수를 하면 규모가 훨씬 크다.

## 3. 그래서 빠진 것은 무엇인가

셋이다.

### ① 관계의 뜻이 코드에만 있다

`samples.material_id` 가 *"이 시료는 이 재료에서 잘라 왔다"* 라는 것은 **주석에만**
있다. 기계는 그것이 포함인지 파생인지 참조인지 모른다. AI 가 「이 물성값이 어느
재료에서 왔나」 를 물으려면 128개 외래키 중 **어느 것이 뜻 있는 길인지** 알아야
하는데, 지금은 `users`·`workspaces` 같은 소유·감사 FK 와 구별할 방법이 없다.

RA 의 `relation_types` 레지스트리가 푸는 문제가 정확히 이것이다. 다만 RA 는 새
엣지에만 필요했고, **우리는 이미 있는 FK 를 설명해야 한다.**

### ② FK 로 못 담는 관계가 있다

- **시험 ↔ 장비 개체** — 장비 파일이 모델 문자열만 적어서 같은 모델 두 대를 못 가른다
  (`[계획] …` 보유 장비 참조). 사람이 고르는 관계라 FK 하나로 안 끝난다.
- **물성 ↔ 시험법 ↔ 장비** — `instrument_capabilities.property_key` 가 그 관계인데
  **컬럼이라 그 하나뿐**이다. 「이 시험법은 이 규격을 따른다」 같은 것을 더할 자리가 없다.
- **재료 ↔ 문헌 재료** — `catalog_links` 로 있다. 관계 하나에 표 하나를 만든 셈이라,
  다음 관계가 생기면 또 표를 만들게 된다.
- **구성체 ↔ 부품** — ADR 0026 이 `AssemblyMember` 로 설계했다. 아직 표가 없다.

### ③ 축과 축 사이가 비어 있다

기준정보는 **축 안의 계층**(Family→Grade)만 안다. **축을 가로지르는 관계** —
「물성 항목」과 「시험 종류」, 「장비 유형」과 「물성 항목」 — 은 어디에도 없다.
그런데 그것이 MCP 가 답해야 할 질문의 대부분이다:

> "PC/ABS 의 온도별 탄성계수를 얻으려면 어떤 시험을 해야 하고, 우리가 그 장비를
> 갖고 있나?"

이 질문은 **물성 → 시험법 → 장비 유형 → 보유 장비** 로 네 축을 건넌다.

## 4. 단계

### 1단계 — 관계 레지스트리 (뜻을 데이터로)

`relation_types` 를 둔다. RA 의 칸을 거의 그대로 쓴다:

    slug            part_of · derived_from · tested_by · measured_by · adopted_from …
    label           사람용 정방향 («포함됨»)
    inverse_label   역방향 («포함»)
    directed        방향성이 있나
    transitive      **재귀로 펼칠 관계인가** (part_of=참, tested_by=거짓)
    acyclic         순환 금지인가
    src / dst       허용되는 양쪽 종류

**우리만의 추가**: `source` — 이 관계가 **어디에 실려 있나**.

    fk:samples.material_id        이미 있는 외래키를 설명만 한다
    table:catalog_links           관계 전용 표가 이미 있다
    edge                          아래 ②의 일반 관계 표에 산다

이 칸이 RA 와 갈리는 지점이고, **표를 안 바꾸고 온톨로지를 얻는 열쇠**다. 기존
FK 를 옮기지 않고 *가리키기만* 한다.

첫 관계 세트는 지금 있는 FK 중 **뜻 있는 것만** 고른다. `created_by_id` ·
`workspace_id` 같은 소유·감사 FK 는 온톨로지가 아니다 — 그것을 넣으면 그래프가
사람과 부서로 뒤덮인다(RA 가 보고서를 노드에서 뺀 것과 같은 판단).

### 2단계 — 일반 관계 표

`entity_edges`(가칭). FK 로 못 담는 관계만 여기 산다.

    src_kind, src_id     'test_run', <uuid>
    dst_kind, dst_id     'equipment_unit', <uuid>
    relation             relation_types.slug
    note, created_by_id, created_at

**다형 참조라 FK 무결성이 없다.** 그래서 두 가지를 함께 둔다: `src_kind` 가
아는 종류인지 검사하고, **끊어진 참조를 세는 점검**을 둔다(기준정보 어긋남 검사와
같은 자리). 무결성을 잃는 대신 관계마다 표를 만들지 않는다.

`catalog_links` 는 **옮기지 않는다.** 이미 잘 돌고 유일 제약도 걸려 있다 —
레지스트리가 `table:catalog_links` 로 가리키면 된다.

### 3단계 — 트래버설 모듈 (전환 경계)

`matcore/…` 가 아니라 `app/shared/graph.py` 다. **DB 를 아는 일이라 matcore 에
둘 수 없다**(AGENTS.md: matcore 는 DB 도 HTTP 도 모른다).

    neighbors(db, kind, id, *, relations, direction) -> [(kind, id)]
    traverse(db, seeds, *, relations, direction, max_depth) -> 도달 집합
    subgraph(db, seeds, *, relations, max_depth) -> {nodes, edges}
    path_between(db, a, b, *, relations, max_depth) -> [경로]

내부는 **재귀 CTE**. `source` 가 `fk:` 인 관계는 그 표를 조인하고, `edge` 인 것은
`entity_edges` 를 본다 — **부르는 쪽은 그 차이를 모른다.** 그것이 이 모듈을 두는
이유이고, 나중에 그래프 엔진으로 갈 때 바뀌는 유일한 파일이다.

**권한은 여기서 안 한다.** 그래프는 그래프만 계산하고, 가시성 교집합은 부르는
쪽이 한다(RA 와 같은 분리, `visible_materials` 패턴 재사용).

### 4단계 — MCP 가 스키마를 안다

지금 MCP 의 `get_taxonomy` 는 **분류와 분포**만 준다. 여기에 관계를 더한다:

    get_ontology()          축·종류·관계 타입 목록 — AI 가 스키마를 인지하는 자리
    related(kind, id, …)    그 개체와 이어진 것들
    path(a, b)              「이 물성값이 어느 장비로 나왔나」

**이것이 이 작업의 진짜 목적**이다. 사람은 화면에서 링크를 눌러 다니면 되지만,
AI 는 스키마를 읽을 수 있어야 길을 찾는다.

### 5단계 — 축을 가로지르는 관계 (데이터)

물성 ↔ 시험 종류 ↔ 장비 유형. **표는 3단계에서 이미 생겼으므로 여기서는 값을
넣는 일**이다. 문헌 카탈로그의 `instrument_capabilities` 750건이 이미 물성↔장비를
들고 있으니 그것을 관계로 투영하는 것부터 한다.

### (미래) 그래프 엔진

**아직 아니다.** 방아쇠 셋 중 하나도 안 당겨졌다. 당겨지면 Apache AGE 를 본다
— Postgres 확장이라 같은 DB·트랜잭션·백업이고, `pg_trgm` 을 깐 것과 같은 패턴이다.

## 5. 하지 않을 것

- **`entities` 한 표로 통합** — §1. 지금 있는 것을 전부 잃는다.
- **RDF/OWL/SPARQL** — 표준 온톨로지 스택은 추론기와 별도 저장소를 끌고 온다.
  우리가 필요한 것은 「관계를 기계가 읽는 것」 이지 서술논리 추론이 아니다.
  필요해지면 `relation_types` 를 OWL 로 **내보내면** 된다(그때 비용 0).
- **모든 FK 를 관계로 등록** — 사람·부서·감사 FK 는 온톨로지가 아니다.
- **화면부터** — 관계도 시각화는 RA 에 있고 보기 좋지만, **읽을 관계가 없으면
  그릴 것도 없다.** 1~3단계 뒤에 판단한다.

## 6. 먼저 답해야 할 것

1. **무엇을 위한 온톨로지인가.** MCP/AI 가 길을 찾게 하는 것이 목적이면 1·3·4단계면
   충분하고 2단계도 최소로 끝난다. 사람이 관계도를 그려 탐색하는 것이 목적이면
   순서가 달라진다.
2. **어느 질문에 답하고 싶은가** — 두세 개만 적으면 필요한 관계가 정해진다.
   지금 짐작하는 것: 「이 물성값은 무엇으로 어떻게 나왔나」(provenance),
   「이 물성을 재려면 무엇이 필요하고 우리가 가졌나」(capability),
   「이 재료와 비슷한 것」(유사).
3. **구성체(ADR 0026)를 기다릴까.** 그쪽이 `AssemblyMember` 로 관계를 만들 예정이라,
   2단계를 그 전에 하면 두 벌이 될 수 있다. 다른 세션과 겹치는 자리다.
