# [계획] 계산 확장 — 새 물성 계산을 배포 없이, 중심 코드 없이 붙이는 길

2026-09-13. 입력(장비 파일 정의 = 데이터, ADR 0006)과 출력(솔버 덱 = 파일, ADR 0023)
은 이미 배포 없이 는다. **계산**은 다르다 — 무엇이 되고 무엇이 안 되는지 실측으로
가른 뒤, 두 단계를 하기로 했다.

## 1. 지금 — 계산은 세 층이고 층마다 자유도가 다르다

| 층 | 예 | 지금 | 근거 |
| --- | --- | --- | --- |
| **① 적합식 · 카드 블록 · 솔버 렌더러** | Ghosh 경화식, Johnson-Cook, Norton 크리프 | **폴더 하나로 된다** — 중심 코드 0줄 | `extensions/ghosh_hardening` · `johnson_cook_static` 이 실제로 이 길로 붙어 있다 |
| **② 처리 단계**(곡선 → 곡선·스칼라) · **묶음**(곡선 n벌 → 하나) | 공칭→진응력, 항복점, DMA 유리전이 / Prony 묶음, 속도 가족 | 등록 창구(`registry.register(kind="processing" \| "grouping")`)는 ①과 같은데 **확장에서 써 본 적이 없다** — 내장만 그 길로 등록돼 있다 | 창구는 열려 있고 검증이 없다. 개발계획 §11 「확장 창구 넷 중 하나만 써 봤다」 |
| **③ 새 데이터 모양이 필요한 물리** | 점탄성 — 마스터커브(기준 온도·시프트 인자를 든 겹친 곡선), Prony 세트 | **안 된다.** 표 2개(`master_curves`·`prony_fits`) + 읽기 훅 + 화면 6개, 2,700줄이 중심에 필요했다 | 확장은 마이그레이션을 못 쓴다(AGENTS) — 옳은 규칙이다 |

「탄소성·점탄성이 자유롭게 안 붙는다」 는 느낌은 정확히 ③이다. 탄소성은 사실 ①+②로
된다(경화식 = ①, 진응력·항복점 = ②).

**묶음(grouping)은 이미 일반화돼 있다**(ADR 0020, `matcore/groups`). 「여러 시험 →
하나」 는 `GroupResult` 한 표(플러그인 id · 구성원 · 옵션 · 결과 JSON)에 담긴다.
남은 예외는 `app/modules/grouping/services.py` 의 `_COLLECTORS` — 묶음마다 「채택된
결과에서 무엇을 꺼내는가」 를 `if` 한 줄로 알고 있다. 그 파일 머리에 "다음 물성을
붙일 때 그 한 줄이 거슬리면 레지스트리로 옮길 때다" 라고 적혀 있다.

## 2. 하기로 한 것 — 순서대로

### 1단계 · ②를 실제로 열어 둔다 (반나절) — **끝(2026-09-13, 4456ff0)**

확장 폴더에서 **처리 단계 하나와 묶음 하나**를 등록하는 예를 만들고, 레시피
편집기·묶음 목록에 뜨는지, 배치로 도는지, 결과 아티팩트에 `plugin_version` 이 남는지
시험으로 못 박는다(`tests/unit/test_ext_*.py`, 운영과 같은 `extensions.load()` 경로로).

이때 **확장 계약서를 생성한다**(아래 3절). 창구가 있다는 것과 써 봤다는 것, 그리고
남에게 설명할 수 있다는 것은 셋 다 다르다.

### 2단계 · 수식을 데이터로 받는다 (며칠) — 가장 값지다 — **끝(2026-09-13)**

**한 것.** ADR 0030 대로. 평가기 `matcore/formula.py`, 자리 셋에 묶는
`matcore/formulas.py`, 표 `formulas` + `app/modules/formulas`(목록·만들기·고치기·끄기·
지우기·미리보기·어휘), 화면 「관리 → 계산식」(`/admin/formulas`). 등록 키는
`formula.<key>` — 파이썬 확장·내장과 이름이 못 겹친다. 기동 때와 저장할 때 레지스트리에
넣으므로 재시작이 없다. 계획과 다른 점: 표 이름은 `fitting_families` 가 아니라
`formulas` 다 — 적합식만이 아니라 값 단계·열 단계도 같은 표에 든다(자리가 칸이다).

**확인한 것.** 화면에서 적은 Swift 가 내장 Swift 와 같은 계수·같은 R² 를 낸다
(`tests/api/test_formulas_api.py`). 식을 고쳐도 저장된 처리 결과의 값은 그대로다. 라벨만
고치면 판이 안 오른다. 레시피가 쓰는 식은 409 로 못 지우고 끄면 목록에서만 빠진다.

지금 새 경화식은 파이썬 파일이라 **물성 개발자 + 배포**가 필요하다. 그런데 경화식
대부분은 닫힌 식이다 — `σ = A + B·εⁿ`, `σ = A·(1 − e^{−bε})`. 형식 프로파일·솔버 덱을
데이터로 받듯이 적합식도 데이터로 받는다:

    화면(기준정보 아래 「적합식」)에서
      식        y = A + B * x**n
      x·y 축    strain_true_plastic / stress_true   (Family.x_column·y_column 과 같은 어휘)
      파라미터   A [Pa] 초기 200e6 범위 0~2e9 · B [Pa] … · n [1] 0.05~1
      담는 곳   hardening 블록
      재료군    metal

    서버는 이것을 `fitting.Family` 로 만들어 **같은 레지스트리에** 넣는다 — 파이썬 식과
    나란히 서고, 화면·MCP·배치는 둘을 구별하지 못한다.

- **식 평가는 안전한 평가기로.** `eval` 이 아니라 허용 함수(`exp·log·pow·sqrt·tanh`)와
  변수만 받는 파서. 미분은 수치로(`tangent` 는 비워 둔다).
- **저장 위치.** 새 표 `formulas`(key · kind · label · expression · variables ·
  parameters · result · axes · block · applies_to · version · enabled · created_by).
  키에 `formula.` 접두어가 붙으므로 파이썬 확장과 겹칠 수 없다.
- **한계를 처음부터 적는다.** 적분·미분방정식·다중 곡선 동시 적합(Prony, Anand, 초탄성
  다중 모드)은 이 길로 안 된다 → ①(파이썬 폴더). 화면이 그 말을 한다.
- **단순 스칼라 계산도 같은 방식.** 「기존 스칼라들의 식」(예: `yield_ratio =
  proof_stress / tensile_strength`)을 처리 단계로 등록 — `makes_values` 하나짜리.
  곡선을 만드는 단계는 이 길로 안 된다(열 하나를 식으로 만드는 것까지는 가능).
- **저장된 레시피·카드는 안 건드린다.** 식을 고치면 새 판(`version`)이 되고 옛
  결과는 옛 판으로 남는다 — 처리 결과의 `plugin_version` 과 같은 규율.

**설계 문서**: 착수 전에 ADR 한 장(식 문법 · 저장 · 파이썬 식과의 공존 · 판 관리).

### 2.5단계 · 묶음 하나짜리 물리 — **온도 의존 탄소성** (2026-09-13, 끝)

`tensile.temperature_family` 를 속도 가족과 같은 모양으로 키웠다: 온도 묶음(±`bin_kelvin`)
별 평균 곡선 → 온도별 소성 표, 기준 온도 대비 응력비, 연화 기울기 dσ/dT, Johnson-Cook
온도 항 m(녹는점을 받아). 카드 블록 `temperature_table` 과 Abaqus `*PLASTIC` 온도 열
덱은 확장 폴더 안(`card.py`). **중심에 더한 것은 공용 길 하나뿐이다** —
`POST /fitting/cards/from-group`: 묶음 플러그인이 `register(..., card=fn)` 으로 「값·상세·
경고 → 블록」 을 선언하면 계보·탄성 물려받기·저장은 중심이 맡는다. 다음 묶음(이방성
Hill·피로 S-N·Paris·GISSMO)은 이 길로 **중심 코드 0줄**이다.

LS-DYNA 는 `*MAT_106` + `*DEFINE_TABLE` 이 필요한데 카드 자리를 검증할 실측이 없어
안 냈다. 남은 것: 폭 변형률(Hill)·피로·레오미터 시험 종류는 **데이터가 먼저**다.

### 2.6단계 · 레오미터 + 유변 식 (2026-09-13, 끝)

「식만 더하면 된다」 는 절반만 맞았다. 시험 종류 `rheometer_flow` 와 TRIOS 프로파일
`ta_hr_flow`(공개 실파일 둘로 검증 — DMA850 과 같은 `[step]` 구조)는 씨앗으로, Cross·
Carreau 는 확장 폴더 `extensions/rheology`(식·`rheology` 블록·Abaqus `*VISCOSITY` 덱)로
붙였다. 중심에 더한 것 셋, 전부 일반화다: ① `Family.residual="log"` — 수십 배를 지나는
곡선의 잔차 눈금, ② 「적합할 수 있나」 를 등록된 식의 축으로 판단(진소성변형률 상수
제거), ③ 식을 안 골랐으면 묶음의 열에 맞는 식만 견줌. 덱 단위계에 `Pa.s`(`N.s/mm2`)를
더했다 — `MPa.s` 기호는 단위표가 `mPa.s` 로 읽어 1e9 배 사고라 시험이 지킨다.

### 3단계 · 「중간 산물」 을 일반화한다 — **두 번째 ③이 나타날 때**

`master_curves` 를 `DerivedCurve(kind, 원본 곡선들, meta)` 같은 일반 표로 바꾸고, 확장이
「내 물리는 이런 kind 의 산물을 낸다」 고 선언하게 한다. 지금 하지 않는 이유: 사례가
하나뿐이다. 하나를 보고 추상화하면 그 하나의 모양이 그대로 규칙이 된다. 크리프 마스터
커브(Larson-Miller)처럼 같은 모양이 하나 더 오면 둘을 보고 한다(4절 조사).

## 3. 개발할 사람에게 지금 무엇을 어떻게 알려 주고 있나

솔직한 현황: **계약서가 없다.** 있는 것은 셋이다.

| 자리 | 내용 | 한계 |
| --- | --- | --- |
| `backend/extensions/README.md` | 등록 셋(블록·식·렌더러)의 예와 지키는 것 | 처리·묶음 예가 없다. **입력 열 이름 어휘**(`stress_true`·`strain_true_plastic` 이 어디서 오는지)가 없다 |
| 데이터클래스 docstring | `fitting.Family`·`cards.BlockSpec`·`registry.Plugin`·`processing.Frame`·`StepResult` 에 칸마다 왜 있는지 | 코드를 열어야 보인다. 한 자리에 없다 |
| 살아 있는 예 둘 + 시험 | `ghosh_hardening`·`johnson_cook_static`, `tests/unit/test_ext_*.py` | 식 하나·블록 하나 모양만 |

입력·출력이 **무엇인지**는 사실 코드가 전부 알고 있다 — 내장 처리 단계의
`makes_columns`·`makes_values` 가 열·스칼라 어휘이고, `Family.x_column` 이 그중 무엇에
맞추는지이고, `BlockSpec.produces` 가 담기는 모양이고, 렌더러의 `needs` 가 먹는 것이다.
사람에게 안 보일 뿐이다.

**할 일(1단계에 포함)**: `scripts/describe_extension_api.py` 가 레지스트리를 읽어
`docs/확장-계약.md` 를 **생성한다** — 손으로 쓰면 뒤처진다(`dependents.py` 의 교훈).

    ## 처리 단계가 받는 것 — Frame
      columns: 채널 키 또는 앞 단계가 만든 열. 전부 SI.
      내장 단계가 만드는 열: strain_engineering(1) · stress_engineering(Pa) · strain_true(1) ·
        stress_true(Pa) · strain_true_plastic(1) · …   ← makes_columns 에서
      내장 단계가 내는 스칼라: youngs_modulus(Pa) · proof_stress(Pa) · …            ← makes_values 에서
    ## 처리 단계가 내는 것 — StepResult(columns 추가, values, notes)
    ## 적합식 — Family: (파라미터, x) → y · 축은 위 열 어휘에서 · 담기는 블록
    ## 카드 블록 — BlockSpec: produces(스칼라) · rows(표 열) · 단위는 SI_UNITS 에서
    ## 솔버 렌더러 — needs(어느 블록의 어느 값) · Deck → Rendered
    ## 묶음 — 구성원(시험들)에서 꺼내는 것 · GroupResult

CI 가 생성본과 저장본을 대조한다(`openapi.json` 과 같은 방식).

## 4. 조사 — 「중간 산물」 이 필요한 물리가 얼마나 있나

CAE 물성 특성화에서 흔한 것을 이 저장소의 세 갈래(처리 = 시험 하나 · 묶음 = 여러 시험
→ 하나 · 중간 산물 = 시험 하나 안의 겹친 곡선)로 나눠 봤다.

| 물성 | 입력 | 계산 | 갈래 | 지금 |
| --- | --- | --- | --- | --- |
| 탄소성 (경화식) | 인장 곡선 1 | 진응력 변환 → 소성 구간 → 식 적합 | ① + ② | 됨 |
| 초탄성 (Mooney·Ogden) | 단축·2축·전단 곡선 | 여러 **모드** 동시 적합 | ② 묶음 성격 (지금은 카드 블록에 모드별로) | 됨(블록) |
| 속도 의존 (rate table) | 변형률속도별 인장 곡선 n | 곡선 n → 표 | **묶음** | 됨 (`tensile.rate_family`) |
| 온도 의존 탄소성 | 온도별 인장 곡선 n | 곡선 n → 온도별 표 | 묶음 | 안 됨 — 속도 가족과 **같은 모양**, 묶음 플러그인 하나 |
| 이방성 (Hill r값) | MD·TD·DD 곡선 | 곡선 3 → 스칼라 셋 | 묶음 | 안 됨 — 묶음 플러그인 하나 |
| **점탄성 (Prony)** | DMA 온도·주파수 스윕 | **TTS 겹치기 → 마스터커브** → Prony 적합 | **중간 산물** + 묶음 | 됨 (전용 표) |
| **크리프 (Norton·시간경화)** | 응력·온도별 크리프 곡선 n | 곡선 n → 식 적합. 장기 예측은 **Larson-Miller 마스터커브**(시간-온도 중첩) | 묶음 · 장기 예측은 **중간 산물** (점탄성과 같은 모양) | 식은 ①로 붙음(Norton 예). 마스터커브는 안 됨 |
| 피로 (S-N · ε-N) | 시편 수십 개, 각각 **점 하나**(응력, 수명) | 점 n → 회귀(Basquin) | 묶음 | 안 됨 — 묶음 플러그인 하나. ADR 0020 이 이미 이것을 염두에 둠 |
| 균열 성장 (Paris) | da/dN vs ΔK 시험 n | 점·곡선 n → 식 | 묶음 | 안 됨 — 묶음 |
| 파단·손상 (GISSMO·삼축성) | 형상 다른 시편 n | 시편별 파단 변형률 → 삼축성 곡선 | 묶음 | 안 됨 — 묶음 |
| 유변 (Cross·Carreau) | 점도-전단율 곡선 1 | 식 적합 | ① | 식만 더하면 됨 |
| 열물성 온도 의존 | 선언값 온도점 | 표 | 선언 물성 | 됨 |
| 압축·굽힘·전단 | 곡선 1 | 처리 | ② | 처리 단계 |

**결론.**

- 「중간 산물」(시험 하나 안에서 곡선 여럿을 겹쳐 새 곡선을 만드는 것)이 필요한 것은
  **점탄성과 크리프 장기 예측(LMP) 둘**이다. 나머지는 전부 처리(①·②) 아니면 묶음이다.
- 즉 3단계 일반화는 **크리프 마스터커브가 필요해지는 날** 하면 되고, 그때 점탄성과 둘을
  보고 `DerivedCurve` 를 뽑는다.
- 훨씬 많은 것이 **묶음** 이고, 묶음은 이미 일반 표를 갖고 있다. 막는 것은
  `_COLLECTORS` 의 `if` 한 줄뿐이다 — 1단계에서 묶음을 확장 폴더에서 등록해 보면 그
  한 줄을 레지스트리로 옮길 때가 온다.
- 2단계(수식을 데이터로)가 덮는 범위: 경화식·유변·크리프 식·단순 스칼라. 화면에서
  식을 더하는 것이 실제로 부서가 하고 싶은 일의 대부분이다.
