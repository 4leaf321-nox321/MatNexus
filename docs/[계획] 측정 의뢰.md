# [계획] 측정 의뢰 — 「이 재료의 이 물성을 재 달라」 가 기록으로 흐르게

날짜: 2026-09-14
관련: [회의정리 2026-08-28](회의/회의정리-2026-08-28-물성데이터관리-AI평가시스템.md) ·

[ADR 0026](adr/0026-복합-물성-구성체와-시험법을-둔다.md)

## 무엇이 문제인가

회의(08-28)의 결론은 「업체가 재 준 물성은 못 올린다 → **측정을 내부에서 한다** →
신뢰성 그룹이 재고 등록한다」 였다. 그런데 지금 플랫폼은 **잰 뒤**부터만 있다 —
시료 → 시편 → 시험 → 처리 → 카드. 「누가 무엇을 왜 재 달라고 했고, 언제 어디까지
됐나」 는 메일·구두에 있고 기록이 없다. 그래서

- 해석 쪽(CA)은 「의뢰했는데 어디까지 됐나」 를 물어야 알고,
- 측정 쪽(신뢰성)은 「이 시험을 누가 왜 시켰나」 가 시험 행에 남지 않고,
- 같은 재료의 같은 물성을 여럿이 따로 의뢰한다.

VOC 가 「게시판이고 절차다」(2026-09-11) 로 자리 잡은 것과 같은 문제다. 같은 무늬로
푼다: **한 건은 상태를 거쳐 가고, 바뀔 때마다 누가·언제·무슨 말로가 남는다.**
다른 점은 하나 — 의뢰는 **끝이 데이터**다. 시험 행이 붙고 결과가 채택되면 진행률이
저절로 오르고, 채택된 결과가 카드가 되면 의뢰가 닫힌다.

## 어디에 — 새 모듈 `commissions`

    backend/app/modules/commissions/  ↔  frontend/src/modules/commissions/
      models.py   Commission · CommissionItem · CommissionEvent
      routes.py   /api/commissions …
      schemas.py
      services.py 누가 보나 · 어느 쪽인가 · 어디로 옮기나 · 진행률 · 알림

- **재료 물성 realm** 이다. 대상이 지금 있는 재료·시료·시편·시험이고, 결과가 지금
  있는 카드다. 복합 물성 realm 의 「시료 배분」(2단계, 해석으로 리스크를 도출해 배분)
  과는 다른 것이다 — 그쪽은 **어디에 쓸지 정하는 계획**, 이쪽은 **재 달라는 절차**.
  나중에 시료 배분이 생기면 그 결과가 의뢰를 만드는 쪽으로 이어진다.
- 사이드바 「카탈로그」 묶음의 「시험」 아래에 **「측정 의뢰」** 하나. 「내 활동」 에
  「내 의뢰」 는 따로 두지 않는다 — 목록의 탭(내가 낸 것 / 우리 부서가 받은 것 / 전체)
  으로 충분하고, 항목이 늘면 찾기가 어려워진다.
- 이름은 `commissions` 로 정했다(2026-09-14) — `requests` 는 파이썬 라이브러리와 같아
  grep 이 헷갈린다. 사용자에게 보이는 말은 **「측정 의뢰」** 다.

## 모델 — VOC 의 무늬 + 데이터에 닿는 다리

```
Commission                     측정 의뢰 한 건
  id, seq (사람이 부르는 번호 — 「의뢰 12번」)
  title, purpose (왜 필요한가 — 해석 과제·판정·비교…)
  requester_workspace_id  FK   낸 부서
  lab_workspace_id        FK   받는 부서 (측정하는 곳)
  sample_id               FK?  무엇을 재는가 — 등록된 시료. RESTRICT
  material_hint           text 새 재료(등록 전)면 이름·등급·업체·두께를 글로 — 받는 쪽이 등록 후 잇는다
  sample_plan             text 시료 전달 — 몇 개, 어떻게, 언제
  due_on                  date 희망 기한
  priority                enum normal / urgent
  status                  enum (아래)
  assignee_id             FK?  담당자 (접수 때 정한다)
  status_at, status_by_id      목록의 「최근 처리」 열 — VOC 와 같은 이유(N+1 방지)
  created_by_id, created_at

CommissionItem                 의뢰 항목 — 「이 시험 종류를 이 조건으로 n 개」
  id, commission_id FK, position
  test_type_id            FK?  시험 종류 (인장·DMA·레오미터·피로…) — 미정이면 비움
  property_hint           text 종류 미정일 때 무엇을 재는지(물성 이름) — 받는 쪽이 종류를 정한다
  conditions              jsonb 시험 종류의 조건 칸(TestConditionField)으로 적는다 — 시험 등록 때와 같은 폼
  orientations            text[] RD/TD/45 …
  count                   int  시편 수
  deliverable             text 무엇으로 받을지 — 카드 종류 키(탄소성·초탄성·유변…) 또는 'curves'
  note                    text
  ← 진행률은 저장하지 않는다. 이 항목에 붙은 시험 중 결과가 채택된 것의 수 / count 로 센다.

CommissionEvent                일어난 일 하나 — 등록·상태 변경·댓글 (VocEvent 와 같음)
  id, commission_id, at, by_id, from_status, to_status, note

TestRun.commission_item_id FK?   시험이 어느 의뢰 항목에 답하는가 (nullable)
```

**시험을 의뢰에 잇는 자리는 `TestRun` 의 열 하나**다. 연결표를 따로 두면 「한
시험이 두 의뢰에 답한다」 가 가능해지지만, 그것은 실제로는 「같은 물성을 두 번
의뢰했다」 는 신호라 허용하지 않는 것이 맞다. 열 하나면 시험 상세에 「의뢰 12번 ①」
배지를 join 없이 그린다. `tests` 모듈에 열을 더하는 것이라 플랫폼 개발자 경로다.

### 상태

    draft        작성 중    낸 사람만 본다. 항목을 채우는 동안
    submitted    접수 대기  받는 부서 관리자에게 알림
    accepted     접수       담당자·예정일을 정함        ← 말이 있어야: 언제쯤
    in_progress  시험 중    시험이 하나라도 붙으면 저절로
    on_hold      보류       시료 미도착·장비 고장       ← 이유를 반드시
    delivered    결과 전달  모든 항목이 채워짐 — 담당자가 옮긴다 ← 무엇을 어디서 보는지
    closed       완료       낸 사람이 확인
    rejected     반려       안 하기로 함                ← 이유를 반드시

이동 규칙은 VOC 처럼 `LAB_MOVES`(받는 부서 담당자·관리자) / `AUTHOR_MOVES`(낸 사람:
`delivered → closed | in_progress`(부족하면 되돌림), `rejected → submitted`) 두 표와
`NOTE_REQUIRED` 로 둔다. `in_progress` 로의 자동 이동만 예외 — 시험이 붙는 순간
서비스가 옮기고 이벤트를 남긴다(by = 시험 등록한 사람).

### 권한 — 판정은 `shared/permissions.py` 한 곳

- **보기**: 낸 부서 멤버 + 받는 부서 멤버 + 시스템 관리자. `draft` 는 낸 사람만.
- **쓰기**: 항목 편집은 `draft`·`submitted` 에서 낸 사람만. 상태 이동은 위 두 표.
- **결과 읽기**: 의뢰에 붙은 시험은 받는 부서 것이라 낸 부서 사람은 원래 못 본다.
  의뢰 상세 API 가 **그 시험의 요약과 카드**를 의뢰 권한으로 돌려준다 — 목록 API 나
  시험 상세로 우회해 들어가는 길은 열지 않는다(「검색에는 뜨는데 열면 404」 의 반대,
  「의뢰에서는 보이는데 시험 목록엔 없다」 는 의도된 것). 시험 상세까지 열고 싶으면
  `graph.visible_ids` 에 「내 의뢰에 붙은 시험」 을 더하는 것 하나로 끝나게 만든다 —
  판정 지점이 하나여야 그게 된다.

### 알림 — `EVENT_KINDS` 에 셋

    commission.submitted 새 의뢰가 우리 부서로 왔다     → 받는 부서 관리자
    commission.changed   내 의뢰가 움직였다             → 낸 사람 (상태·댓글·시험 붙음)
    commission.due_soon  기한 3일 전인데 안 끝났다      → 담당자·낸 사람 (jobs 큐, 하루 한 번)

## 화면

| 주소 | 무엇 |
| --- | --- |
| `/commissions` | 게시판. 탭: 내가 낸 것 · 우리 부서가 받은 것 · 전체. 열: 번호·제목·재료·항목 수·진행률(3/5)·상태·기한·최근 처리 |
| `/commissions/new` | 새 의뢰. 한 화면 세 묶음 — ① 무엇을(재료 고르기 또는 글로 적기, 목적) ② 어떤 시험을(항목 표 — 시험 종류·조건·방향·수량·받을 것) ③ 시료·기한(시료 유무, 전달 방법, 희망일, 받는 부서). 「임시 저장」 = draft, 「의뢰」 = submitted |
| `/commissions/:id` | 상세. 위: 상태 띠 + 이동 단추(허용된 것만) · 중간: 항목 표(항목마다 진행률, 붙은 시험 목록, 채택 결과 요약, 「시험 등록」 단추) · 아래: 타임라인(이벤트 + 댓글 칸) |

이어지는 자리(작지만 이것이 「절차가 데이터에 닿는」 부분이다):

- **재료 상세** 「측정 의뢰」 단추 — 재료가 채워진 새 의뢰로.
- **시험 등록·일괄 등록** 에 `?commission_item=` — 시편의 시료·시험 종류·조건이 항목에서
  채워지고, 등록되면 `commission_item_id` 가 붙는다. 시편이 없으면 항목의 방향·수량대로
  시편을 먼저 만드는 단추.
- **시험 상세** 에 「의뢰 12번 ①」 배지 — 클릭하면 의뢰로.
- **시험 목록** 필터 `commission=` — 이 의뢰의 시험만.
- **홈** 에 「접수 대기 n · 시험 중 n · 기한 임박 n」 한 줄(받는 부서 관리자·담당자).
- **커넥터 inbox** — 시편 못 정한 파일의 후보에 「진행 중 의뢰의 항목」 을 함께 보인다
  (3단계).

## 순서

### 1단계 · 절차가 흐른다 (2~3일)

모델·마이그레이션(`TestRun.commission_item_id` 포함) · 상태 표 · 게시판·새 의뢰·상세 ·
알림 둘(`submitted`·`changed`) · 시험 상세에서 「의뢰에 잇기」(있는 시험을 항목에 붙임)
· 진행률. **부서 둘 사이 권한**(보기·결과 읽기)까지 포함한다 — 나중에 얹으면 목록
쿼리를 다 다시 본다.

시험: 상태 이동 표(허용/불허, 말 필요) · 권한(낸 부서·받는 부서·제3부서·draft) ·
진행률(채택 없는 시험은 안 센다) · 시험 삭제·이관 시 링크(`dependents` 자동 수집).
사보타주 등급: 권한과 진행률만.

### 2단계 · 등록이 의뢰에서 시작된다 (1~2일)

`?commission_item=` 채움 · 시편 일괄 생성 · 재료 상세 단추 · 시험 목록 필터 · 홈 한 줄 ·
`delivered` 조건(모든 항목 채워짐) 검사 · 카드 링크(항목의 `deliverable` 카드가
만들어졌는지).

### 3단계 · 운영 (필요해질 때)

`due_soon` 잡 · 커넥터 inbox 후보 · 의뢰서 내보내기(`export.register_renderer` —
성적서 A12 양식이 오면 그 모양으로) · MCP `list_commissions`·`create_commission`
(`mcp_server/` 손편집) · 가이드 문서·공지.

## 정한 것 (2026-09-14, 사용자 답)

1. **받는 부서는 고른다** — 부서 목록(`/workspaces/options`)에서. 측정 조직이 하나가 아니다.
2. **낸 부서 관리자의 승인은 없다.** 필요해지면 `submitted` 앞에 상태 한 줄.
3. **시료가 있으면 시료로, 없으면 새 재료를 글로.** 처음엔 `sample_id` 필수였는데 같은
   날 「신규 재료도 의뢰해야 한다」 로 바뀌었다 — `sample_id` 는 nullable, `material_hint`
   (이름·등급·업체·두께)가 대신 말한다. 받는 쪽이 재료·시료를 등록한 뒤 `POST
   /commissions/{id}/sample` 로 잇는다(시험이 붙은 뒤엔 못 바꿈). 시료 없이는 시험을 못 붙인다.
3-1. **시험 종류도 미정일 수 있다.** 항목의 `test_type_id` 는 nullable, `property_hint`(무엇을
   재는지 — 「80 °C 탄성계수」)가 대신 말한다. 받는 쪽이 `POST …/items/{id}/test-type` 로
   종류(와 조건)를 정한 뒤 시험을 붙인다. 둘 중 하나는 있어야 한다(pydantic validator).
4. **「받을 것」 은 항목마다 고른다** — 카드 블록 키(종류가 되는 블록) 또는 `curves`.
5. **과제 정보는 자유 글(`purpose`)만.** 과제를 특정하는 키는 두지 않는다.

### 1단계 구현 메모 (v1.234)

- 조건 검증·SI 변환은 `app/shared/conditions.py` 로 옮겨 시험 등록과 의뢰가 **같은 함수**를
  쓴다(모듈끼리 직접 못 부르는 규칙). `tests.services.normalize_conditions` 이름은 그대로.
- 받는 부서가 낸 부서 시료에 시편·시험을 만드는 것은 **이미 되던 일**이다 — 재료 계층의
  가시 범위가 「전역 + 열린 부서」 라 시편·시험 등록은 보이는 시료면 된다. 그래서 결과
  읽기 우회 API 는 필요 없었다. 낸 부서가 `restricted` 면 받는 부서가 시료를 못 본다 —
  그때는 부서 설정의 일이다(의뢰 화면이 그 말을 해야 한다 — 2단계).
- 「결과 전달」 게이트는 **항목마다 채택 결과 하나 이상**. 수량을 다 채우라는 것은 아니다 —
  5개 의뢰에 4개 유효인 일이 흔하고, 그 판단은 말로 남긴다.
- 이력 삭제·편집(VOC 의 관리자 기능)은 아직 없다. 필요해지면 VOC 것을 그대로 옮긴다.

### 3단계 구현 메모 (2026-09-18)

셋을 했다 — `due_soon` 잡 · 커넥터 inbox 후보 · MCP `create_commission`.
**의뢰서 내보내기는 안 했다**: 성적서 A12 양식이 아직 없어서, 지금 만들면 양식이
온 날 다시 만든다.

- **기한 알림은 낸 사람에게 안 간다.** 위 `EVENT_KINDS` 표에는 「담당자·낸 사람」
  이라고 적혀 있었는데, 낸 사람이 그 알림을 받고 **할 수 있는 일이 없다** — 재촉은
  알림이 아니라 말로 하는 것이고, 낸 사람 화면에는 기한이 이미 보인다. 받는 쪽만
  본다: 담당자, 아직 없으면 받는 부서 관리자(아무도 안 맡은 건이야말로 조용히
  기한이 지난다).
- **사람마다 한 통으로 묶는다.** 건마다 보내면 기한이 몰린 날 다섯 통이 오고, 그
  다음부터 이 알림은 안 읽힌다. 키(`commission:due:<user>:<날짜>`)에 날짜가 들어가
  하루 한 통이다 — 워커는 콘솔 앱이라 자주 껐다 켜진다(D9).
- **inbox 후보는 잇지 않고 말만 한다.** 시편 후보 줄에 「의뢰 #12 ①번 항목」 을
  적고 링크를 건다. 자동으로 이으면 잘못 맞았을 때 의뢰가 **재지도 않은 것을 잰
  것으로** 적고, 그 숫자는 낸 부서의 보고서로 간다 — 커넥터의 `auto_register` 를
  기본으로 안 켜 둔 것과 같은 판단이다. 잇는 것은 의뢰 화면의 「시험 연결」(거기가
  이력을 남기는 유일한 자리다).
- 판정은 `app/shared/commission_hints.py` 에 둔다 — `pipelines` 가 `commissions`
  를 못 부른다. 상태를 **읽을 때** 센다: 파일이 며칠씩 수집함에 서 있을 수 있어,
  들어온 시각의 상태를 박아 두면 옛날 말을 보인다.
- **MCP 는 `draft` 로만 만든다.** 접수 대기로 내는 것은 사람이 화면에서 한다 —
  받는 쪽 일정을 잡아 두는 일이라 AI 가 대신 결정할 것이 아니다. 기본이
  `dry_run=True` 이고, 받는 부서는 이름으로 줘도 `/workspaces/options` 로 푼다.
