# 셋이 함께 고칠 때 주의할 것

세 사람이 한 저장소를 고친다. 각자 다른 AI 도구를 쓴다(Claude Code · Codex).
이 문서는 **왜 이렇게 나눴는지**와 **무엇이 실제로 사고를 내는지**를 적는다.

규칙 자체는 [AGENTS.md](../AGENTS.md) 에 있다. 여기는 그 규칙의 배경이다.

---

## 먼저 알아야 할 것 하나

**지침 파일은 아무것도 막지 못한다.**

막는 힘은 세 층이고, 힘의 차이가 크다.

| 층 | 무엇 | 실제로 막히나 |
| --- | --- | --- |
| 기계 | CI 검사 + 브랜치 보호 | **막힌다.** 무슨 생각을 하든 머지가 안 됨 |
| 사람 | CODEOWNERS + 리뷰 필수 | 대체로 막힌다 |
| 선의 | `AGENTS.md` · `CLAUDE.md` | **안 막힌다.** 사고를 줄일 뿐 |

AI 는 지침을 읽고도 안 지킬 수 있다. 사람도 급하면 그렇다. 그래서 규칙을 적는
것으로 끝내지 않고 CI 에 검사를 붙였다 — 그리고 **브랜치 보호는 한 번 웹에서
켜야 한다**(아래 마지막 절).

---

## 어떻게 나눴나

**소유는 사람이 아니라 경로에 붙는다.** 누가 어느 도구를 쓰는지는 상관없다.

```
backend/extensions/**   물성 개발자
그 밖의 전부            플랫폼 개발자
```

### 왜 이 선인가 — 이미 그렇게 만들어져 있었다

`backend/matcore/extensions.py` 가 처음부터 이 분업을 예상하고 만들어졌다.
그 파일 머리말이 이렇게 적어 뒀다.

> 새 물성을 더할 때 계산 파일을 만드는 것까지는 값이 낮았다. 그런데 그 파일을
> **읽게 하려면 중심 코드에 이름을 적어야** 했다. (…) 여러 사람이 각자 물성을
> 붙이면 **같은 줄을 서로 고치게** 되고, 확장을 따로 배포할 길이 없다.

증거도 있다. Ghosh 경화식을 붙인 커밋(`438b0b5`)이 건드린 파일 전부:

```
backend/extensions/README.md
backend/extensions/ghosh_hardening/__init__.py
backend/extensions/ghosh_hardening/equation.py
backend/tests/unit/test_ext_ghosh.py
frontend/package.json                          ← 버전 한 줄
```

중심 코드 0줄, `openapi.json` 0줄, 마이그레이션 0건, 프론트 0줄. **이음매가
실제로 성립한다는 것을 한 번 재 본 것**이다.

### 확장이 부를 수 있는 것 넷

새 물성은 계산·카드 블록·CAE 덱·적합식을 다 가져올 수 있다.

| | |
| --- | --- |
| `matcore.registry.register` | 처리 플러그인 |
| `matcore.cards.register_block` | 물성 카드 블록 |
| `matcore.export.register_renderer` | CAE 덱 |
| `matcore.fitting.register_family` | 적합식 |

**폴더 하나로 안 끝나면 그것은 확장 설계가 잘못된 것이다.** 우회하지 말고 말한다.

---

## 진짜 사고를 내는 것은 계산 코드가 아니다

물성 계산은 각자 자기 폴더에서 하므로 거의 안 부딪힌다. 부딪히는 것은 **모두가
건드리는 파일 다섯**이다.

| 파일 | 왜 위험 | 어떻게 막았나 |
| --- | --- | --- |
| `frontend/package.json` | 릴리스마다 바뀜 — **매번 충돌** | 릴리스는 플랫폼만. 확장 PR 이 건드리면 CI 가 막음 |
| `openapi.json` + `schema.d.ts` | 생성물이라 병합이 무의미 | 확장은 API 를 안 바꿈. 그래도 났다면 **병합하지 말고 재생성** |
| `docs/개발계획.md` | 둘 다 같은 자리에 append | 확장 쪽 기록은 `extensions/<이름>/README.md` 에 |
| `migrations/versions/` | 두 head 가 되면 `alembic upgrade` 가 멈춤 | 확장은 마이그레이션을 안 씀. CI 가 막음 |
| `AGENTS.md`·`CODEOWNERS` | 경계 자체를 바꾸는 파일 | **둘 다 리뷰**해야 머지됨 |

### 생성 파일이 충돌하면

병합하지 않는다. **다시 만든다.**

```powershell
cd backend ; .\.venv\Scripts\python.exe scripts\export_openapi.py
cd ..\frontend ; npm run api:types
```

두 줄을 손으로 합치면 스키마와 타입이 조용히 갈라지고, 그 사실은 런타임에야
드러난다.

## AI 둘이 함께 일할 때만 나는 문제

### 1. 지침이 두 벌이 된다

Codex 는 `AGENTS.md` 를, Claude Code 는 `CLAUDE.md` 를 읽는다. 두 벌로 두면
**한쪽만 고쳐진 채 사람마다 다른 규칙을 따르게 된다.**

`AGENTS.md` 를 정본으로 두고 `CLAUDE.md` 는 그것을 가리키기만 한다.
`tests/architecture/test_agent_docs.py` 가 `CLAUDE.md` 가 길어지면(= 규칙을
베끼기 시작하면) 실패한다.

두 도구 다 **작업하는 폴더까지 내려오며** 지침을 합치므로,
`backend/extensions/AGENTS.md` 에 좁은 규칙을 두면 그 폴더에서 일하는 사람의
도구가 그것을 읽는다.

### 2. 「친절하게 고쳐 주는」 것이 충돌이 된다

원래 지침에 이런 조항이 있었다.

> 기존 배치가 이 문서의 규칙과 어긋나면 **작업 스코프 안에서 바로잡는다.**

이건 65의 부채(436커밋 · 프론트 122파일 평면)를 막으려고 일부러 넣은 것이다.
그런데 셋이 함께 고치는 저장소에서는 **남의 파일을 「규칙에 맞게」 고치는 것이
정당해진다.** AI 는 특히 그렇게 한다 — 눈에 보이는 어긋남을 두고 가지 않는다.

그래서 단서를 붙였다: **자기 소유 경로 안에서만.** 시험이 그 문구가 사라지면
실패한다.

### 3. 한 PR 에 두 사람의 일이 섞인다

확장을 고치면서 중심도 함께 고치면 CI 가 막는다
(`scripts/check_boundary.py`). 막을 때 **무엇을 왜 막는지, 무엇을 하면 되는지**
함께 말한다.

```
확장과 중심을 한 PR 에서 함께 고쳤습니다.

  backend/matcore/fitting/__init__.py
      — 중심 계산. 확장은 등록 함수로만 붙는다

두 사람의 일이 한 PR 에 섞이면 리뷰도 되돌리기도 어려워집니다.
확장 변경과 중심 변경을 PR 두 개로 나누세요.
```

**중심만 고치는 변경은 안 막는다.** 플랫폼 개발자의 평범한 일까지 막으면
사람들은 검사를 끄는 방법부터 찾는다.

## 남아 있는 마찰점 둘 — 미리 알아 두면 덜 아프다

### 프론트에는 확장 이음매가 없다

새 물성은 대개 화면에 저절로 뜬다. 프론트 전체에서 물성 키를 박아 둔 곳이
`ProcessingPanel.tsx` 두 줄(`tensile`)뿐이고, 나머지는 서버가 주는 정의를 보고
그린다.

**다만 새 물성이 전용 화면을 원하면** 그때는 확장 개발자가 플랫폼 영역에 들어와야
한다. 그 시점에 협의한다 — 미리 만들어 두지 않는다.

### 새 물성이 DB 에 저장해야 하면 경계가 깨진다

ADR 0016(선언 물성)이 대부분을 데이터로 처리하므로 보통은 필요 없다. 필요해지는
순간 마이그레이션이 필요하고, 그건 플랫폼 영역이다.

**규칙: 확장은 마이그레이션을 쓰지 않는다. 필요하면 요청한다.** 필요해졌다는
것 자체가 설계를 다시 볼 신호다.

## 일하는 리듬

- **짧은 브랜치, 자주 머지.** 확장은 폴더가 갈려 있어 오래 두어도 덜 아프지만,
  플랫폼 쪽은 생성 파일 때문에 오래 두면 충돌이 쌓인다.
- **릴리스는 플랫폼 개발자만.** 버전을 안 올린 커밋은 배포를 안 만들므로
  ([auto-tag.yml](../.github/workflows/auto-tag.yml)) 나머지는 `main` 에 자유롭게
  커밋하면 된다. 배포 시점만 따로 정한다.
- **한 물성은 한 사람이.** 폴더를 사람 단위가 아니라 **물성 단위**로 쪼갠다
  (`extensions/ghosh_hardening/`, `extensions/<다음 물성>/`). 확장 로더가 폴더를
  훑는 방식이라 이 분할에 비용이 0이다.

## 검증은 셋 다 각자 돌린다

```powershell
cd backend
.\.venv\Scripts\ruff.exe format . ; .\.venv\Scripts\ruff.exe check .
.\.venv\Scripts\mypy.exe
.\.venv\Scripts\python.exe -m pytest
cd ..\frontend ; npm run build
```

**스위트를 둘 동시에 돌리지 않는다.** 같은 시험 DB(`matnexus_test`)를 물고 서로
기다리다 멈춘다. 실제로 겪었고, 그때 증상은 「틀린 결과」가 아니라 **아무 결과도
안 나오는 것**이었다 — 한동안 새 코드를 의심했다.

증상이 나면 코드보다 먼저 이것부터 본다.

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like '*pytest*' }
```

살아 있는 pytest 가 하나라도 있으면 **그것이 원인이다.** 배경 작업을 죽이는 것과
프로세스를 죽이는 것은 다르다.

## 한 번은 웹에서 눌러야 하는 것

파일로 못 하는 설정이 둘 있다. **이걸 안 켜면 위의 CI 검사가 있어도 그냥 push
로 넘어간다.**

GitHub 저장소 → **Settings → Branches → `main` 브랜치 보호 규칙**에서:

1. **Require a pull request before merging** — 켠다
   - **Require review from Code Owners** — 켠다 (이게 `CODEOWNERS` 를 강제한다)
2. **Require status checks to pass before merging** — 켠다
   - 목록에서 `verify` (CI - Windows) 를 고른다

그리고 [.github/CODEOWNERS](../.github/CODEOWNERS) 의 `@플랫폼-개발자`·
`@물성-개발자` 자리에 **실제 GitHub 아이디**를 넣는다. 그 전까지는 리뷰 요청이
아무에게도 안 간다.
