# [계획] MaterialTwin 이식

## 원칙 셋

1. **MatNexus 구조는 그대로 둔다.** 겹치는 기능(인제스트·처리·피팅·점탄성·카드·
   조직·운영)은 전 항목 MatNexus 가 우세하다 — 받지 않는다.
2. **받는 것은 「이쪽에 없는 서비스」다** — 물성 카탈로그(데이터+출처+등급 모델)와
   그 소비면(대표값·비교·Ashby·LS-DYNA·측정법). 새 모듈로 받아 기존 표를 건드리지
   않는다.
3. **데이터가 본론이다.** MaterialTwin 의 진짜 자산은 코드가 아니라
   `materialtwin.db` — 출처·등급·조건이 붙은 물성값 42,209건이다. 시험 데이터
   75건은 곡선 파일이 스냅샷에 없어 이관 대상이 아니다.

  만 빈다.

## 단계 계획

### 0단계 — 설계 결정 (ADR 1편, 반나절)

- **카탈로그는 별도 모듈이다.** `app/modules/catalog` ↔ `frontend/src/modules/catalog`.
  기존 `materials` 표는 불변 — 카탈로그 재료는 문헌상의 등급/제품이고 사내 재료는
  실물 lot 이라 수명주기가 다르다. 연결은 사내 재료 쪽에 선택 링크 하나
  (`catalog_material_id`, SET NULL)로만.
- **표 4~5개**: catalog_materials(계통·역할 태그 포함) · catalog_sources ·
  catalog_values(value+unit(SI)+conditions JSONB+method+tier+source FK) ·
  catalog_definitions(271키 — SI 단위·조건축·규격). 기준정보 `property_item` 과는
  **매핑 표**로 잇는다(억지 통합 금지 — 축의 목적이 다르다: 기준정보는 선언 물성
  입력용, 271키는 카탈로그 색인용).
- **원본 보존 원칙**: tier·조건·출처·정정 이력을 그대로 나른다. 값을 지어내지도
  고치지도 않는다 — MaterialTwin 의 「빈 칸이 틀린 값보다 낫다」 와 MatNexus 의
  「참고값은 신뢰 키로 못 나간다」 는 같은 독트린이다. tier4 도 똑같이 쓴다 —
  배지·출처로 구별만 하고 기본 제외하지 않는다(2026-09-06 사용자 결정:
  추정·가정값도 필요해서 모은 데이터다).

### 1단계 — 카탈로그 모듈 (1~2주) ★본론

- 마이그레이션 + 이관 스크립트 `scripts/import_materialtwin.py`:
  SQLite 를 직접 읽어 PG 에 적재. **멱등**(자연키: 재료명 / doi>hash>url /
  재료·키·출처·조건), **드라이런 기본**, 적재 후 **무결성 검사 축소판**
  (FK·단위 일치·tier 범위·(BH)max 물리 검산 등 MaterialTwin `integrity_check` 에서
  추림). MaterialTwin 의 비파괴 union 병합기 설계를 차용 — 재실행·갱신관에도 안전.
- 화면: 카탈로그 목록(패싯: 계통·도메인·제조사·분류 + **물성값 범위 필터**,
  표시 단위 입력→SI 환산) · 상세(도메인별 표, **tier 배지 + 대표값/대안값 칩 +
  밀린 이유 + 조건 차이** — MaterialTwin UX 그대로가 배울 것) · 사내 재료 상세에
  카탈로그 연결 섹션.
- 대표값 선택기(`catalog_compare.py`)와 대안 주석기(`catalog_alternatives.py`)는
  (재료·키·값·조건·tier·출처) 6칸만 요구하는 순수 로직이라 shared 로 포팅 가능.

### 2단계 — LS-DYNA 렌더러 (3~5일)

- `matcore/export` 렌더러 등록제에 **dyna 렌더러 추가** — *MAT_ELASTIC/024(표
  소성)/006(점탄성)/076(다항 Prony) + 열(*MAT_THERMAL_ISOTROPIC) + CTE 곡선.
  MaterialTwin `dyna_export.py`(1,500줄)를 참고하되 우리 렌더러 틀·단위계 파생에
  맞춰 다시 쓴다(통째 이식 아님).
- **값 출처 각주**($ 주석 + 참고문헌 블록)를 렌더러 공통 기능으로 — 카탈로그 값뿐
  아니라 기존 카드 내보내기에도 출처 스냅샷이 있으니 같은 틀로.
- BOM 붙여넣기 매칭 화면(MID·재료명→퍼지 매칭→덱).

### 2.5단계 — 혼합 덱 (계획만, 시점 미정 — 2026-09-06 사용자 결정)

BOM 매칭을 문헌 전용에서 **「사내 확정 카드 우선 + 문헌 보충」 혼합**으로 키운다:
후보 목록에 사내 카드(실측)가 문헌과 같이 서고 기본 선택, 카드가 있는 부품은
곡선 덱(*MAT_024)으로·없는 부품은 문헌 스칼라로 메꿔 **한 파일**로 — 각주가
어느 쪽인지 말한다(사내는 「시험 n건」, 문헌은 「논문·tier」). 매칭 기억(한 번
고른 「BOM 이름→재료」 저장)과 사내 연결(catalog_links) 자동 확정을 **함께**
만든다 — 한 몸의 기능이라 따로 만들면 두 번 일한다. 다열(엑셀 통째) 붙여넣기의
열 매핑도 이때. 경계상 가능함은 확인됨(모델 참조 허용, 카드 blocks 는 Deck 이
먹는 모양 그대로).

### 3단계 — 활용 화면 (3~5일)

재료 비교 매트릭스(카탈로그 재료 n종, 상대 막대·후보 칩) · Ashby 차트(축 자유
선택·로그·색상 그룹) · 커버리지 격자(계통×도메인, 축소판).

### 4단계 — 측정법 모듈 (2~3일)

`app/modules/metrology` — 계측기·측정능력 2표 + 데이터 이관 + 「물성→기법·규격→
장비」 화면, 「잴 장비 없는 물성」 일급 표시. 안내서(guide)와 상호 링크.

### 5단계 — 선택 (후순위, 요청 시)

합성 곡선(스칼라→σ-ε, 「합성」 표지) · MCP 노출(MatNexus 인증·권한과 접합 설계
필요 — MaterialTwin 은 무인증 단일 사용자 전제였다) · 토우 보정·시컨트 E 처리
단계 · Johnson-Cook 피팅(확장 경로 — 물성 개발자 협의, backlog).

### 이식하지 않는 것

인제스트·파서·처리·피팅·점탄성(전부 MatNexus 우세) · 시험 데이터 75건(곡선 파일
미포함) · HEAX 배포물·drive-sync·수집 파이프라인(데이터만 받는다) · 인증 대체.
MaterialTwin 의 방법론 문서(1MB+)는 코드와 별개의 자산이니 폴더째 보존.

## 위험과 주의

- **소유 경로**: catalog·metrology·렌더러는 중심 코드 = 플랫폼 개발자 소유라
  진행 가능. 피팅 모델 추가만 `extensions`(물성 개발자 경로)라 협의 후 backlog.
- **라이선스**: 카탈로그 값은 출처 명시된 사실 데이터이고 원문 PDF 는 스냅샷에
  없다(경로만 기록됨 — 이관 시 local_path 는 참고 문자열로만 유지). MaterialTwin
  문서에 저작권 입장이 명시돼 있다.
- **tier4 표기**: 배지·출처로 구별하되 어느 경로에서도 기본 제외하지 않는다
  (2026-09-06 사용자 결정 — 원본 README 의 「해석 투입 금지」 경고는 표기로만
  계승). 채택은 스냅샷이라 재이관이 채택된 값을 조용히 바꾸지 않는다.
- **다른 세션 충돌**: composite 모듈·realm.ts 등 미커밋 작업과 겹치지 않게 신규
  모듈·신규 파일 위주로 작업한다.
- **문서-코드 어긋남**: MaterialTwin 문서 수치는 2026-09-01 기준이라 라이브 DB
  (42,209행)와 다르다 — 이관 검증은 항상 DB 실측으로.

독립적으로 진행 가능하다.

## 라벨 정합 — 결정 (2026-09-05, 실측 근거)

카탈로그와 우리 라벨의 실측 대조 결과에 대한 사용자 결정과 그 처리:

1. **물성 이름.** 확인 결과 — 항복강도·인장강도(+연신율·경도)는 기본 물성 항목
   (`BUILTIN_PROPERTY_ITEMS`)에 **이미 있고** 처리 산출(`proof_stress`·
   `tensile_strength`)과 대응까지 걸려 있다. 포아송비·밀도는 선언 물성이 아니라
   **재료의 기본 칸**(`Material.density_si`·`poisson_ratio`)이다 — 항목으로 또
   받으면 같은 값을 두 곳에 받게 되므로 목록에 추가하지 않는다(개발 DB 에 5종만
   보였던 것은 ensure 미실행 상태였을 뿐). 잇는 지점은
   `catalog/mapping.py` 의 `PROPERTY_ITEM_MAP` 한 곳이고, 자리(declared/column/
   measured)를 구분한다 — 계약 테스트가 양끝을 실물에 대고 검사한다.
2. **이름 개명(열전도도→열전도율, 열팽창계수→선팽창계수(CTE)) — 결정됨, 실행은
   조율 후.** 두 라벨은 matcore 내보내기 needs·fitting·선언 물성·프론트 등
   25개+ 파일에 문자열로 박혀 있고, 그중 다수가 **다른 세션이 지금 미커밋으로
   고치는 파일**(LVE/CTE 덱 작업)이다. 기준정보 개명 기계(별칭 흡수)+코드 참조
   일괄 치환을 한 커밋으로, 그 작업이 합류한 뒤 진행한다. 매핑 표의 label 만
   따라 바꾸면 카탈로그 쪽은 끝난다(MT key 가 안정 id).
3. **재료 분류.** 저장은 원본 그대로(무손실), **표기를 우리 family 축에 맞춘다** —
   `CATEGORY_MAP`(metal→Metal …). 우리 축에 아직 없는 값(Ceramic 등)은 연결
   단계에서 family 용어로 생성.
4. **서술형 이름(64%가 60자 초과).** 카탈로그 재료를 사내 재료로 연결/승격할 때
   짧은 규격명만 grade 로, 서술형 전체는 **별칭(alias)·details** 로 받는다 —
   record_name 규칙(등급+상세+두께)을 서술형으로 오염시키지 않는다.
5. **재료 고유 id — 설계(구현은 materials 모듈 작업 합류 후).** 현재 사내 재료의
   사람용 식별자는 record_name 뿐인데, grade 개명이 이름을 재계산하므로 보고서·
   외부 문서의 인용이 낡는다. 카탈로그 연결에도 안정 참조가 필요하다. 설계:
   `materials.code` — 등록 시 연번으로 자동 부여(`M-000123`), **불변·유니크**,
   화면 표시·검색 지원, 기존 재료는 등록순 백필. 이름은 사람이 부르는 것,
   code 는 기계와 문서가 무는 것. materials 모듈(routes·schemas·services)을
   다른 세션이 고치는 중이라 충돌을 피해 그 합류 뒤 별도 커밋으로 구현한다.

## 단위 — 확정 (2026-09-06)

**값은 양쪽 다 SI 라 숫자 변환이 0건이다.** 다른 것은 표기뿐 — MT `J/(kg*K)`·
`kg/m^3` vs matcore `J/(kg.K)`·`kg/m3`. 처리 방식: ① 카탈로그 화면은 원본 표기
그대로(무손실 — matcore 에 없는 차원·눈금이 실재), ② 채택은 SI 값을 그대로
보내고 `input_unit` 을 비운다(서버가 정본 SI 로 해석), ③ 표기 등가는
`mapping.SI_UNIT_EQUIV` + 계약 테스트가 지킨다(매핑 10종의 mt_unit 을 라이브
카탈로그 정의와 실측 대조 — 10/10 일치). 등가표에 없는 단위(HV·ShoreA·전기
차원)는 채택 경로에 오르지 못한다.

## 진행 기록

- **2026-09-06 — 문헌 재료 → 사내 재료 만들기** (카탈로그 상세의 「사내 재료로
  등록」). 이름 배치는 **세 겹 지칭**으로 확정(사용자 결정): ① grade 는 규격·
  제품급이면 카탈로그 grade(실측 8%만 보유), 서술형이면 사람이 짓는다 ② alias
  에 원본 이름 **전체**(실측 최장 198자 ≤ 200 상한) ③ 만들자마자 문헌 연결 —
  이름을 어떻게 줄여도 원본 추적이 안 끊긴다. 긴 material_class(자유 문장)는
  분류 칸에 프리필하지 않는다(기준정보 오염). 생성은 기존 POST /materials 를
  그대로 재사용 — 이름 조립·기준정보·유니크는 서버 한 곳(ADR 0004), 백엔드
  신규 코드 0. 물성값은 생성 후 「카탈로그에서 채우기」(연결이 이미 걸려 있음).
