## 1. 처리 결과가 있는 시험은 영구 삭제가 터진다 🔴 — 버그

`_purge_run`(`trash/services.py:553-563`) 은 `curves` 와 `test_summaries` 만 지우고
시험 행을 지운다. 그런데 `processing_results.test_run_id` FK 에는 **ondelete 가
없다**(`processing/models.py:153-155`). 처리 결과를 한 번이라도 저장한 시험을
휴지통에서 영구 삭제하면 FK 위반 → 500 이고, `purge_many` 는 한 트랜잭션이라
**함께 고른 다른 것까지 전부 안 지워진다.**

같은 함정을 이미 두 번 겪고 두 번 다 손으로 풀었다 — 레시피 영구 삭제는
`ProcessingResult.recipe_id` 를 먼저 NULL 로 끊고(`trash/services.py:463-470`),
재료 트리는 층마다 flush 한다(2026-08-31 실측 주석). 시험↔처리 결과만 빠졌다.
`tests/api/test_trash.py` 에 처리 결과가 낀 조합이 없어서 안 걸렸다.

**구현 스케치** — `_purge_run` 에서 `ProcessingResult` 를 함께 DELETE 한다(결과는
그 시험의 파생물이라 남길 이유가 없다 — 채택 요약도 이미 같이 지워진다). 마이그레이션
없이 끝나고, 처리 결과 낀 영구 삭제 시험을 하나 박는다. 이때 그 결과의 Parquet
(`processing/{run_id}/…`)도 지워야 하는데, 그것이 아래 2번과 한 몸이다.

## 2. 처리·마스터커브 파일은 영영 안 지워진다 🟠

filestore 에서 무언가를 실제로 지우는 곳은 셋뿐이다 — 영구 삭제(`source/` 폴더만),
수집함 정리, 저장소 정리(`test-runs/` 아래 고아·만료). 그런데 파일은 네 군데 더
쌓인다:

| 경로 | 쓰는 곳 | 지우는 곳 |
| --- | --- | --- |
| `test-runs/{run}/source/` | 업로드 | 영구 삭제 + 정리 ✅ |
| `test-runs/{run}/curves/` | 파싱 | 정리(고아 스캔) ✅ — 영구 삭제 직후엔 고아로 남았다가 정리가 잡는다 |
| `processing/{run}/…` | 처리 결과 저장 (`processing/routes.py:211`) | **없음** |
| `master-curves/{run}/…` | 마스터커브 (`viscoelastic/services.py:174,477`) | **없음** — 행은 CASCADE 로 사라져도 파일은 남는다 |
| `guide/{asset}/…` | 안내서 그림 | **없음** |

고아 스캔(`existing_run_dirs`)도 `test-runs/` 만 걷기 때문에 이 파일들은 **세지도,
지우지도 않는다.** 처리 결과는 「다시 돌리면 새 파일」 인 append-only 설계라
(그 자체는 옳다 — 옛 결과가 변하지 않는 것이 목적) 쌓이는 속도가 가장 빠른
축이고, 디스크가 조용히 찬다.

**구현 스케치**

- 영구 삭제에서 시험의 `processing/{run}`·`master-curves/{run}` 폴더를 함께 지운다
  (1번과 한 커밋).
- 고아 스캔을 `processing/`·`master-curves/` 로 넓힌다 — 폴더 이름이 곧 run_id 라
  같은 방식이 그대로 통한다. 행 없는 폴더 = 고아.
- 저장소 리포트의 총량에 이미 잡히고는 있으니(전체 크기만 센다), 리포트에
  「처리 n GB · 마스터커브 n GB」 줄만 더해 주면 쌓임이 보인다.

## 3. 부서 합치기, 이름이 겹치면 500 🟠

`merge_into` 의 FK 걷기는 `materials.owner_workspace_id` 와
`format_profiles.owner_workspace_id` 도 일괄 UPDATE 하는데, 두 표에는 부서 범위
유일 제약이 있다 — `(owner_workspace_id, record_name)` · `(owner_workspace_id, key)`.
**양쪽 부서에 같은 이름의 재료(또는 같은 key 의 읽을 형식)가 있으면 UPDATE 가
IntegrityError 로 터지고, 잡는 곳이 없어 500 이다.** 가져오기(import)에는 409
처리를 넣었는데 합치기에는 없다.

재료 이름은 grade+details+두께로 만들어지므로, 두 부서가 같은 재료를 각자 등록해
쓰다가 합치는 — 합치기를 하는 바로 그 상황에서 — 겹칠 개연성이 낮지 않다.

**구현 스케치** — 합치기 전에 두 부서의 재료 이름·형식 key 교집합을 세어, 있으면
「겹치는 이름 n건: … 먼저 한쪽을 지우거나 이름을 바꿔 주세요」 를 422 로 돌려준다.
미리보기(옮겨질 목록)에도 같은 경고를 싣는다 — 누르기 전에 아는 것이 이 저장소의
무늬다. IntegrityError → 409 안전망도 가져오기처럼 깐다.

> 정정: [관리자 기능 개발](%5B완료%5D%20관리자%20기능%20개발.md) 문서에 「합친 뒤
> 같은 key 의 시험 종류가 중복될 수 있다」 고 적었는데, **사실이 아니다** — 시험
> 종류 key 는 부서 소유와 무관하게 전사 유일이라(`uq_test_types_key`) 애초에 중복이
> 못 생긴다. 진짜 충돌 지점은 여기 적은 재료 이름과 형식 key 다.

## 4. 기준정보 Expand 단계 — 완주 시점을 정하자 🟠

재료의 family/category/grade, 시료의 제조사 등, 시험의 장비/부문 — 전부 **문자열
컬럼과 `*_term_id` FK 가 병존**하고 읽는 쪽은 아직 문자열을 읽는다(ADR 0010 의
Expand 단계). 어긋남 점검이 6시간마다 돌고, 수리도 있고, 용어 개명이 문자열을
따라 고치는 훅도 있다 — **감시 장치는 다 있다.** 문제는 이 상태가 「단계」 가
아니라 「상태」 가 되어 가는 것이다: 병존이 길어질수록 문자열만 고치는 새 코드가
스며들 자리가 넓어지고, 어긋남 점검은 사후 탐지지 예방이 아니다.

**구현 스케치** — 큰 공사가 아니라 **마감 결정**이다. ① 개발 DB·운영 DB 에서
어긋남 0 이 몇 주 유지되는지 확인하고(`vocabulary_drift_checks` 가 이미 「언제부터
0」 을 답한다), ② Backfill(빈 FK 채우기 — 수리 기능이 곧 그것이다) 실행,
③ Contract — 읽는 쪽을 term 으로 돌리고 문자열은 표시 캐시로 격하 또는 제거.
축 하나(예: 시편 규격)로 먼저 완주해 본을 만든다.

## 5. 선언↔측정을 잇는 열쇠가 라벨 문자열이다 🟡

선언-실측 격차 비교(`statistics/routes.py:551-613`)와 물성 표 화면은 선언 물성의
`item`(기준정보 용어 이름)과 측정 스칼라의 `label` 을 **이름 문자열로 join** 한다.
용어를 개명하거나 플러그인이 라벨을 바꾸면 오류 없이 「매칭 안 됨」 으로 조용히
빠진다. 지금은 항목이 적어 실해가 없지만, 확장(extensions)이 스칼라를 더할수록
이름 충돌·이탈 여지가 커진다.

**구현 스케치** — 매핑을 한 곳에 표로 둔다: `curvedata.DECLARED_KEYS` 가 이미
이름→(파이프라인 key, SI 단위) 표이므로 이것을 정본으로 삼아 spec-gap 도 label 이
아니라 key 로 잇게 한다. 당장 급하지 않으니 6번과 함께 한 번에.

## 6. 파이프라인이 아는 선언 물성이 3종뿐이다 🟡

`@declared_…` 참조로 처리 파이프라인에 들어가는 선언 물성은 탄성계수·포아송비·
밀도 셋이다(`curvedata.DECLARED_KEYS`). 나머지 항목(항복강도·인장강도·열팽창 등)은
선언해 둬도 파이프라인에서 **오류 없이 조용히 무시**된다. 사용자가 「적어 놨는데
왜 안 쓰나」 를 알 길이 없다.

**구현 스케치** — 표에 항목을 더하는 일이라 작다(항목당 두 줄 + 시험). 더하지
않는 항목이라면, 처리 입력 화면에서 「이 항목은 파이프라인 참조를 지원하지
않습니다」 를 보여 주는 쪽이라도.

## 7. grade 오타 중복은 아무도 못 잡는다 🟡

재료 유일성은 `(부서, record_name)` 이고 이름은 grade+details+두께다. grade 를
`SGARC440` / `SGARC 440` 으로 다르게 적으면 같은 실물이 두 줄이 된다. grade 가
기준정보 축(open)이라 피커가 오타를 줄여 주지만, 새 용어 생성이 열려 있는 한
막지는 못한다 — 그리고 그것이 맞다(등록 병목을 만들지 않는다).

**구현 스케치** — 막지 말고 **보여 준다**: 재료 등록 시 trigram 유사 이름 상위
몇 건을 「비슷한 재료가 이미 있습니다」 로 띄운다. 검색용 GIN 인덱스가 이미 있어
쿼리 한 줄이다. 사후로는 기준정보의 용어 병합이 이미 수습 수단이다(grade 병합 →
이름 재계산 훅까지 있다).

## 8. 안내서 문서는 지워지면 못 돌아온다 🟡

`guide_documents`/`guide_sections` 는 `deleted_at` 이 있는데 휴지통 대상 목록
(`trash/services.py` 의 KINDS)에 없다 — 소프트 삭제는 되지만 복구·영구삭제 화면이
없어, 지운 안내서는 DB 에 영원히 「지워진 채」 남는다. 휴지통 FLAT_KINDS 에 한 줄
더하면 끝날 모양새이니, 안내서를 실제로 지우는 일이 생기기 전에 넣어 둔다.

## 관찰 — 지금은 손대지 않지만 알고 있어야 하는 것

- **시험의 회차 유일 제약만 부분 인덱스가 아니다.** 재료·시료·시편은 「살아있는
  것 기준 유일」(WHERE deleted_at IS NULL)인데 시험만 소프트 삭제된 행이 회차
  자리를 계속 붙든다. 실해는 없고(회차는 자동 증가) 복원 충돌도 없는 대신, 지운
  시험의 회차가 영구 결번이 된다 — 계보 보존으로 보면 오히려 맞는 면도 있다.
  통일할지는 실제 불편이 나올 때 정한다.
- **데이터 편집 감사는 부분이다 — 설계다.** 감사는 되돌릴 수 없는 것만 남긴다는
  원칙(카드 확정·삭제·개명 등)이라 재료 PATCH·시편 치수 수정은 안 남는다. 다만
  시편 치수 덮어쓰기(`PUT /specimens/{id}/dimensions`)는 계산 결과를 바꾸는
  손편집이라, 감사 대상 승격을 다음 감사 정비 때 저울에 올린다.
- **레시피에는 이력이 없지만 결과가 이력이다.** 레시피 수정은 덮어쓰기지만, 모든
  처리 결과가 실행 시점의 단계 전체(`steps_snapshot`)와 라이브러리 버전까지 들고
  있어 재현성은 결과 쪽에서 성립한다. 옳은 배치다.
- **휴지통의 `_UNIQUE_COLUMNS` 는 DB 부분 유니크 인덱스와 손 동기화하는 두 번째
  목록이다** — 코드 주석이 이미 경고한다. 새 부분 유니크를 만들 때 같이 고칠 것.

## 이번에 확인하고 문제없다고 판정한 것

다음에 같은 점검을 반복하지 않도록 남긴다 (2026-09-05 기준):

- **처리 결과·앙상블은 append-only.** 다시 돌리면 새 행·새 파일 — 「예전 결과를
  열었더니 값이 달라졌다」 가 구조적으로 불가능하다. 수정·삭제 라우트 자체가 없다.
- **카드의 출처(`source.test_run_ids`)가 자유 JSON 인 것은 의도다.** 카드는 근거를
  들고 있는 스냅샷이라, 시험이 지워져도 카드가 막거나 값을 잃으면 안 된다 —
  `record_names` 를 함께 담아 지워진 뒤에도 읽을 수 있다. 묶음 결과(`members`)도
  같은 설계.
- **SI 정본은 아키텍처 테스트로 못 박혀 있다.** `test_frontend_units.py` 가 프론트
  표를 파싱해 matcore 정본과 전 차원 일치를 검사한다. 두 차례 단위 감사와 일치.
- **같은 파일 두 번 업로드: 사람은 허용+경고, 커넥터는 409.** 재시험일 수 있어
  사람은 안 막고 비고에 적는다 — 의도 주석 확인. 옳은 비대칭이다.
- **`temperature_step_count` 의 NULL≠0 구분과 「514건 못 채움」은 정상.** NULL 은
  「안 세어 봄」, 514건은 온도 채널이 없는 인장류라 셀 것이 없다 — 화면도 별도
  `unknown` 통으로 센다.
- **시편 치수 폴백(실측→시편→규격 공칭)과 면적이 같은 소스를 본다** — 두께는
  실측인데 면적은 공칭으로 계산하던 버그가 고쳐진 구조 그대로다.
- **의존성 레지스트리는 FK 자동 걷기다.** 하드코딩 목록이 없고, FK 아닌 참조
  (워크벤치 바구니)는 EXTRA_CHECKS 로 보탠다. 부서·계정·형식 삭제가 이 길을 탄다.
- **읽을 형식 잠금** — 시험이 1건이라도 있으면 채널 삭제·단위 변경을 막고,
  라벨·순서는 자유. 잠글 것과 열어 둘 것의 경계가 맞다.

반복하지 않는다.
