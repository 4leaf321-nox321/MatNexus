# 운영 핸드북

사고가 났을 때 찾는 문서는 코드 주석이 아니다. 여기에는 **운영자가 손으로 하는 일**만
적는다 — 잠겼을 때, 백업과 복구, 도입 체크리스트, 홈의 운영 경고가 뜨면 할 일.
배포 절차는 [README](../README.md#배포)에, 설계 판단은 [ADR](adr/)에 있다.

## 수칙 — 시스템 관리자는 2인 이상

비밀번호 재설정은 「다른 관리자가 임시 비밀번호를 발급」 하는 길뿐이다. 시스템
관리자가 1명이면 그 사람이 잠기는 순간 복구 경로는 아래 「잠겼을 때」 의 서버
콘솔뿐이다 — 2026-08 말에 실제로 겪었다(비밀번호 착오로 로그인 실패, 콘솔에서
재설정). 계정 화면이 관리자가 1명이면 안내를 띄운다. **코드로 강제하지는 않는다** —
도입 초기에 1인일 수밖에 없는 기간이 있다.

## 잠겼을 때 — 관리자 본인이 로그인할 수 없다

로그인 실패는 같은 계정에서 5회부터 응답이 2초씩 늦어진다(최대 30초, 15분 창).
**잠금은 없다.** 30초를 기다린 뒤 맞는 비밀번호를 넣으면 들어간다.

비밀번호 자체를 모르면 서버에서 직접 되돌린다:

```powershell
cd C:\Server\MatNexus\backend
.\.venv\Scripts\python.exe scripts\set_admin.py --email admin --password '<새 비밀번호>'
```

- 계정이 없으면 만들고, 있으면 비밀번호를 바꾼다. 다음 로그인에서 비밀번호 변경을
  강제한다(`--no-force-change` 는 운영에서 쓰지 말 것).
- 아이디를 바꿔야 하면 `--rename-from <옛 아이디>` 를 함께 준다.
- 끝나면 계정 화면에서 **두 번째 시스템 관리자**를 지정한다 — 이 문단을 다시 읽지
  않으려면.

## 백업 — 매일 03:00, DB 덤프 세대 관리 + 파일스토어 미러

`scripts/deploy/backup.ps1` 이 한 번에 둘을 받는다. DB 에는 곡선의 경로와 해시가,
파일스토어에는 그 내용이 있어서 **같은 시각**에 받아야 한다.

받는 것(`-BackupRoot` 아래):

| 경로 | 무엇 | 세대 |
| --- | --- | --- |
| `db\db-<YYYYMMDD-HHMMSS>.dump` | pg_dump 커스텀 포맷 | 일 7벌 + 일요일분 4벌 |
| `filestore\` | 시험 원본·Parquet·처리 결과 | 미러 1벌(robocopy /MIR) — 불변 파일이라 세대가 필요 없다 |
| `env\.env` | 접속 정보·JWT 비밀키 | 최신 1벌 |
| `LAST_BACKUP.txt` | 언제 무엇을 받았나 | 최신 1벌 |

작업 스케줄러 등록(관리자 PowerShell 에서 한 번):

```powershell
$action  = New-ScheduledTaskAction -Execute 'powershell.exe' `
  -Argument '-NoProfile -ExecutionPolicy Bypass -File C:\Server\tools\MatNexus\backup.ps1 -AppPath C:\Server\MatNexus -BackupRoot D:\MatNexus-backup'
$trigger = New-ScheduledTaskTrigger -Daily -At 03:00
Register-ScheduledTask -TaskName 'MatNexus Backup' -Action $action -Trigger $trigger `
  -RunLevel Highest -User 'SYSTEM'
```

- 워커 프로세스에 넣지 않는다 — 워커가 죽은 날 백업도 조용히 죽는다.
- `backend\.env` 에 `BACKUP_DIR=D:\MatNexus-backup` 을 적으면 서버 화면과 홈이
  **마지막 백업 시각**을 보이고, 36시간이 지나면 붉게 말한다. 안 보이면 없는 것과 같다.
- 백업 드라이브는 DB·파일스토어와 **다른 물리 드라이브**여야 한다.

## 복구 — 한 번은 실제로 해 본다

복구해 본 적 없는 백업은 백업이 아니다. 분기에 한 번 리허설한다:

```powershell
# 확인만 — 새 DB 로 되돌려 본다. 지금 DB 도 파일스토어도 안 건드린다
.\restore.ps1 -BackupRoot 'D:\MatNexus-backup' -DbName matnexus_restore_check

# 실제 복구 — 앱을 먼저 중지한다. 특정 시점 덤프를 고르려면 -DumpFile
.\restore.ps1 -BackupRoot 'D:\MatNexus-backup' -DbName matnexus -AppPath 'C:\Server\MatNexus' -Force
.\restore.ps1 -BackupRoot 'D:\MatNexus-backup' -DumpFile 'D:\MatNexus-backup\db\db-20260901-030000.dump' -DbName matnexus -AppPath 'C:\Server\MatNexus' -Force
```

`restore.ps1` 은 되돌린 뒤 **DB 가 가리키는 파일이 실제로 있는지 센다.** 하나라도
없으면 그 사실을 말한다 — DB 와 파일스토어의 시점이 어긋난 것이다.

복구 뒤에는 `alembic upgrade head` 로 스키마가 코드와 맞는지 본다(덤프가 옛 버전이면
마이그레이션이 남아 있다).

## 홈의 운영 경고가 뜨면

시스템 관리자의 홈에만 붉은 「운영」 줄이 선다. 각각 할 일:

| 경고 | 뜻 | 할 일 |
| --- | --- | --- |
| 백업 — … | 백업 설정이 없거나, 덤프가 없거나, 36시간 넘게 밀렸다 | 위 「백업」. 스케줄러 이력을 본다 |
| 디스크 n% (임계 85%) | 파일 저장소 드라이브가 찼다 | 서버 → 저장소 정리. 오펀·보존만료를 치운다 |
| 보존기간 지난 삭제 n건 | 지운 시험의 파일이 보존기간을 넘겨 남아 있다 | 저장소 정리에서 **사람이** 지운다. 자동 영구삭제는 없다 |
| 실패한 작업 n | 재시도 3회를 다 쓴 백그라운드 작업 | 서버 → 작업 큐. 오류를 읽고 「다시 시도」 |

임계값은 `.env` 의 `DISK_ALERT_PERCENT`(기본 85)로 바꾼다.

## 서버가 멈춘 것 같으면 — `/api/health` 를 본다

실측(2026-09-10, 두 번): 사내망에서 DB 연결이 잠깐 끊긴 뒤 백엔드가 요청을 받지 않는
채로 남았다. DB 는 멀쩡했고 재기동하면 바로 돌아왔다. 그동안 화면은 안 뜨고 AI 는
「자료가 없다」 로 답했다.

`http://<서버>/api/health` 가 **DB 까지 찔러 보고** 답한다:

| 응답 | 뜻 | 할 일 |
| --- | --- | --- |
| `200 {"status":"ok","database":"ok"}` | 앱과 DB 모두 정상 | — |
| `503 {"status":"degraded","database":"unreachable: …"}` | 앱은 살아 있는데 DB 에 못 닿는다 | PostgreSQL 서비스·네트워크를 본다. DB 가 돌아오면 앱은 스스로 재연결한다 |
| 응답 없음 (타임아웃) | 앱이 멈췄다 | 서비스면 감시 작업이 3분 안에 다시 띄운다(아래). 창이면 `run_server.ps1` 창을 닫고 다시 띄운다 |

연결 시도는 10초에 끊긴다(`connect_timeout`) — 매달린 연결이 서버를 통째로 붙드는 일이
없게. 맺어진 연결이 망 끊김으로 조용히 죽는 것은 TCP keepalive 가 잡는다(30초 놀면
10초 간격으로 세 번 찔러 봄, `database.py`) — 안 켜면 질의 도중 끊긴 스레드가 윈도우
기본 재전송 시간(십수 분)만큼 매달린다.

**보는 사람이 없으면 health 는 소용없다** — 그래서 감시 작업이 본다(2026-09-17).
`service.ps1 -Action Install` 이 `MatNexus-Watchdog` 작업을 함께 등록하고, 서비스가 있는
서버는 `deploy.ps1` 이 배포 때마다 등록·갱신한다(따로 돌릴 것 없음): 1분마다
`/api/health`, 잇달아 세 번 답이 없으면 `MatNexus` 서비스를 다시 띄운다. 서비스가
`Running` 인데 답이 없을 때만이다 — `Stopped` 면 배포(deploy.ps1 이 교체 동안 멈춘다)나
관리자가 멈춘 것이라 손대지 않고, 죽은 프로세스는 NSSM 이 되살린다. 10분에 한 번까지만
하는 것은 뜨자마자 죽는 것을 1분마다 되살리면 원인이 안 보여서다. 503 은
재시작하지 않는다 — 앱은 살아 있고 DB 가 돌아오면 스스로 재연결한다.

    .\watchdog.ps1 -AppPath 'C:\Server\MatNexus' -Status      # 작업 상태 · 잇단 실패 · 최근 로그
    C:\Server\MatNexus_data\logs\watchdog.log                 # 정상일 때는 조용하다(회복 때만 한 줄)

재시작이 잦으면(로그에 「다시 띄웁니다」 가 되풀이) 감시가 아니라 앱이 문제다 —
`service-server.log` 의 첫 줄과 `app.log` 를 본다.

## 서비스로 띄운다 — 재부팅해도 뜨고, 죽으면 되살아난다 (2026-09-15)

`service.ps1 -Action Install`(배포.md 1-4)이 `MatNexus`·`MatNexusWorker` 를 Windows
서비스로 등록한다(NSSM 동봉). 그 뒤로:

- 부팅 때 저절로 뜬다(지연 자동 시작 — PostgreSQL 이 먼저). 프로세스가 사라지면 10초 뒤
  SCM 이 되살린다. **떠 있는데 멈춘** 상태(응답 없음)는 서비스가 못 알아채므로 감시 작업
  (`MatNexus-Watchdog`, 위 절)이 health 를 보고 다시 띄운다.
- `deploy.ps1`·`rollback.ps1` 이 서비스를 알아서 멈추고 다시 띄운다. 배포 뒤 창을 열 일이
  없고, 워커도 새 코드로 다시 뜬다.
- 콘솔 출력은 `<AppPath>_data\logs\service-server.log` · `service-worker.log`. 「뜨자마자
  죽는다」 는 대개 여기 첫 줄에 이유가 있다 — 흔한 것은 포트가 이미 물려 있음(창 방식
  서버가 아직 떠 있음), `.env` 없음, 가상환경 없음.
- 서비스로 등록한 뒤 `run_server.ps1` 창을 또 띄우면 같은 포트를 두 번 무는 것이다 —
  `run.py` 가 「이미 쓰고 있다」 고 멈춘다. 그때는 창을 닫는다.
- 상태·재시작·해제: `.\service.ps1 -AppPath … -Action Status | Restart | Uninstall`.

## 배포가 스스로 하는 것 — 코드의 씨앗 맞추기

기본 축·사내 물성 항목·시험 종류·형식 프로파일은 코드에 씨앗이 있다. 설치 때 심고
그 뒤로는 관리자가 고친 것을 배포가 되돌리지 않는데, 그러다 **코드가 뒤에 더한 것**
(새 채널, 프로파일 규칙, 차원 선택지, 항목 속성)까지 못 들어오는 일이 있었다 —
실측(2026-09-12): DMA 마스터커브 자동 등록 규칙이 08-31 에 코드에 들어갔는데 그 전에
설치된 서버는 오류 없이 그 기능이 없었다.

이제 `deploy.ps1` 이 `alembic upgrade` 뒤에 `scripts/refresh_builtins.py` 를 돌린다.
없는 것은 만들고 빠진 것만 채운다 — **관리자가 고친 라벨·열 이름·값은 그대로다.**
몇 번 돌려도 같다. 손으로 돌리려면:

```powershell
cd C:\Server\MatNexus\backend
.\.venv\Scripts\python.exe scripts\refresh_builtins.py
```

## 배포 뒤 「dynamically imported module」 — 열어 둔 화면이 옛 index 를 든 것

**증상**: 배포 뒤 몇몇 화면(계정 관리·카탈로그·검색 같은 **늦게 읽는 화면**)이
"Failed to fetch dynamically imported module" 로 안 열리고, 새로고침하면 된다.
매일 릴리스하니 자주 났다(2026-09-16).

**원인**: 화면은 처음 한 번 `index.html` 을 받고, 화면마다 청크 파일을 **그때그때**
받는다. 청크 이름에는 내용 해시가 붙어 배포마다 바뀐다. 배포는 운영 폴더를 통째로
바꾸므로, 배포 **전에** 열어 둔 브라우저는 옛 index 가 가리키는 옛 청크를 찾고 —
그 파일은 이제 없다. 아직 안 들어가 본 화면만 그렇다(들어가 본 화면은 이미 받았다).
서비스가 재시작하는 몇 초 동안도 같은 오류가 난다.

**대응(둘 다 v1.242)**:
- `deploy.ps1` 이 **직전 버전의 `frontend\dist\assets` 를 새 폴더에 이어받는다.**
  해시 이름이라 충돌이 없다. 배포 전에 열어 둔 화면이 옛 청크를 그대로 받아 계속
  돈다 — 한 세대만, 그 다음 배포에는 그 사람도 새로고침한 뒤다.
- 화면은 청크를 못 받으면 **스스로 한 번 새로고침한다**(30초 안에 두 번은 안 한다 —
  서버가 내려간 동안이면 끝없이 돌기 때문). 그래도 안 되면 잠시 뒤 새로고침한다.

## 계산식 — 배포 없이 식 하나를 붙인다

「관리 → 계산식」 에서 시스템 관리자가 적은 식은 저장하는 순간 카드의 식 후보·레시피
단계 목록에 `formula.<키>` 로 뜬다. 자리는 셋 — 곡선에 맞추는 식(경화식·점도식) · 값에서
값을 내는 식(항복비) · 곡선에서 열을 내는 식(ADR 0030). 재시작이 없다 — 기동 때와 저장할 때
서버가 표를 읽어 레지스트리에 넣는다. 기동 로그에 `계산식 N개를 올렸습니다` 가
찍히고, 표를 못 읽으면(마이그레이션 전) 경고만 남기고 식 없이 뜬다.

운영에서 지킬 것 셋:

- **저장 전에 「미리보기」 를 누른다.** 채택된 시험 하나를 골라 실제 곡선으로 돌린다.
  문법이 맞는데 뜻이 틀린 식(축을 바꿔 적음, 단위가 천 배)은 이것으로만 드러난다.
- **고치면 판이 오른다.** 저장된 레시피·결과·카드는 옛 판 그대로다 — 다시 돌리면 새
  판으로 돈다. 뜻이 달라지는 고침은 고치지 말고 **새 키로 만들고 옛 것을 끈다.**
- **쓰는 식은 못 지운다.** 화면이 「쓰는 곳」 을 보여 주고 지우기를 막는다. 대신
  끄면 목록에서만 빠지고 옛 결과는 그대로 읽힌다.

정렬·구간 탐색·회귀 같은 알고리즘은 이 길로 안 된다 — 물성 개발자의 확장 폴더
(`backend/extensions/README.md`)다.

## 누가 고치나 — 「왜 못 고치지」 를 받았을 때 (ADR 0035)

자료를 고치는 사람은 넷이다: 시스템 관리자 · 자료 관리자 · 그 자료의 **등록자** · 그
자료에 **편집을 받은 부서**의 멤버. 소속 부서는 권한을 정하지 않는다. 화면의 자료 머리에
「등록자 ○○ · 편집 부서 ○○」 가 적히고, 못 고치면 까닭과 물어볼 사람이 그 옆에 뜬다.

- **새 자료는 등록자만 고친다.** 팀이 함께 고칠 것이면 등록자가 「권한」 에서 부서에
  편집을 준다. 2026-09-24 전에 있던 자료는 그때의 소속 부서에 편집을 줘 두었다.
- **담당이 바뀌면 넘긴다.** 「권한」 → 등록자 넘기기(아래에 딸린 것까지). 넘길 수 있는
  사람은 등록자와 자료 관리자뿐이다 — 남이 붙인 것은 건너뛰고 이름을 말한다.
- **커넥터로 들어온 시험**은 커넥터의 부서가 고친다(등록자가 없다).
- 이관 계정 하나로 올린 자료는 그 계정이 등록자다 — 실제 담당자에게 재료째 넘긴다.
- **정의와 장비도 같다**(3단계) — 시험 종류 · 장비 파일 정의 · 레시피 · 해석용 물성 정의 ·
  보유 장비. **누구나 만들고** 등록자 · 편집을 받은 부서 · 자료 관리자가 고친다. 전에는 부서
  관리자(장비는 「어느 부서든 관리자면」)였다. 2026-09-24 전에 있던 정의는 그 등록 부서에,
  장비는 그 장비를 든 조직에 편집을 줘 두었다. 기본 정의(씨앗)는 등록자가 없어 자료 관리자가
  고친다.
- **부서 관리자가 하는 일은 셋이다** — 부서 멤버, 장비 커넥터와 수신함, 측정 의뢰 알림
  (변경 이력도 본다). 새 기준정보 값(Grade·제조사 등)과 핸드북 승인은 **자료 관리자**의
  일로 옮겼다. 「새 등급을 못 만든다」 를 받으면 자료 관리자에게 보낸다.
- **지운 것은 지운 사람이 되살린다.** 사이드바 「휴지통」 에 내가 되살릴 수 있는 것만
  뜬다(내가 등록했거나 편집을 받은 부서의 것). 함께 돌아올 것 중 남의 자료가 있으면 그
  사람이 되살린다. **영구 삭제는 시스템 관리자만**(관리 › 서버 › 휴지통).
- **상단의 부서 선택기는 없다.** 그것이 정하던 것이 없어서 걷었다 — 홈 · 워크벤치는 전사
  한 주소, 부서로 좁힌 시험 목록은 `/tests?workspace=<부서>`, 부서 멤버는 그 화면 안에서
  부서를 고른다. 옛 주소(`/w/<부서>/…`)는 새 주소로 넘어간다. 내 소속과 역할은 계정
  메뉴(오른쪽 위 이름)에 적힌다.
- **의뢰·커넥터·워크벤치도 전원이 본다.** 움직이는 것은 그대로다 — 의뢰는 낸 쪽 · 받는
  쪽(작성 중인 것은 낸 사람만 본다), 수신함은 그 커넥터 부서의 관리자, 워크벤치 작업은
  그 부서 사람과 시작한 사람. 남의 것은 읽기로 열린다.

## 데이터를 다른 플랫폼에 넘길 때 — 백업을 주지 않는다

「서버 → 데이터 내보내기」(시스템 관리자). 고르는 것은 셋 — 곡선 포함 · 문헌 포함 · 메모.
큐에 들어가고, 다 되면 그 화면 목록에 줄 수와 크기가 뜬다. 파일은 **서버 폴더에서
사람이 가져간다**(`EXPORT_DIR`, 안 적으면 filestore 옆의 `exports`).

**백업을 건네지 않는다.** 셋 다 실무에서 문제가 된다:

- **`.env` 가 들어 있다** — JWT 비밀키. 그것만으로 토큰을 위조할 수 있다.
- **곡선이 DB 에 없다** — `curves` 는 경로·해시만 들고 점은 파일스토어의 Parquet 다.
  덤프만 주면 「시험이 있었다는 기록」만 간다.
- **읽을 수가 없다** — pg_dump 커스텀 포맷은 복원해야 보인다.

내보내기는 CSV 17장 + 곡선 CSV + README + manifest 로 나가고, **숫자는 전부 SI** 다
(열 이름에 단위가 박혀 있다 — 화면의 mm·MPa·tonne/mm³ 와 다르다). 계정·토큰·감사·
접근 로그·등록자는 **안 나간다.**

넘기기 전에 사람이 확인할 것 둘:

- **부서 가시성이 이 파일 안에는 없다.** 전 부서로 뽑으면 남의 부서 재료가 그대로
  간다 — 그쪽 동의를 받았는지 확인한다. 누가 언제 무엇을 뽑았는지는 감사에 남는다.
- **문헌 값은 우리 것이 아니다.** 대부분 MaterialTwin 이관본이고 원본은 논문·핸드북
  이다. 산출물의 README 가 출처별 라이선스를 세어 적는다 — 실측(2026-09-22)으로 출처
  3,013건 중 라이선스가 적힌 것은 2건뿐이었다. **빈칸은 「모른다」 이지 「자유」 가
  아니다.** 사내 값만 주려면 문헌을 끄고 뽑는다.

명령줄로도 같은 것을 뽑는다 — `python scripts/export_dataset.py --out D:\export`.
화면과 **같은 함수**를 부른다.

## 배포 뒤 — 안내 공지를 발행한다

새 기능 안내는 배포 패키지에 실려 온다(`backend/seeds/notices/*.md`). 배포 스크립트가
그것을 **공지 초안**으로 넣고, 관리자만 본다. 배포한 사람이 첫 독자다 — 공지 화면에서
읽고, 이 서버에 안 맞는 말이 있으면 고치고, 발행한다. 중요한 것만 팝업을 켠다.

같은 안내는 두 번 들어오지 않고, 운영에서 고친 글은 다음 배포가 덮지 않는다. 손으로
돌리려면:

```powershell
cd C:\Server\MatNexus\backend
.\.venv\Scripts\python.exe scripts\import_notices.py --check   # 무엇이 들어올지
.\.venv\Scripts\python.exe scripts\import_notices.py           # 초안으로 넣기
```

개발자가 할 일: 릴리스마다 `backend/seeds/notices/<날짜>-<제목>.md` 를 하나 쓴다.
첫 줄이 `# 제목`, 나머지가 본문(마크다운 아님 — 줄바꿈과 「-」 목록만).

## MCP 서버 — AI 연결 (선택)

**앱과 별개로 돈다.** 안 띄워도 화면·API·워커는 멀쩡하고, 띄우면 AI 가 재료·
문헌 물성·측정법·시험을 직접 묻고 덱까지 만든다(`run_mcp.ps1`, 8012).

세 가지를 기억한다.

1. **권한은 그 사람의 것이다.** 서버는 받은 개인 토큰(PAT)을 백엔드로 넘기기만
   하고, 무엇을 볼 수 있는지는 지금 있는 권한 코드가 정한다 — **만능 토큰이
   없다.** 사람마다 자기 토큰을 발급받아 등록한다.
2. **토큰은 클라이언트 설정 파일에 평문으로 남는다.** MCP 클라이언트 공통
   성질이라 막을 수 없다 — 그래서 **수명을 짧게 주고**(발급 화면에서 일수를
   정한다), 사람이 바뀌거나 PC 를 옮기면 **그 자리에서 폐기**한다(내 계정 →
   토큰 → 삭제).
3. **밖에 열 때는 허용 Host 를 준다.** `MATNEXUS_MCP_ALLOWED_HOSTS` 없이
   `MATNEXUS_MCP_HOST` 만 바꾸면 서버가 기동을 거절한다.

안내 문구(단위 규약·값의 무게·tier·합성 표지)는 `mcp_server\guide\GUIDE.md` 에
있고 **서버가 매 호출 다시 읽는다** — 고치면 재시작 없이 반영된다.

## 의미 검색 엔진 — 임베딩 (선택)

**앱과 별개로 돈다.** 안 올려도 검색은 멀쩡하다 — 「일치·포함·비슷」 은 DB 만으로
돌고, 엔진이 있으면 거기에 **뜻이 비슷한 것**이 얹힌다. 그래서 엔진이 죽어도
검색이 죽지 않는다(그 반대로 만들면 안 된다).

명령 하나로 설치·서비스 등록·모델 내려받기까지 끝난다:

**무엇이 색인되나** — 핸드북 절(산문) · 사내 재료(분류·별칭·용도·메모를 말로 엮어) · 문헌
재료 설명 · **물성 정의**(이름·기호·키·별칭·설명). 이름·번호는 일부러 안 넣는다 — 그건
트라이그램의 일이고, 겹치면 같은 것을 두 번 맞히고 순위만 흔들린다. 물성 정의가 든 덕에
「비캣 연화온도」 처럼 사전에 없는 말이 **별칭 후보 큐의 「이것 아닐까」** 로 이어진다
(기준정보 › 해소 못 한 물성 이름).

**켜졌는지는 화면이 말한다** — 서버 › 서버 정보의 「의미 검색」(2026-09-18). 조각 수·모델·
차원과, 꺼져 있으면 **왜 그런지와 할 일**(설정이 off · pgvector 없음 · 아직 색인 안 함)이
한 줄로 뜬다. 「지금 색인」 을 누르면 워커가 뒤에서 전부 다시 색인한다(실측: 조각 809개에
39초). 모델을 바꿔 차원이 달라지면 그 색인이 표를 다시 만들고 새로 채운다 — 원문은 그대로라
잃는 것은 시간뿐이다. 평소에는 하루 한 번 저절로 돈다(`search.reindex`).

```powershell
cd scripts\deploy
.\setup_ollama.ps1              # 설치 + 시작 시 자동 실행 + bge-m3
.\setup_ollama.ps1 -CheckOnly   # 아무것도 안 바꾸고 상태만
.\setup_ollama.ps1 -TakeOver    # 사람이 깐 트레이 앱을 SYSTEM 작업으로 넘긴다
```

네 가지를 기억한다.

1. **트레이 앱이 아니라 작업으로 돈다.** Ollama 의 윈도우 설치본은 로그인한
   사람의 트레이에 뜨는데, 서버는 아무도 로그인해 있지 않다 — 그래서 이 스크립트가
   `MatNexus-Ollama` 작업을 만들어 **시작 시 SYSTEM 으로** 띄운다. 안 그러면
   재부팅한 다음 날 「의미 검색만 안 되네」 로 드러난다.
   - **이미 11434 가 응답하면 작업을 만들지 않는다.** 같은 서버에서 TestScope 가
     올린 엔진이든 사람의 트레이 앱이든, 두 작업이 한 포트를 두고 다투면 뒤에 뜬
     쪽이 조용히 죽는다. `-CheckOnly` 로 보고, 도는 것이 **트레이 앱**이면
     `-TakeOver` 를 준다 — 트레이 인스턴스를 내리고, 로그인 시 자동 실행 항목을
     지우고, 그 사람 프로필에 받아 둔 모델을 전역 자리로 복사한 뒤 작업으로 띄운다
     (TestScope 의 같은 옵션을 옮겨 왔다, 2026-09-16).
2. **모델 자리를 기계 전역으로 못 박는다**(`OLLAMA_MODELS`,
   기본 `C:\ProgramData\MatNexus\ollama-models`). 서비스는 SYSTEM 으로 돌고 사람은
   자기 계정으로 `ollama pull` 을 돌리므로, 안 박아 두면 **받은 모델을 서비스가
   못 본다.**
3. **pgvector 도 함께 필요하다.** 벡터를 DB 에 넣고 빠르게 찾는 확장인데, 윈도우
   PostgreSQL 에는 안 들어 있다. 개발 PC 에서 한 번 빌드하고 서버는 복사만 한다:

   ```powershell
   .\build_pgvector.ps1                                   # 개발 PC, 한 번
   .\install_pgvector.ps1 -FromDir <산출물 폴더>           # 서버, 관리자 권한
   ```

   **DLL 은 PostgreSQL 메이저 판에 묶인다**(17용은 16에서 안 뜬다). 설치 스크립트가
   판을 대조해 먼저 막는다. 표는 다음 배포가 저절로 만든다 — `deploy.ps1` 이
   `ensure_semantic_schema.py` 를 매번 부르고, 확장이 없으면 조용히 넘어간다.

   **백업에 영향이 있다.** 확장을 켠 DB 의 덤프에는 `CREATE EXTENSION vector` 가
   들어가므로, **복원 대상 기계에도 pgvector 가 먼저 설치돼 있어야** 한다. 새 서버로
   옮길 때 순서는 「pgvector 설치 → 복원」이다.

4. **차원이 설정과 맞아야 한다.** 스크립트가 마지막에 임베딩을 한 번 재서 차원을
   찍어 준다 — 그 숫자를 `.env` 의 `EMBEDDING_DIM` 에 적는다. 모델을 바꾸면 차원이
   바뀌고, **이미 만들어 둔 벡터는 전부 다시 만들어야 한다.**
