# 물성 데이터 관리와 AI 기반 평가 시스템 구축 논의 — 정리

- 일시: 2026-08-28 (녹취 약 36분)
- 성격: 내부 논의 (CA 그룹 관점). 음성 인식 원문이라 조직명·용어 일부는 추정 — 맨 아래 「용어」 참고.

---

## 1. 논의의 출발점

- 요청서를 쓰기로 했고, 그 전에 **역할(R&R)부터 정리**해야 한다는 데서 시작.
- 기본 그림:
  - 물성을 **전사에서 관리하는 시스템**을 만드는 것은 **GTR** 역할에 가깝다.
  - 그것을 **지식화해서 활용**하게 만드는 것도 GTR 이 해 줬으면 한다.
  - 시험을 만들고·수행하고·데이터를 넣는 것은 **신뢰성 그룹**이 맞다.
- 바로 반문이 나옴: *"시험 규격을 만드는 게 GTR 역할이 맞나? CS 센터가 아니고?"*
  - 시뮬레이션 관련 물성은 CA 쪽이 맞지만, **전사 물성 관리는 CS 환경센터**가 하겠다고 할 수 있다.
  - → **내부적으로 다시 논의해야 할 포인트**로 남김.
- 오히려 **시뮬레이션과 연동하는 방법을 찾는 것** — 예: 역공학으로 물성을 뽑아 주는 것 — 이 GTR 이 할 일일 수 있고, 그런 아이템을 발굴하는 것도 GTR 몫.

- 신뢰성 그룹은 「물성을 구축해 주면 LLM 으로 시험법 만들 때 활용하겠다」 정도.

## 3. 품질센터(신뢰성 그룹)의 입장 — 애매한 부분

- 시험법 만드는 건 하고 싶고, 물성이 중요하다는 것은 인지.
- 그러나 **물성 DB 를 자기들이 만들 생각은 없다.** DB 관리 주체가 되고 싶지 않음.
- 다만 **해야 할 시험이 있으면 해 준다** — 지원은 가능.
- 규격·인증 쪽도 「그것도 된다」.
- 승인원은 PDF 파일 업로드 형태로만 있고, **AI 가 이해할 수 있는 형태의 데이터는 없다.**

### COO 요청의 스코프

- 들은 바로는: 품질센터가 「우리가 이거 하겠다」 → COO 가 「그런 부분을 **시뮬레이션으로, 신소재 등을 검토할 수 있는 프로세스**를 만들어서 해라」.
- 품질센터는 시험만으로는 모르는 것이 있어 **시뮬레이션을 더 활용**하고 싶어 함.
- 품질 쪽 시뮬레이션 역량은 조금씩 늘리는 중이나 아직 부족 → **CA 그룹이 가이드해 주길** 항상 바람.
- 개발 도중 평가가 아니라, 시험을 진행·인정하는 프로세스를 **새로 만들고 싶고, 만드는 시점부터 CA 와 연결**되길 원함.

## 4. 「AI 가 이해할 수 있는 데이터」의 기준

- 레포트 아카이브를 기준으로 뭐가 더 있어야 하나 → **맥락(컨텍스트)을 이해할 수 있어야 한다.**
- 맥락 이해 = **그래프 DB** 를 만들어야 한다는 얘기.
- 그래프 DB = **기준정보를 세워야 한다**는 얘기. 기준정보로 상호 연결 관계를 만든다.
- 따라서 **어떤 데이터를 먼저 모을지 스코프를 정해야 한다.**

### 가야 할 방향

- 지금 PDF 로 저장하는 시험 규격들을 **늘리고**, 그것을 **시뮬레이션 평가와 병행해서 검증**하는 방향.
- 기존 규격 양식과 그 **분류 체계를 참고**해서, 거기에 CA 를 붙여 함께 관리·검색할 수 있는 DB 로.
- **그걸 만들 사람이 필요하다.**
- 열린 질문: GTR 이 플랫폼과 전체 데이터 구조를 만드는 것은 알겠는데, **시험 규격 자체의 DB 까지 범위에 넣어야 하나?** CS 센터에 물성 DB 가 있다고 하니 그쪽이 할 수도.
  - CA 물성은 이쪽에서 지키되, 부품 표준·인증·밀시트 동일성 같은 **모든 물성의 거버넌스는 CS 에 있다.**
  - 그렇다면 **장기적으로는 CS 도 끌어들여서 전부 해야 맞다.**

## 5. 인프라 — 서버·DB 는 어디에

- AX 팀의 현재 과제는 **AI-ready 데이터를 어떻게 만들지에 대한 POC.**
- 서버는 **아마 BDC** 로 들어갈 것. BDC 와 AX 가 협의 중이고, 어제 회의가 그것.
  - DB 를 BDC 에 올리는 것은 된다.
  - **GPU 계산 서버**까지 지원되는지는 모름.
  - BDC 서버는 **외부 인터넷 차단**될 듯 → 「풀 수 있다」고 회의에서 들었다고 함. 확인 필요.
  - 인터넷 차단은 **개인정보가 있는 DB 에 한해서** → 개인정보를 넣으면 안 된다. **개인정보의 범위**는 BDC 에 확인.
- 인터넷 없어도 운영 자체는 문제 없음. **설치의 문제** — 오프라인 설치가 되도록 만들고는 있으나 의존성 때문에 귀찮아질 수 있음.
- BDC 에 넣으면 **BDC 가 원하는 양식**에 맞춰야 할 수도 → 「아마 그러지는 않을 것」. 귀찮으면 **AX 팀이 투자하는 GPU 자원으로 MX 내부에 서버**를 만들 수도. **자유도**가 중요하게 얘기되고 있으니 어제 회의에서 강조됐어야.
- 사내 시스템 간 연계는 **API 표준**을 따라야 함.

### PLM-MCP POC

- 표준화를 위해 이번 POC 에서 **PLM 을 BDC 에 연결하고, 전체 클로드에 MCP 를 오픈**하는 것을 함. 오래 갈 과제.
- 주관은 **MX AX 팀**. AX 팀은 지원 조직이라 스스로 못 하고, **스마트폰 개발 그룹** 사람들을 모아서 하고 있음.
- 전문성이 없어 **BDC 와 직결(상주)** 시킬 것 같음 — 전문가를 붙여 놓고 하려는 이유. BDC 에서 사람이 올 수도, 구성 가이드가 올 수도.
- 우리 과제(물성)는 **PLM 을 하는 게 아니다** — 우리가 담당하는 **HW 엑스포 포탈** 안의 것과 전사 물성을 연결하는 것. 3rd-party 시스템 연동이 아니므로 그쪽처럼 무겁지 않음.
- 배경: 원래 HW 담당이 화자에게 PLM 연동을 시켰었음. 이후 AX 팀에 넘어감.
- 사내 시스템 API 연계는 **보안에서 공식적으로 안 된다**고 했었음. AX 팀이 윗선을 통해 강제로 풀고 있음 — 전사 조직·지원 쪽이라 파워가 세서 BDC 가 끌려옴.

## 6. 데이터 거버넌스와 접근 권한

- 「거버넌스를 지키면서 저장」= **BDC 에 다 모아 놓고 접근 권한을 BDC 에서 관리.**
- 예: 클로드로 과제별 비교를 물으면 데이터를 가져오는데, **전략과제 서약 안 한 사람이 가져가면 안 됨** → 사람별 권한 하이어라키 필요. BDC 는 이걸 이미 만들어 봤음(PLM 과 비슷하게).
- 그러면 **우리가 접근권한을 만들 필요가 없다.** 우리는:
  - 모든 시스템을 **SSO 연동**으로만 바꾸고,
  - DB 는 **그쪽에 있는 것을 조회**하는 구조로.
  - 지금처럼 PostgreSQL 을 따로 두는 게 아니라, **포맷을 알려 주고 우리 테이블을 그쪽 DB 에 올린다.**
  - **아직 정해진 것은 없고, 다들 그렇게 생각하고 있을 뿐.**
- 물성 뿐 아니라 **레포트 아카이브도** 같이 가야 한다는 얘기.

### 중간 정리

- 로그인 인증은 거의 연동으로.
- DB 는 그쪽으로 이동할 수도.
- 개별 서버가 아니라 **전부 BDC 로 옮겨** 그쪽에서 서버 운영.
- 표준·양식을 그쪽에서 제안해 올 수도 — 정해지지 않음.
- PLM 을 통해 무엇이 필요한지 정해질 것. 우리는 **AX 로 할 수 있는 아이템을 찾아 만들기만** 하면 됨.

### 열린 문제 — 복사 저장과 온톨로지

- 각 시스템(PLM 등)에서 데이터를 가져와 온톨로지를 구성할 텐데, **그 정보를 복사해서 우리 테이블에 저장해도 되는지** 확실한가?
  - 예전에 VD 대시(?)를 통해 받아온 걸 보면 안 되는 건 아닌 듯. 확인 필요.
  - 최근 SPDM API 로 데이터를 끌어와 저장한 것처럼, PLM 데이터도 그렇게 해도 되는가.
- **전략과제**는 접근 제한이 있음. 레포트 아카이브에 전략과제 정보가 있으면, 로그인 시점부터 일반/전략과제 사용자를 나눠야 하는 것 아닌가?
  - BDC 답: **BDC 에서 조회하는 시점에 끊는다.**
  - 그렇다면 조회한 데이터를 **긁어 와서 저장하면 안 된다**는 얘기 — 여기서 누구나 볼 수 있으니.
  - 물성 DB 는 **다른 사업부도 쓰는 전사 시스템**이 될 것. 전략과제는 확실히 차단해야.
- 선택지:
  1. 시스템 권한 제어만으로 되는가
  2. 안 되면 로그인한 사람에 따라 **DB 접근 자체를 다르게**
  3. 그것도 안 되면 저장하지 않고 **그때그때 호출** → **그러면 온톨로지가 구성이 안 된다.**
- 결론: **아직 모른다.** 해 보지 않으면 몰라서 **니즈가 높은 PLM 으로 해 보면서 결정**하겠다는 것.
- 만약 과제 정보를 레포트 아카이브·물성 DB 에 **저장하면 안 된다**면:
  - 로그인 인증도, 권한 제어도 이쪽에서 만들면 안 되고,
  - 과제를 특정할 수 없는 **키**만 받아 데이터에 연결해 두고, 그쪽에서 조회할 때 이쪽을 찾아 들어가게 하며, 이쪽 DB 를 다 그쪽에 저장하는 식으로 갈 수밖에 없음. **가능할지 쉽지 않다.**

### 컴플라이언스 — 전략과제보다 더 큰 문제

- 전략과제는 **사용자 풀을 제한하고 서약**하게 하면 해결 가능.
- 진짜 문제는 **업체에서 받은 데이터의 컴플라이언스.** 이건 해결이 더 안 되므로 **그런 데이터는 안 올라가게** 해야.
- 레포트 아카이브는 큰 상관 없음(보고서에 업체 분석을 넣는 경우만 조금 문제).
- **물성 DB 는 문제** — 업체가 측정한 물성은 못 올린다.
  - → **물성 측정을 내부에서 해야 한다.** 신뢰성 그룹의 역할이 크게 강조됨.
  - → 신뢰성 그룹이 **측정을 직접 하는 체계를 구축·관리**하고, **물성 DB 에 데이터를 만들고 등록하는 역할**이 되어야.
- 온톨로지·다음 스텝이 가능하려면 **컴플라이언스 문제를 없앤 상태**를 먼저 만들어야 함. 이것을 검토해야 한다는 것을 **ETF(?)로 만들든 어떻게든 윗사람들에게 얘기**해야. (녹음해 두고 관찰하자는 말도.)

## 7. 신뢰성 그룹이 실제로 하려는 것

- 윗선에 보고한 계획: **시장 리스크에 더 정합되는 신뢰성 시험을 AI 로 발굴**하겠다.
  - 시장 정보는 HWX 의 시그널 포지처럼 받아오고, 스펙 정보는 다른 식으로.
  - 표준 시험 정보와 소재 물성 특징을 이용해 **시험법을 유도**해 보고 싶다.
  - 「부품군별 시장 불량 비교 → 물성 차이와 연결」까지 깊게 생각하지는 않았을 것.
- 즉 역할은 **시험법을 만들어 적용** = **신뢰성 시험을 늘리겠다**, 시장 상황에 더 맞는 시험을 발굴하겠다는 것이 최종 목적.
- 그 계획서·보고서를 **CA 쪽으로 보내 주기로** 함. 무슨 플랜으로 기획한 건지 잘 안 잡힘.
- CA 그룹에 요구한 것: 시험 평가 경험이 많으니 **어떻게 평가하면 좋을지**, 그리고 **시뮬레이션으로 병렬 분석**할 수 있게.

### CA 그룹이 제시한 방향

- 여러 층이 들어간 소재는 **개별 물성을 잴 수 없어** 시험을 하는 것이고, 시뮬레이션으로 재현이 안 된다 → **역공학**으로 찾아야.
- 방향:
  1. **간단한 표준 시험 몇 가지**를 정하고,
  2. **역공학**으로 물성화해서 시뮬레이션하고,
  3. **시뮬레이션 자체도 규격**으로, **시험도 규격**으로 만든다.

### 예시 — 결로

- 신뢰성 시험의 결로 페일 기준에 **시장 근거가 없는데**, 시장에서는 결로 문제가 난다.
- 기준을 역학적으로 의미 있게 정하고 원인도 찾고 싶다.
- 필요한 것:
  - 다른 분야 시험 규격을 여러 개 찾아 **AI 로 우리에 맞는 시험 규격**을 만드는 것,
  - 시뮬레이션이 안 되니 **시뮬레이션 방법을 유도**하는 것,
  - 결로 관련 물성이 없으니 **결로 물성 측정 시험법**을 만드는 것,
  - 만든 시험법으로 **새 소재가 나올 때마다 누군가 시험해서 데이터를 채우는 것.**
- CA 입장: 결로 시뮬레이션 방법을 새로 발굴하고 물성을 찾는 것까지는 하되, **소재마다 업데이트하는 것은 신뢰성이든 GTR 이든 외부**에서 해 줬으면.
- GTR 이 잘하는 것: **새 시험용 지그를 만들고 그 지그로 시험해 비교**하는 것. 신뢰성 그룹은 그런 경험이 거의 없으므로 이 역할을 GTR 에 맡기고 싶음.

## 8. 최종 역할 정리 (합의)

| 역할 | 누가 |
| --- | --- |
| 규격 안에서 시험을 만들고 **운영**하는 것 | **신뢰성 그룹** |
| 시험을 만들기 위한 제반 조건 — **지그 제작, 비교 규칙** 등 | **GTR** |
| 시뮬레이션 **역공학**으로 **판별 기준·시뮬레이션 기준**을 만드는 것 | **CA 그룹** |
| **플랫폼**을 만들어 **데이터 전체를 관리**하는 것 | **GTR** + CA 가 개발한 플랫폼 위에서 |

## 후속 정리 (2026-09-05, 킥오프 준비)

회의 뒤 확정·보정된 것. 회의 내용 자체는 위 그대로 둔다.

### 과제

- **과제명:** AX 툴 기반 평가 체계 및 CAE 품질 협업 모델 구축 (물성 해석 연계 신뢰성 예측 고도화)
- **추진 방향:** ① 실물 시험–해석 상호 검증 AX 시스템 ② 불필요한 시험·해석 최소화 — 승인 기간 단축·판정 신뢰도 ③ 사업부 간 물성 DB 공유·활용
- **배경:** 각 사업부 복합 물성 최대 활용·미보유 물성 AX 도출 / 해석 기반 리스크 도출 → 제한된 시료 배분 / 시험 문제 발생 시 메커니즘 도출 툴
- **지원 범위:** 물성 측정(온습도·DMA·피로)·평가 데이터 등록 포맷 표준화, AX 기반 공유 연결 체계
- CAE 그룹은 디지털트윈사무국과 물성 협업, 신뢰성 그룹과 복합 검증 강화 협업을 검토 중이었다.

### 용어 — 「복합 물성」

회의에서 「물성」 이라 부른 것은 재료 본연의 성질이 아니다. 여러 층·재료가 결합된
**부품 단품**에서 층별 물성을 따로 잴 수 없어 복합체를 시험하고 역공학으로 뽑는
값, 층 하나가 바뀌었을 때의 거동 차이, 시장 불량을 재현하는 부품 시험의 데이터 —
과제는 이것을 **복합 물성**이라 부른다. 재료 물성(규격·인증·밀시트)은 CS 환경센터
거버넌스이고, 과제 범위는 복합 물성이다. **회의의 「전사 물성 관리 주체 — GTR 인가
CS 인가」 는 둘을 하나로 봐서 생긴 질문이었고, 나누면 사라진다.**

### 역할 (확정)

| 조직 | 역할 |
| --- | --- |
| GTR 디지털트윈사무국 | 플랫폼 개발 |
| GTR 개발디지털트윈 | 지그 제작, 비교 규칙 등 시험 조건을 만들기 위한 제반 조건 제공 |
| MX CAE 그룹 | 역공학으로 판별 기준·시뮬레이션 기준 정립 |
| MX 신뢰성 그룹 | 규격 안에서 시험을 만들고 운영 |

회의의 8절 정리와 같되, 「플랫폼」 이 GTR 안에서 **디지털트윈사무국**으로, 「지그·
비교 규칙」 이 **개발디지털트윈**으로 나뉜다.

### 플랫폼 요구사항 — 기존 시험 데이터 체계와의 정렬

플랫폼을 만드는 디지털트윈사무국은 MX 의 시험 현장·데이터를 직접 못 본다. 부품
시험이 지금 어떤 항목으로 어디에 어떤 규칙으로 관리되는지 모르면 DB 를 짜도
현장이 안 쓴다. 재현 시험을 받아 역공학·시뮬레이션까지 가져가려면 **기존 시험
데이터 체계 → 재현 시험 → 역공학 → 방법론** 네 사슬이 한 줄로 정렬되어야 한다.

그래서 **무엇을 MX 에 물어야 하는지**를 먼저 목록으로 두었다 — 6개 영역 35항목
(신뢰성 21 · CAE 5 · 개발DT 3 · CS/AX/BDC 6, 필수 24), 각각 「왜 필요한가 → DB 의 어느
자리」 와 「받는 형태」 를 붙여서. 1차 묶음(A1·A2·A4·A7·A11·B1·B3)은 킥오프 뒤
1주 안에.
