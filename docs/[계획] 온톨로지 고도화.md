# [계획] 온톨로지 고도화 — 무엇을 빌리고, 무엇을 더하나

2026-09-16. 세 갈래를 대 보고 쓴 것이다 — **MatNexus 의 지금**([[계획] 온톨로지](%5B계획%5D%20온톨로지.md),
ADR 0028), **StandardPlatform(SP, WSL `~/projects/StandardPlatform`)** 의 메타모델과
정제 파이프라인, 그리고 「그룹의 모든 자료를 온톨로지화한다」 는 물음에 대한 조언
(Core → Domain → Instance → Evidence → Document 의 5층, 관계 20~40개, 그래프+RAG 두 축).

> 한 줄 결론: **MatNexus 는 도메인 층이 이미 진하고 근거 사슬이 반쯤 있다. 빠진 것은
> 「문서를 근거로 붙이는 자리」 와 「업무 세계의 긴 꼬리(과제·이슈·결정·부품)를 코드 없이
> 담는 자리」 다.** 앞은 MatNexus 안에서 만들고, 뒤는 SP 의 메타모델을 **빌리되 표를
> 복제하지 않는다** — SP 의 `system` 타입이 정확히 그 자리다.

## 0. 조언의 5층에 두 플랫폼을 대 보면

| 층 | 조언이 말하는 것 | MatNexus (지금) | StandardPlatform (지금) |
| --- | --- | --- | --- |
| **Core** | Object·Activity·Person·Org·Property·Document·Decision | 코드에 박힌 표 60개 + 관계 레지스트리 17마디·19관계(`shared/relations.py`). 사람·부서·감사 FK 는 일부러 뺌 | `work-core.json`(업무·문서·사람·기관·설비·SW·기술분야·부서, 관계 10) + `plm-core.json`(프로젝트·과제·개발모델·시험주체). **허브가 내려주고 쌍둥이는 확장만** |
| **Domain** | Material/Test/CAE/Requirement/Failure… | **가장 진하다** — 재료→시료→시편→시험→처리→카드→채택, 물성 이름 사전 271+별칭, 단위 환산 값 검색, 조건 정규화, 장비·측정능력, 계산식(ADR 0030), 카탈로그 문헌값 42k | 타입·속성·관계를 **데이터로 정의**(`object_types`·`property_defs`·`relation_types`). 단위는 라벨 문자열, 값 검색은 문자열 비교만 |
| **Instance** | 실제 객체·관계 | 표마다 제 형태·제 규칙(유일제약·리비전·권한·소프트삭제) | `objects`(JSONB)·`object_relations`·`object_links`. 별칭·합치기·이력·되돌리기·품질·롤업 |
| **Evidence** | 값 → 시험 → 조건 → 파일 → 페이지 → 추출시각 | **측정값은 있다**(파일 해시→시험→처리결과→카드 블록→채택, 문헌값→출처). **문서 위치(페이지·셀)는 없다.** 선언 물성의 출처는 `source_ref` 문자열 | 관계에 `evidence_note`(글 한 줄)뿐. 파이프라인의 `_source`(파일·시트·행·페이지)는 **플랫폼에 안 올라간다**(계획서 ⑭ 「출처를 담을 자리」 가 열린 질문) |
| **Document** | 원문 보관 + RAG | `search_chunks`(bge-m3, kind+entity_id 로 마디에 매달림 — 재료·카탈로그·가이드) · 파일스토어(장비 원본) | 첨부 모듈(`owner_table/owner_id/owner_field`), 의미 검색 없음 |
| **거버넌스** | AI 후보 → 사람 승인, 동의어 사전 | 기준정보 별칭·병합·사용수·어긋남 검사. **후보 큐는 없다** | 정의 가져오기 계획+경고+스냅샷, 코드표 승격, 허브 관리 정의 잠금, 묶음 미리보기 지문 |
| **파이프라인** | 파싱(결정적) → 추출(AI) → 매핑 → 검증 → 적재 | 원천별 이관기(`mt_import`·카탈로그) — 문서용은 없다 | `sp_profile`(조사) → `sp_work`(작업폴더) → `sp_table`(표를 규칙으로) → `validate` → `preview`(지문) → `apply`. 로컬 MCP 14도구, 골든 셋은 「다음」 |
| **AI 접점** | 8개쯤의 기본 도구 + 시맨틱 층 | MCP 57도구, `get_ontology`·`related`·`find_path`·`resolve_property`·`find_by_property`·`search_all`, 종류별 `entry`·물음별 `recipes`(37→16번 실측) | MCP 18도구, **타입마다 도구를 안 만든다** — 동적인 것은 스키마 |

읽히는 것 셋:

1. **두 플랫폼 다 Evidence 층이 비어 있다.** MatNexus 는 측정값에 한해 사슬이 있고,
   SP 는 글 한 줄이다. 조언이 「가장 많이 빠뜨린다」 고 한 자리가 맞다. 그리고 MatNexus
   가 먼저 만들 수 있다 — 측정값 사슬이 이미 근거 모양이라 **그 모양을 문서로 넓히면** 된다.
2. **긴 꼬리는 MatNexus 표로 만들면 안 된다.** 과제·이슈·결정·요구사항·부품은 그룹마다
   다르고, 표로 만들면 그룹마다 코드를 고친다. SP 가 이것을 데이터로 푸는 데 이미 5단계를
   끝냈다(2026-09-11~12). 다시 만들지 않는다.
3. **MatNexus 의 마디는 SP 의 `system` 타입이다.** SP 는 부서·계정을 `objects` 에 복제하지
   않고 원 표를 투영한다(`SystemSource`). 재료·시험·카드도 같은 자리에 선다 — 행을 복제하지
   않고 **선(`object_links`)만** SP 쪽에 둔다. 두 플랫폼 사이의 경계가 여기서 정해진다.

## 2. 더할 것 — MatNexus 안에서

### A. 근거(Evidence) 층 ★ 이번 고도화의 핵심

조언의 그림을 MatNexus 말로 옮기면:

    SECC (material)
      ─ has_card ─▶ 카드 · 블록 「인장」                   ← 있다
      ─ adopted ──▶ 처리 결과 #… (채택)                    ← 있다 (관계 레지스트리)
      ─ processed_from ─▶ 시험 #132 ─ tested ─▶ 시편        ← 있다
      ─ 파일 해시 → filestore                              ← 있다
    항복강도 = 280 MPa @ 23 °C                              ← 값·조건 있다
      ─ evidence ─▶ 「인장시험결과_2025.xlsx」 Sheet2/R13     ← **없다**
      ─ extracted_by/at · confidence                        ← **없다**
    선언 물성(데이터시트에서 옮겨 적음) → source_ref "포스코 카탈로그 2024"   ← 글자뿐

만들 것:

| 무엇 | 모양 |
| --- | --- |
| `documents` | 파일스토어의 문서(PDF·xlsx·pptx·docx·md). `sha256`·`kind`(datasheet·report·paper·minutes·spec)·제목·부서 소유·업로드자. **장비 원본과 같은 저장소, 다른 표** — 장비 파일은 시험에 매달리고 문서는 여러 마디에 매달린다 |
| `evidence` | `(kind, entity_id)` — 레지스트리의 마디 어디든 — `document_id` · `locator`(JSONB: page / sheet·cell / paragraph / bbox) · `quote`(발췌) · `extractor`(사람·AI 모델·스크립트) · `confidence` · `extracted_at` · `note`. **관계에도 붙는다**: `(kind='edge', edge_id)` |
| 선언 물성·문헌 출처·`same_as`·`adopted` 가 근거를 갖게 | `source_ref` 문자열은 두되, 근거 행이 생기면 그것이 정본. 화면의 값 옆에 「근거 N」 |
| `search_chunks` 에 `locator` | 문서 조각도 페이지·시트를 안다 → 의미 검색이 **곧 근거 후보**가 된다. 조각은 `kind='document'` 로 색인 |
| MCP `get_evidence(kind, id)` · `get_source(document_id, locator)` | 조언 §9 의 도구 둘. `related` 가 찾고 `get_evidence` 가 원본으로 내려간다 |
| 구조 시험 | 레지스트리 마디마다 근거를 붙일 수 있는지, 끊어진 `document_id` 가 없는지(다형 참조라 FK 가 없다 — 기준정보 어긋남 검사와 같은 자리) |

**하지 않을 것**: 문서 본문을 그래프 마디로(조언 §8, [계획] 온톨로지 §1-④ — 실측 데이터는
안 넣는다). 근거는 **마디에 매달린 잎**이지 마디가 아니다.

### B. 계산의 계보 — 근거의 다른 얼굴

ADR 0030 「계산식은 데이터다」 로 식이 이미 행이다. 그런데 **계산된 값이 어느 식과 어느
입력에서 나왔는지**는 관계로 안 잡혀 있다. 관계 둘을 더한다:

    computed_by   카드 블록 값 → 계산식            source=fk/edge (식 실행 기록이 있으면 fk)
    input_of      카드 블록 값 → 계산식 실행         조언의 inputOf/outputOf

「이 값 어디서 왔어」 에 측정이면 시험으로, 계산이면 식과 입력으로, 문헌이면 페이지로
내려간다 — 세 갈래가 **같은 도구(`get_evidence`)** 로 답한다.

### C. 관계 레지스트리 — 19 → 30 안쪽에서 멈춘다

조언 §7(초기 20~40)과 우리 실측(19)이 맞는다. 더할 후보와 판정:

| 후보 | 판정 | 근거 |
| --- | --- | --- |
| `computed_by` · `input_of` | **넣는다** | §B |
| `evidenced_by`(마디→문서) | **관계가 아니라 근거 표**(§A) | 관계로 두면 마디마다 잎이 수십 개 뻗어 그래프가 문서로 뒤덮인다 — 사람·부서 FK 를 뺀 것과 같은 판단 |
| `calibrated`(장비→교정) | 보류 | [§8-①] 장비 6·교정 4 — 자료가 먼저 |
| `ran_with`(결과→레시피) | **넣는다** | 「이 레시피로 돌린 결과들」 을 AI 가 물었다. FK 가 있으니 값이 싸다 |
| `requested_by`(시험→측정 의뢰 항목) | **넣는다** | `test_runs.commission_item_id` 가 생겼다(v1.234). 「이 의뢰에서 나온 값」 이 곧 질문이다 |
| `member_of`(재료→구성체) | 보류 | ADR 0026 은 아직 초안이고 표가 없다. 표가 생기면 `table:` 로 가리키기만 |
| 사람·부서·감사 FK | 계속 뺀다 | — |

`edge` 표(5단계, `entity_edges`)는 **여전히 안 만든다** — 넣는 것 전부 FK 나 연결 표가 있다.
근거 표(§A)가 그 역할의 절반을 대신한다.

### D. 조건을 온톨로지가 안다

값 검색은 이름·단위·범위를 안다. **조건(온도·변형률속도·주파수)** 은 `shared/conditions.py`
가 정규화해 블록에 두지만 질의 도구에는 없다. `find_by_property(..., conditions={"temperature":
{"near": 80, "unit": "degC"}})` — 조언의 `measuredAt → 23 °C` 가 질의 쪽에서도 성립해야
「80 °C 에서의 항복강도」 를 AI 가 찾는다. 조건은 마디가 아니라 **값의 한정자**다.

### E. Core 대응표 — SP 와 같은 말을 쓰기 위해

MatNexus 마디를 SP 코어·조언의 Core 에 대응시켜 **한 장으로** 둔다(`GET /api/ontology` 의
`core_mapping`):

| MatNexus | SP work-core / plm-core | 조언의 Core |
| --- | --- | --- |
| `workspace` | `dept`(system) | Organization |
| `instrument` · `equipment_unit` | `equipment` | Object(설비) |
| `source`(논문·데이터시트) · `guide_document` · **`document`(§A)** | `document` | Document |
| `test_run` · `commission` | `work`(업무) / `plm_task`(과제)에 `about`·`produces` 로 | Activity |
| `material` · `sample` · `specimen` · `property_card` | (SP 에 없음 — **system 타입으로 투영**) | Object·Property·Value |
| `term`(기준정보) | `topic`(기술 분야)·코드표 | Property 어휘 |

이 표가 있어야 SP 쪽에서 「과제 X 가 산출한 문서 → 그 문서가 근거인 물성값 → 그 재료」
를 두 플랫폼을 건너 걸을 수 있다. **관계는 SP 에 저장하고(`object_links`), 물성 세계는
MatNexus 가 답한다.**

### F. 거버넌스 — AI 는 후보를 만들고 사람이 확정한다

| 길 | 지금 | 더할 것 |
| --- | --- | --- |
| 이름 해소 실패(`resolve_property` 빈손) | 아무 데도 안 남는다 | `alias_candidates` 에 쌓고 홈 「남은 일」 에 「해소 못 한 이름 N」 (B4) |
| 문서에서 AI 가 뽑은 값 | 없음 | 묶음(B5)으로 들어와 `status=proposed`. 승인 전엔 검색·카드에 **안 보인다** — 보이면 그 순간 정본이 된다 |
| 관계 종류 추가 | 코드 PR | 그대로 — **관계 종류는 사람이 코드로**(조언 §5 「Core 는 거의 수동」). 후보는 규약 문서에 「제안됨」 절로 |
| 근거 없는 값 | 조용히 있다 | 품질 보고(B3)에 「근거 없는 선언 물성 N」. 막지는 않는다 — 막으면 사람이 가짜 근거를 적는다 |

### G. 평가 — 「AI 가 찾나」 를 숫자로

[§8-③] 그대로, 이번엔 먼저 한다. 물음 세트(조언의 질문 유형별: 순회·조회·값·근거·
문서) + 도구 자취 채점(호출 수·지도 봤나·빈손 호출·기대 사실 포함). **골든 셋**(SP 계획 ④)
은 여기서는 「물음 30개 + 답에 반드시 있어야 할 것」 이다. CI 에는 안 넣고 릴리스 전 추세로.

### H. MCP — 도구 수를 줄이지 말고 **들머리를 좁힌다**

57도구는 도메인이 진한 값이지 잘못이 아니다. 다만 조언 §9 와 SP 의 실측(도구가 길수록
엉뚱한 것을 고른다)을 받아, **온톨로지 도구 8개를 「먼저 볼 것」 으로 가이드 첫 줄에**:

    get_ontology · search_all · resolve_property · find_by_property
    related · find_path · get_evidence · get_source

나머지 49개는 그 아래 층이다(레시피가 가리킨다). 도구를 합치는 것은 평가(§G)가 「같은
물음에 호출 수가 준다」 를 보인 뒤에.

## 4. 갈림길 — 사용자가 정할 것

1. **하나로 갈까, 둘로 갈까.** 이 계획은 「MatNexus = 물성 도메인 + 근거」, 「SP 쌍둥이 =
   코어 + 긴 꼬리 + 업무 문서」 의 **둘**을 전제한다(2단계 다리). 하나로 합치려면 SP 의
   `ontology`·`objects` 모듈을 MatNexus 로 이식하는 길인데, 이식 비용(마이그레이션 23개,
   프론트 모듈 셋)보다 **두 플랫폼이 갈리는 비용**이 큰지 먼저 본다. 지금 답: **둘로 가고,
   다리(2단계)가 아프면 그때 합친다.**
2. **파일럿 그룹의 자료는 무엇이 많은가.** 시험성적서·데이터시트가 많으면 4단계가
   MatNexus 쪽에 무겁고, 회의록·PPT·CAE 보고서가 많으면 SP 쪽이 무겁다. 조언 §1 의
   「문서 종류가 아니라 업무 세계」 — 그룹 정리 템플릿(SP `templates/파일럿-그룹-정리.md`)을
   먼저 채운다.
3. **AI 정책.** 사내 문서를 외부 모델에 보낼 수 있나. 4단계의 추출기(`extractor`)가
   무엇이 될지가 여기서 정해진다 — 안 되면 사내 모델 + 결정적 파서(표·시트) 비중이 커진다.
4. **근거를 얼마나 강제하나.** §F 는 「막지 않고 센다」 로 두었다. 특정 종류(예: 문헌
   물성값)만 근거 필수로 올릴지.

## 5. 하지 않을 것 — 다시 적는다

- MatNexus 표를 일반 객체(JSONB)로 옮기지 않는다. SP 의 `system` 타입이 그러지 말라고
  있는 것이다.
- LLM 이 타입·관계 종류를 만들지 않는다. 인스턴스와 별칭 **후보**까지만.
- 관계 종류 30개를 넘기지 않는다. 넘길 것 같으면 근거 표나 속성으로 내린다.
- RDF/OWL/그래프 엔진 — 방아쇠([계획] 온톨로지 §1-③)가 안 당겨졌다. 두 플랫폼을 건너는
  질의가 잦아지면 그때 본다.
- 문서 본문을 마디로 넣지 않는다. 마디는 작고 안정적이고 권한이 안 붙는 것.
