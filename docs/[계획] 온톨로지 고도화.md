# [계획] 온톨로지 고도화 — 카드가 나오게, 물성이 찾히게

2026-09-16. 전면 수정(같은 날 세 번째). 앞 판은 「문서 근거」 를 앞에 두었는데, MatNexus 의
용도가 아래 둘로 확정되어 **그 둘에 직접 답하는 것**으로 순서를 다시 잡았다.

| | 용도 | MCP 로 오는 물음 |
| --- | --- | --- |
| ① | 연결된 플랫폼이 **재료 · 시뮬레이션 안의 물성 id · 솔버**를 주면 그 **CAE 카드(덱)** 를 돌려준다 | 「SECC 를 MID 3 으로 LS-DYNA MAT_024 로 줘」 |
| ② | 여러 물성을 **조회해 찾는다** — 사내 측정과 문헌을 가리지 않고 | 「항복강도 200 MPa 근처, 80 °C, 믿을 만한 것」 |

StandardPlatform(SP) 은 참조만 한다(별도 시스템). 조언의 5층(Core→Domain→Instance→
Evidence→Document)에서 이 두 용도에 닿는 것은 **Domain 과 Instance 사이의 「길」** 이고,
Evidence 는 그 뒤다. 지금까지 한 것은 [[계획] 온톨로지](%5B계획%5D%20온톨로지.md) · ADR 0028.

> 한 줄 결론: **코드 안에만 있는 규칙 셋 — 「이 솔버 형식에 어떤 블록이 필요하다」 · 「이 시험이
> 어떤 물성을 낸다」 · 「이 값이 어떤 조건에서 나왔다」 — 을 관계와 축으로 꺼내 놓으면, ① 은
> 「나오나 · 왜 안 나오나 · 어디서 채우나」 를, ② 는 「어떤 물성이 어떤 조건에 어떤 등급으로
> 있나」 를 질의 한 번에 답한다.** 표는 안 갈아엎는다.

## 1. 지금 어디까지 되나 — 실측

### ① 카드 뽑기

> **BOM 덱**이란: 부품표(BOM — 부품마다 재료 이름이 적힌 표)를 붙여 넣으면 줄마다 사내
> 카드나 문헌 재료를 맞춰(`match_bom`) **여러 재료를 한 덱 파일로** 내는 것이다
> (`/cards/bom-deck` 화면, MCP `build_deck`). 부품표의 번호가 그대로 MID 가 된다.
> 「여러 재료 + id 지정」 은 이 길이 이미 하고 있었고, 빠져 있던 것은 솔버 선택과
> 단일 카드의 MID 였다.

```
match_bom(부품표) → build_deck(rows=[{mid, name, card_id | catalog_material_id}], units)
```

| 되는 것 | 안 되는 것 |
| --- | --- |
| **여러 재료를 한 덱으로**, **MID 는 요청 쪽이 지정**(`POST /fitting/decks/bom`, `BomDeckRowIn.mid`). 사내 카드는 곡선 덱(*MAT_024), 문헌만 있으면 스칼라 덱, 각주에 출처 | **솔버를 못 고른다** — BOM 덱은 LS-DYNA 고정(`lit_format="dyna_elastic"`, 카드는 「가장 곡선다운 형식」 을 스스로 고름). Abaqus·OptiStruct·Radioss 형식은 **단일 카드 export** 에만 있다 |
| 단일 카드 export 는 형식·단위계를 고른다(`GET /fitting/cards/{id}/export?format&units`) | 단일 export 는 **MID 를 못 준다** — 카드 UUID 에서 만든 수가 박힌다 |
| 형식마다 필요한 블록이 `ExportProfile.definition.needs` 에 적혀 있고 `missing_for()` 가 판정한다 | 그 판정은 **카드 하나를 렌더할 때만** 나온다. 「이 **재료**로 MAT_024 가 나오나」 는 카드를 열어 `available_formats` 를 봐야 알고, **왜 안 나오나 · 어디서 채우나**는 아무 도구도 답하지 않는다 — AI 가 `measurement_gaps` · `adopt_catalog_values` · `how_to_measure` 를 알아서 이어야 한다 |

### ② 물성 찾기

| 되는 것 | 안 되는 것 |
| --- | --- |
| 이름 해소(사전 271 + 별칭) · 단위 환산 값 검색(`find_by_property`) · 문헌 등급 1~4 · 사내↔문헌 재료 잇기(`links_to`) · 장비(`measured_by`) · 비교 도구 둘 | **조건**(온도·변형률속도·주파수)으로 못 거른다. 조건은 `test_runs.conditions` 에 시험 종류가 정의한 **제 이름의 키**로 있고(부서마다 `temp`·`temperature` 가 갈릴 수 있다), 카드 블록에는 조건이 안 실리고, 문헌값 `conditions` 는 자유 JSON |
| | **사내 물성에 등급이 없다.** 검색 결과에 문헌 3등급 값과 사내 실측 3표본 평균이 **같은 줄로** 선다 |

| | 이름을 못 푼 말(「UTS」)이 **아무 데도 남지 않는다** |

## 2. 보강 — 무엇을, 왜, 어떻게

### A. 카드 요구 그래프 — 「온톨로지에 채운다」 의 뜻

지금 「MAT_024 에는 `elastic` 과 `plastic` 블록이 필요하다」 는 규칙은 **덱 정의 JSON 안(`needs`)** 에
있고, 「인장시험은 `elastic`·`plastic` 블록을 낸다」 는 **블록 레지스트리 코드(`register_block`)**
에 있고, 「문헌 `mechanical.yield_strength` 는 `plastic.yield_stress` 자리에 들어간다」 는 **채택
코드** 에 있다. 셋 다 기계가 실행은 하지만 **질의는 못 한다** — 「이 재료로 MAT_024 가 나오나」 를
물으면 렌더를 돌려 봐야 안다.

「온톨로지에 채운다」 = 이 셋을 **관계 레지스트리의 마디·관계로 한 번 더 적는 것**이다. 표를
새로 만드는 게 아니라 `source=table:export_profiles(...)` · `source=code:` 로 **이미 있는 곳을
가리키기만** 한다(ADR 0028 의 방식 그대로). 그러면:

```
export_profile「dyna_mat024」 ─needs─▶ block「elastic」, block「plastic」
test_type「인장」            ─yields─▶ block「elastic」, block「plastic」
catalog property「yield_strength」 ─fills─▶ block「plastic」.yield_stress
material「SECC」 ─has_card─▶ card ─has_block─▶ block「elastic」        (있음)
```

에서 **한 번의 트래버설**로 답이 나온다:

| 물음 | 길 |
| --- | --- |
| 이 재료로 MAT_024 가 나오나 | 카드의 블록 ⊇ 형식의 `needs`? |
| 왜 안 나오나 | `needs` − 카드 블록 = 「`plastic` 이 없다」 |
| 어디서 채우나 | `plastic` ◀yields─ 「인장시험」 · ◀fills─ 문헌값 3건(등급 2) · ◀computed_by─ 계산식 |

만들 것: 마디 `export_profile` · `block`(카드 블록 종류) 둘, 관계 `needs` · `yields` · `fills` ·
`has_block` 넷. 그리고 이것을 그대로 보여 주는 화면·도구 —

- 재료 상세 **「낼 수 있는 형식」 표**: 형식 × (나옴 / 빠진 블록 / 채울 길). 카드가 여럿이면 카드별.
- MCP `deck_readiness(material_id, format)` → `{ready, missing_blocks, ways_to_fill}`. **① 의 첫 도구**가 된다 — AI 가 형식을 시도하기 전에 이것을 본다.

### B. 덱 — 솔버를 고르고, 단일 카드도 MID 를 받는다

온톨로지가 아니라 ① 을 닫는 데 필요한 둘.

| 무엇 | 지금 | 고침 |
| --- | --- | --- |
| `build_deck` 이 **솔버 형식**을 받는다 | LS-DYNA 고정 | `format=`(카드용) · `lit_format=`(문헌용) — 단일 export 가 이미 아는 형식 목록 그대로. 형식이 그 카드에서 안 나오면 그 줄은 `skipped` 에 이유와 함께(§A 의 빠진 블록) |
| 단일 export 가 MID 를 받는다 | 카드 UUID 에서 만든 수 | `?mid=3` — BOM 덱과 같은 범위 검사(1~`MAX_SOLVER_ID`) |
| 요청 플랫폼의 부름 | 부품표 매칭 뒤 두 단계 | `build_deck(rows=[{mid, material_id | card_id, format}])` 한 번 — 재료 id 만 주면 서버가 낼 수 있는 카드를 고른다(§A 의 판정을 쓴다) |

### C. 사내 물성에도 등급 — 문헌과 같은 척도로

찾기 결과에 문헌과 사내가 섞여 서는데, 문헌만 1~4 등급이 있다. **사내 값에도 같은 척도**를 준다.
MCP 로 찾으면(`find_by_property` · `materials_with`) **사내·문헌이 한 목록**에 오고, 줄마다
`origin`(측정/문헌/선언/계산)과 `tier` 가 붙는다 — 「등급 2 이상만」 은 `min_tier=2`, 「사내
실측만」 은 `origin="measured"`. 섞어 보되 갈라 볼 수 있어야 한다.
사람이 매기지 않고 **카드가 자기 근거에서 산출한다**(매기면 두 벌이 되고, 두 벌은 갈린다):

| 등급 | 문헌(있음) | 사내(더함) — 자동 |
| --- | --- | --- |
| 1 | 그 제품 문서에 인쇄된 실측 | 시험 · 채택된 처리 결과 · **표본 ≥ 3** / 선언 물성 중 **밀시트·데이터시트** 출처(그 제품·그 로트의 문서) |
| 2 | 핸드북·규격·공인 DB | 시험 · 채택 · 표본 1~2 / 선언 물성 중 **규격** 출처 |
| 3 | 계열 대표값·2차 인용 | **선언 물성 중 「문헌」 출처**(어느 문헌인지·그 문헌의 등급을 모른다) |
| 4 | 계산·추정·가정 | **계산식으로 낸 값** · **합성 곡선**(`synthesize`) · 추정 |

`find_by_property` · `compare_*` · 커버리지(§E)가 등급을 한 열로 보이고 `min_tier=` 로 거른다.
덱 각주에도 값마다 등급이 실린다 — 「이 덱은 등급 1 값 7개 · 등급 3 값 2개(밀도·푸아송)」.

### D. 조건을 축으로 — 「어떤 조건에」 를 기계가 알게

조건이 못 찾히는 원인은 **이름이 통일돼 있지 않아서**다. 시험 종류마다 조건 칸을 제 이름으로
정의하고(ADR 0006 — 시험 종류를 부서가 만든다), 문헌값은 자유 JSON 이다. 값은 SI 로 정규화돼
있지만(`normalize_conditions`) **키가 다르면 같은 조건이 아니다.**

해법은 기준정보가 이미 하는 방식이다 — **축을 하나 두고 바인딩한다**(ADR 0010).

| 무엇 | 모양 |
| --- | --- |
| 기준정보 축 「시험 조건」 | 용어: `temperature` · `strain_rate` · `frequency` · `humidity` · `pressure` · `aging_time` · `pre_strain` … 각각 SI 단위 |
| `test_condition_fields.canonical_key` | 시험 종류의 조건 칸이 어느 축 용어인가. 비우면 「이 시험만의 조건」 — 찾기에는 안 쓰이지만 잃지는 않는다. 화면: 조건 칸 정의에 「표준 조건」 고르기 |
| 카드 블록에 `conditions` 스냅샷 | 카드를 만들 때 쓴 시험들의 조건을 **표준 키로** 블록에 함께 적는다(값 범위 — 같은 카드가 23 °C 시험 5건이면 `{temperature: 296.15}`, 여러 온도면 표 블록이 온도를 열로 갖는다). 카드는 자기 근거를 들고 있어야 한다는 원칙(§source)의 연장 |
| 문헌값 `conditions` → 표준 키 매핑 | 이관 때 `temperature`/`T`/`temp` 를 표준 키로. 못 푼 키는 그대로 두고 센다 |
| 값 검색·비교에 조건 | `find_by_property(…, conditions={"temperature": {"near": 353.15, "tol": 5}})` — 단위는 값과 같은 규칙으로 **반드시** 받는다 |

조건은 **마디가 아니라 값의 한정자**다 — 그래프는 커지지 않는다.

### E. 커버리지 — 「이 재료에 무엇이 어떤 조건에 어떤 등급으로」 한 장

§A·C·D 가 있으면 계산만으로 나온다. 새 표 없음.

| 도구 | 답 |
| --- | --- |
| `property_coverage(material_id)` | 행 = 물성(블록 key), 열 = 표준 조건, 칸 = {출처: 측정/문헌/선언/계산, 등급, 값·범위, 카드/시험 id}. 빈 칸은 「없다」 가 아니라 「이 조건에는 없다」 |
| `materials_with(property, conditions, min_tier)` | 반대 방향 — ② 의 본 물음. 사내 카드와 문헌값을 **한 목록**에 등급 열과 함께 |
| 재료 상세 「물성 지도」 탭 | 같은 계산의 화면. 칸을 누르면 그 값·근거로 |

### F. 이름을 못 푼 말 — 「별칭 후보 큐」 의 뜻

지금: AI 나 사람이 「UTS」 로 찾으면 사전에 없어 빈손이고, **그 사실이 아무 데도 남지 않는다.**
다음 사람도 같은 말로 다시 실패한다.

바꾸는 것: 못 푼 말을 표 하나(`alias_candidates`: 말 · 어디서(검색/MCP/이관) · 몇 번 · 처음/마지막)
에 **쌓아 두고**, 관리자 화면(기준정보 옆)에 「해소 못 한 이름 12」 로 뜬다. 관리자는 줄마다
둘 중 하나를 누른다 — **「인장강도의 별칭으로」**(→ `term_aliases`/물성 사전에 들어가 다음부터
찾힌다) 또는 **「무시」**. 같은 말이 다시 오면 횟수만 오른다. AI 는 후보를 **만들 뿐** 사전을
고치지 못한다. 그것이 큐다 — 실패를 자산으로 바꾸는 줄.

### G. 근거(Evidence) 층 — 뒤로, 그러나 지운 것은 아니다

「이 값 어느 문서 몇 페이지」 는 ①② 다음이다. 다만 §C 의 등급이 근거의 **요약**이고, §A 의
`fills`·`computed_by` 가 근거의 **길**이라, 여기까지 하면 근거 층은 「문서 파일 + 페이지」 를
더하는 일로 줄어든다. 문서가 들어오는 자리는 넷(논문·데이터시트·성적서·교정서)이고 추출은
서버 밖에서 하고 서버는 붙여넣기 → 미리보기 → `proposed` → 승인만 한다(앞 판 §D 그대로).

### H. 관계 레지스트리 — 19 → 27, 30 안쪽

| 더함 | 마디 | 뜻 | source |
| --- | --- | --- | --- |
| `needs` | export_profile → block | 이 형식은 이 블록이 있어야 나온다 | `table:export_profiles.definition.needs` + 코드 렌더러 |
| `has_block` | property_card → block | 이 카드에 이 블록이 있다 | `table:property_cards.blocks` |
| `yields` | test_type → block | 이 시험 종류가 이 블록을 낸다 | `code:register_block` |
| `fills` | catalog property → block key | 문헌 물성이 카드의 이 자리에 채택된다 | `code:adopt` 매핑 |
| `computed_by` · `input_of` | block 값 → formula | 계산의 계보(ADR 0030) | fk / edge |
| `ran_with` | processing_result → recipe | 이 레시피로 돌린 결과 | fk |

뺀 것: `evidenced_by`(관계가 아니라 근거 표) · `calibrated`(자료 4건) · `member_of`(ADR 0026 초안) ·
`substitute_for`(사람이 적는 관계 — 수요가 실측되면). `entity_edges` 표는 여전히 안 만든다.

### I. 평가 — 「AI 가 찾나」 를 숫자로

물음 30개를 **① ② 에서 뽑는다** — 「SECC 를 MID 3 으로 MAT_024」 · 「나오나 안 나오나, 왜」 ·
「200 MPa 근처 80 °C 등급 2 이상」 · 「이 재료에 뭐가 있나」 — 답에 반드시 있어야 할 것 + 도구
자취 채점(호출 수 · 지도 봤나 · 빈손 호출). CI 밖, 릴리스 전 추세. **먼저 만들어 기준선을 잰다.**

## 3. 단계

| 단계 | 기간 | 내용 | 닫히는 물음 |
| --- | --- | --- | --- |
| **0** 기준선 | 1주 | §I 물음 30 + 채점기 | 뒤 단계마다 「나아졌나」 |
| **1** 카드가 나오게 | 2주 | §A 마디·관계 넷 + `deck_readiness` + 「낼 수 있는 형식」 표 · §B `build_deck(format)` · 단일 export `mid` | ① 「나오나 · 왜 안 나오나 · 어디서 채우나 · 상대 id 로 어느 솔버든」 |
| **2** 등급·조건 | 2주 | §C 사내 등급 자동 산출 · §D 조건 축 + 바인딩 + 카드 블록 조건 스냅샷 + `find_by_property(conditions)` | ② 「어떤 조건에 · 믿을 만한 것」 |
| **3** 커버리지·후보 | 1~2주 | §E `property_coverage` · `materials_with` · 「물성 지도」 탭 · §F 별칭 후보 큐 | ② 「이 재료에 뭐가 있나」 · 실패가 사전이 된다 |
| **4** 관계 마무리 | 1주 | §H `computed_by` · `ran_with` · `requested_by` · 덱 각주에 등급 | 「이 값 어디서 왔나」 의 절반 |
| **5** 근거 층 | 2주 | §G `documents` · `evidence` · 붙여넣기 → `proposed` → 승인 | 「어느 문서 몇 페이지」 |

0 → 1 → 2 는 순서가 있다(2 의 커버리지는 1 의 블록 마디와 2 의 조건 축 위에 선다). 3·4 는 바꿔도 된다.

## 4. 하지 않을 것

- 표를 일반 객체(JSONB)로 옮기지 않는다 — 마디는 그대로, 관계는 있는 곳을 가리킨다(ADR 0028).
- 등급을 사람이 매기지 않는다 — 카드가 근거에서 산출한다. 매기면 두 벌이 되고 갈린다.
- 조건을 마디로 만들지 않는다 — 값의 한정자다. 그래프는 커지지 않는다.
- 서버 안에서 LLM 으로 값을 뽑지 않는다. AI 는 별칭 **후보**까지만.
- 관계 종류 30개를 넘기지 않는다.
- 사내 재료코드·ERP 코드 해소 — 수요가 없다. 요청은 MatNexus 재료 id 로 온다.
- RDF/OWL/그래프 엔진 — 방아쇠([계획] 온톨로지 §1-③)가 안 당겨졌다.
