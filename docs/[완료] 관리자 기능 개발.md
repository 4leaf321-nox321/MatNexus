## 1. 백업이 없다 — 전 영역에서 가장 크다 🔴

배포 스크립트 · 주기 작업(`app/jobs/schedule.py` 의 `PERIODIC`) · 문서 어디에도
DB 덤프나 파일스토어 백업이 없다.

**왜 가장 큰가.** 휴지통 · 보관 · 감사 기록이 아무리 잘 되어 있어도 전부 **같은 DB
안**에 있다. 디스크 고장, 잘못된 마이그레이션, `purge` 오용 앞에서는 전부 무력하다.
휴지통의 영구 삭제는 서버가 `confirm=true` 를 다시 받는 이중 확인까지 갖췄지만,
영구 삭제가 진짜로 「영구」 인 시스템은 **백업이 있는 시스템뿐**이다.

**구현 스케치**

- `scripts/deploy/backup.ps1` — `pg_dump` + 파일스토어를 다른 드라이브로 복사.
  UTF-8 BOM(AGENTS 규칙), `Invoke-Native` 로 감싼다(5.1 이 stderr 를 종료성
  오류로 바꾼다 — alembic 에서 겪은 그 함정).
- Windows 작업 스케줄러 등록 안내를 스크립트 머리말에 적는다(설치는 사람이 한다 —
  워커 프로세스에 넣으면 워커가 죽은 날 백업도 조용히 죽는다).
- 세대 관리: 일 7 + 주 4 정도. 지우는 것도 스크립트가 한다 — 안 지우면 백업이
  디스크를 채운다.
- 서버 화면(`/server`)에 **마지막 백업 시각** 표시. 백업 폴더의 최신 파일
  mtime 을 읽으면 되고, 없으면 「백업이 없습니다」 를 붉게 — 안 보이면 없는 것과
  같다.
- 복구 절차를 핸드북에 적는다. **복구를 한 번 실제로 해 본다** — 복구해 본 적
  없는 백업은 백업이 아니다.

## 2. 실패한 백그라운드 작업이 안 보인다 🟠

큐 자체는 잘 되어 있다 — 재시도 3회(`max_attempts`), 지수 백오프, 멈춘 작업 회수
(`reclaim_stalled`). 그런데 3회 다 실패해 `failed` 가 된 작업을 **보는 화면도 API 도
없다.**

파싱 실패는 시험 목록의 상태 열로라도 보인다. 하지만 알림 발송 · 드리프트 점검 같은
다른 종류의 작업이 실패하면 아무 데도 안 뜬다 — 야간에 조용히 죽고, 알림이 안 온
사람은 알림이 없었다고 여긴다.

**구현 스케치**

- 서버 화면에 큐 탭: 대기 n · 도는 중 n · 실패 n, 실패 목록(종류 · 마지막 오류 ·
  시각), 줄마다 「다시 시도」(attempts 를 0 으로 되돌리고 status 를 queued 로).
- 홈 「남은 일」 줄에 「실패한 작업 n」 (아래 3번과 합류).

## 3. 홈에 운영 경고가 없다 — 보여 주지만 알려 주지 않는다 🟠

세 가지가 각자 자기 화면 안에만 있다:

| 무엇 | 지금 어디 | 문제 |
| --- | --- | --- |
| 디스크 사용률 | 서버 화면 `/server` | 열어야 보인다. 운영자는 평소에 안 연다 — 차는 날은 갑자기 온다 |
| 보존기간 지난 소프트 삭제 | 저장소 리포트(「가장 크다」 고 세기까지 한다) | 치우는 손이 없다. 주기 작업엔 드리프트 점검뿐이라 디스크가 조용히 찬다 |
| 실패한 작업 | 아무 데도 없음 | 위 2번 |

**구현 스케치** — 홈의 「남은 일」 줄(읽기 실패 · 붙일 파일 · 확정 대기가 이미 있는
그 줄)에 세 항목을 더한다:

- 「디스크 n% (임계 85%)」 — 초과 시에만.
- 「보존기간 지난 삭제 n건 · m GB」 — 누르면 저장소 정리로. **자동 영구삭제는
  하지 않는다** — 지우는 결정은 사람이 하고, 홈은 그 결정이 밀리고 있다는 사실만
  말한다.
- 「실패한 작업 n」 — 누르면 서버 화면 큐 탭으로.

기존 홈 통계 API 에 세 수를 더하는 일이라 규모가 작다. 숫자는 서버가 센다 —
목록을 받아 화면이 세면 상한에 걸린 순간 숫자가 조용히 틀린다(기존 규칙 그대로).

## 4. 계정 — 골격은 튼튼, 복구 경로가 외길 🟠

**잘 되어 있는 것 (건드리지 않는다)**

- 마지막 관리자 가드: 자기 권한을 못 빼고, 마지막 관리자는 삭제도 거절 —
  관리자 0명이 되는 길이 코드로 막혀 있다.
- 삭제 시 refresh 토큰 즉시 폐기, 소유물은 dependents 로 먼저 보여 준다.
- 임시 비밀번호 발급 — SMTP 없는 환경에 맞는 선택. 초기 비밀번호 강제 변경.
- 정지/활성 분리, 전부 감사 기록.

**문제와 대응**

- **관리자 본인의 복구 경로가 서버 콘솔뿐이다.** 비밀번호 재설정은 「다른 관리자가
  발급」 이 유일한 길이라, 관리자가 1명인 지금 그 사람이 잠기면
  `scripts/set_admin.py` 를 서버에서 직접 돌려야 한다 — **2026-08 말에 실제로 겪은
  상황이다**(비밀번호 착오로 로그인 실패, 콘솔에서 재설정).
  - 대응 ①: **시스템 관리자 2인 이상 유지**를 운영 수칙으로 핸드북에 적는다.
    코드로 강제하지는 않는다 — 도입 초기에 1인일 수밖에 없는 기간이 있다.
  - 대응 ②: `set_admin.py` 복구 절차를 핸드북 「잠겼을 때」 항목으로 옮겨 적는다.
    사고 났을 때 찾는 문서는 코드 주석이 아니다.
  - 대응 ③(화면): 계정 화면에 시스템 관리자가 1명뿐이면 안내 한 줄.
- **로그인 시도 제한이 없다** 🟡 — 사내망이라 위험도는 낮다. 도입한다면 「n회
  실패 시 지연」. **잠금은 하지 않는다** — 관리자 복구가 외길인 시스템에서 잠금은
  자해다.

## 5. 부서 정보 — 흐름은 완성, 온보딩 노이즈가 남는다 🟠

가져오기(RA 트리) → 합치기(이관) → 보관 → 삭제 한 줄기는 2026-09 첫 주에 정비됐다
(v1.198~v1.199.1). 마지막 manager 제거 방지도 있다.

**문제와 대응**

- **모든 부서의 관리자가 사실상 시스템 관리자 1인이다.** 부서를 만들면(가져오기
  포함) 만든 사람이 manager 로 들어간다 — 잠긴 부서(manager 0명)를 막는 옳은
  규칙이지만, RA 트리 수십 개를 가져오면 **그 부서 전부가 멤버 1명(가져온 관리자)**
  이 된다.
  - 대응 ①: 도입 체크리스트에 「부서마다 실제 부서장을 manager 로 지정하고 임시
    manager(시스템 관리자)는 빠진다」 를 적는다.
  - 대응 ②(화면): 부서 관리에 「관리자가 시스템 관리자뿐인 부서 n개」 표시 —
    아직 부서장을 안 정한 부서가 한눈에 보이게.
- ~~합친 뒤 같은 key 의 시험 종류가 중복될 수 있다~~ — **사실이 아니었다.** 시험
  종류 key 는 전사 유일이라 중복이 못 생긴다. 진짜 충돌 지점은 재료 이름과 읽을
  형식 key 이고(겹치면 합치기가 500), 그 분석과 대응은
  [데이터 체계 개선](%5B완료%5D%20데이터%20체계%20개선.md) 3번에 있다.
- 합치는 순간 그 부서를 보고 있던 사람의 화면은 새로고침 전까지 옛 이름이다 🟡 —
  알고만 있는다.

## 6. 기준정보 편집 — 설계 좋음, 병합만 편도 🟠

**잘 되어 있는 것**

- 값 추가는 일반 사용자(피커에서 엔터, 중복이면 409 가 아니라 기존 반환),
  수리 · 병합은 시스템 관리자 — 병목 없이 통제.
- 어긋남 점검이 6시간마다 자동으로 돌고(`VOCABULARY_CHECK_DRIFT`) 수리 기능이 있다.
- 병합하면 옛 표기가 별칭으로 남아 재발을 막는다. 병합 이력(`VocabularyMerge`)이
  남는다.

**문제와 대응**

- **병합 되돌리기가 없다.** 이력은 남지만 역방향이 없다 — 「포스코」 에
  「포스코케미칼」 을 실수로 합치면(서로 다른 회사다) 옮겨진 참조 수백 건을
  수작업으로 갈라야 한다.
  - 되돌리기를 만드는 것은 크다(옮긴 참조를 어느 쪽으로 되돌릴지 병합 후 기록으로는
    못 가른다). 대신 **부서 합치기와 같은 사전 미리보기**를 확인·보강한다:
    몇 건이 옮겨지는지 + 확인을 병합 전에 보여 주는지 화면 기준으로 점검하고,
    없으면 붙인다. 실수는 누르기 전에 막는 것이 이 저장소의 무늬다.

## 7. 휴지통 — 지우는 쪽은 안전, 쌓이는 쪽이 방치 🟠

**잘 되어 있는 것**

- 복구, 계층 겹침 처리(재료와 그 아래 시료를 함께 골라도 안 터진다).
- 영구 삭제는 서버가 `confirm=true` 를 다시 받는다 — API 직접 호출 방어.
- 시스템 관리자 전용, 감사 기록.

**문제** — 보존기간 지난 것을 치우는 손이 없다. 위 3번(홈 경고)으로 대응한다.
자동 영구삭제는 하지 않는다.

## 8. 서버 — 로그 회전은 있음, 알림이 없음

- 로그는 일별 회전 + 보존일 설정이 이미 있다(`TimedRotatingFileHandler`).
- 호스트/CPU/메모리/디스크/DB/버전 표시, 저장소 리포트(오펀 · 잔재 · 보존 초과 3종)
  까지 있다.
- 비어 있는 것은 위에서 다 다뤘다 — 백업(1번) · 디스크 경고(3번) · 큐 탭(2번).
