## 3. 나중에 바꾸면 비싼 구조 결정 14가지

착수 시점에 반영한다. 나머지는 필요해질 때 붙여도 늦지 않다.

### 데이터·스키마

1. **조직 식별자를 내부 키로 감싼다** — 부서를 `workspace.id`(불변 내부 키)로 참조하고
   표시명·slug·외부 claim은 별도 컬럼. 부서 개편·SSO 전환 때 데이터가 묶이지 않는다.
2. **불변/가변을 분리한다** — 곡선·처리결과·모델 파라미터·카드는 불변 리비전.
   표시 설정·임계값·라벨·색상은 별도 가변 테이블. 라벨 하나 바꿨다고 리비전이 찍히면
   안 된다. (65에 이 계층이 없다)
3. **업로드 한도를 유형별로 설계한다** — 시험 원본 / 메시 / 결과 파일의 성격이 다르다.
   단일 한도(65는 16MB)로는 CAE 운영이 안 된다.
4. **계정 삭제와 자료 승계 경로를 처음부터 둔다** — 퇴사자가 등록한 시험 데이터의
   소유권을 누가 받는가. 소유자 컬럼과 이관 잡의 설계에 영향을 준다. IdP를 쓰더라도
   자료 소유권 승계는 애플리케이션 책임이다.

### 확장점의 형태 — 기능이 아니라 형태라서, 나중에 붙이면 만들어진 것을 다 고쳐야 한다

5. **의존성 레지스트리를 먼저 둔다** — `shared/dependents.py`가 `Base.metadata`를 훑어
   FK를 자동 수집. 삭제·이관·아카이브 기능을 만들기 **전에** 넣는다. RA는 이게 없어
   부서 삭제 500 버그를 겪었다(참조 테이블 목록이 하드코딩돼 새 테이블을 못 따라감).
6. **알림을 3분할로 만든다** — `NotificationRule`(규칙) / `RuleState`(발화 상태) /
   `DispatchRun`(발송). 합쳐 만든 뒤 나누는 비용이 크고, 섞으면 중복 발송·상태 꼬임이
   난다.
7. **검색 텍스트를 재귀 추출로 만든다** — D7이 시험종류를 데이터로 정의하게 하므로,
   **스키마별 추출기를 만들면 정의가 늘 때마다 추출기를 따라 만들어야 한다.** 타입에
   결합하지 않고 JSON을 재귀로 훑어 사람이 읽는 문자열만 수집하고, 위치 메타(시험 id ·
   채널 · 필드 경로)를 붙여 검색 스니펫·점프가 같은 토대를 쓰게 한다. 노이즈는 부분일치
   검색에서 무해하다.
8. **정의·규칙의 단일 소스를 만든다** — 시험종류·채널·단위 정의와 그에 딸린 사용자
   도움말·검증 규칙을 `definitions/` 한 곳에 두고 백엔드 런타임·프론트·문서가 그것을
   참조한다. 지금 정하지 않으면 규칙이 코드와 문서로 흩어진다.
9. **PAT(개인 액세스 토큰)를 인증 스키마에 처음부터 넣는다** — 장비 파이프라인이
   API로 데이터를 밀어넣을 자격 증명. sha256 저장 · 평문 1회 노출 · 만료 · 폐기 ·
   최근 사용 기록. 나중에 넣으면 토큰 체계가 둘로 갈라진다.
10. **`matcore` 경계를 기계가 검사한다** — 이 설계의 전제 전부가 "matcore는 DB·HTTP를
    모른다"이다. 사람이 지키는 규약은 AI 개발에서 반드시 뚫린다. §8.2 참조.
11. **모듈 이름을 백엔드·프론트가 공유한다** — §4.2. 지금 맞추면 비용 0원, 400커밋
    뒤에 하면 65가 된다.

### 보안·운영

12. **refresh 토큰 DB 폐기 목록을 처음부터 넣는다** — RA가 비워둔 항목. 나중에 붙이면
    세션 전수 무효화 경로를 새로 만들어야 한다.
13. **예외를 로그로 전파한다** — 65는 `except Exception` 322회/60파일이 불투명한 409로
    치환돼 원인이 로그에 안 남는다. 오류 헬퍼에 로깅을 처음부터 심는다.
14. **기존 자산 흡수 경로를 초기에 확보한다** — 사내에 이미 쌓인 재료 엑셀·시험
    성적서를 못 가져오면 사용자가 옮겨오지 않는다. 도입 성패가 여기서 갈린다.

### 4.2 모듈 명명 규칙 — 어겼는지 기계가 검사한다

비교표는 65의 최대 탐색 비용 원인을 *"백엔드 16 모듈과 프론트 파일명 사이에 연결 규칙이
없어 양쪽 다 훑어야 함"*으로, RA의 최대 이점을 *"이름 하나로 코드와 화면을 동시에 찾음"*
으로 꼽았다. 규칙을 명문화하지 않으면 지켜지지 않는다.

- **R1.** 도메인 모듈은 백엔드 `app/modules/<name>`과 프론트 `src/modules/<name>`이
  **같은 문자열**을 쓴다. 다른 이름 금지.
- **R2.** 프론트에만 있어도 되는 것은 **조립 셸**(`workbench`)과 백엔드가 없는 순수
  화면(`profile`)뿐이다. 새로 만들 때는 ADR에 근거를 남긴다.
- **R3.** 백엔드에만 있어도 되는 것은 화면 없는 하부 기능(`audit`, `search`)이다.
  화면이 생기는 순간 같은 이름의 프론트 모듈을 만든다.
- **R4.** 리소스 모듈은 복수형. 비-리소스(`auth`, `admin`, `search`, `guide`)는 예외.
- **R5.** 워크벤치 5탭은 각 도메인 모듈이 export하는 탭 컴포넌트를 **조립만** 한다.
  탭의 도메인 로직이 `workbench/` 안에 쌓이면 규칙 위반이다.
- **R6.** 위 규칙과 `matcore` 격리를 `tests/architecture`가 검사한다. 통과하지 못하면
  CI가 막는다.

### 4.3 `matcore`가 핵심

65가 물성 6종에 131파일 44k줄을 쓴 원인은 도메인 코드가 4계층(domain/application/
adapters/persistence)에 흩어진 채 물성마다 복제된 것이다. MatNexus는 반대로 간다.

```python
# matcore/fitting/metal_voce.py
@register(kind="fitting", id="metal.voce", inputs=["true_stress_strain"],
          params=[...], produces="hardening_curve")
def fit_voce(curve: Curve, opts: VoceOptions) -> FitResult: ...
```

레지스트리에 등록하면 API·워크벤치 화면·익스포트 대상이 자동으로 따라온다.
**새 물성 추가 = 파일 2~3개**가 목표이며, Phase 5에서 이 비용을 실측해 검증한다.

`matcore`는 DB도 HTTP도 모른다. 입력은 dataclass, 출력은 dataclass. 그래서 테스트가
빠르고, 65에서 코드를 발췌할 때 어댑터 계층을 걷어내기만 하면 된다.

### 4.4 데이터 계층

```
Material (재료: 등급 · 재질군 · 소유 부서 · 공개범위)
  └ Condition (조건: 온도 · 변형률속도 · 방향 · 습도)        ← 물성의 본질적 축
      └ Specimen (시편 n개)                                  ← 통계의 단위
          └ Test (시험: 종류 · 장비 · 시험일 · 시험자 · 원본파일)
              └ Curve (채널 role · 단위 · 원본/정규화, Parquet 경로 + 해시)
                    │
                 [Recipe] ─→ Processed   불변 아티팩트
                    │
                 [Ensemble] ─→ Statistics  평균 · 편차 · 이상치 · 대표곡선
                    │
                 [Fit] ─→ Property        파라미터 + 적합도 + 근거 + 상태플래그
                    │
                 [Export] ─→ SolverCard   솔버별 카드 · 번들
```

65와 다르게 잡는 세 지점:

- **Specimen을 1급으로.** 65의 통계는 `reference_tensile_replicates` / `_outlier` /
  `_pair` 로 인장 전용이라 시험종류마다 복제된다. `앙상블 = 같은 Condition의 Specimen
  집합`으로 일반화하면 통계 코드 1벌이 모든 시험에 적용된다.
- **Recipe를 1급으로.** 65는 세션 핀 방식이라 같은 처리를 100건에 반복 적용하는 경로가
  약하다. 레시피를 저장 가능한 객체로 두면 배치 처리와 장비 파이프라인 자동화가
  같은 기계 위에 얹힌다.
- **시험종류를 데이터로.** `test_type` / `channel_spec` / `unit` 정의를 테이블과
  `definitions/`에 두고 관리 화면에서 편집한다. 새 시험을 받을 때 배포가 필요 없다.

## 5. GUI 구성

RA의 껍데기(`AppShell` + 접이식 `Sidebar` + `Header` + 커맨드 팔레트)를 그대로 쓰고,

| 내 활동 | 내 작업함 / 즐겨찾기 / 알림 | `/personal/*`, `/notifications` |
| 공통 | 공지 / VOC / 가이드 | `/notices`, `/voc`, `/guide` |
| 관리 | 계정 / 부서 멤버 / 시험종류 정의 / 장비 커넥터 / 오펀 파일 / 서버 | `/admin/*`, `/server` |

**워크벤치가 핵심 화면**이다. 65의 `Data / Process / Fit / Export` 4탭에 **Stats를 끼워**
5탭으로 간다.

```
Data ──→ Process ──→ Stats ──→ Fit ──→ Export
시험 선택   레시피 적용    앙상블·이상치   모델 피팅   솔버 카드
                        대표곡선 생성
```

여러 시편을 처리한 뒤 대표곡선을 만들고 그 곡선으로 피팅하는 것이 실제 작업 순서이며,
65에 Stats 단계가 없어 통계가 인장 슬라이스 안에 묻혀 있다.

**R5에 따라 각 탭은 자기 도메인 모듈에 산다.** `modules/tests/WorkbenchDataTab.tsx`,
`modules/processing/WorkbenchProcessTab.tsx` … `workbench/`는 탭 셸·세션 상태·라우팅만
갖는다.

**재료 상세**는 `개요 / 물성 / 곡선 / CAE 카드 / 이력` 5개 영역(65 구성 유지).

**차트**: 곡선 뷰어는 수천~수만 포인트를 다루므로 경량 라이브러리(uPlot 계열), 요약·분포
차트만 Recharts. Phase 2에서 실데이터로 확정하고 §8.5의 번들 예산에 넣는다.

## 8. 개발 규율

65와 RA의 격차 대부분이 코드 실력이 아니라 규율의 유무에서 나왔다. 아래는 Phase 0에
함께 세운다.

### 8.1 정적 검사

- Python `mypy strict = true` (app · matcore · tests 전 범위) + ruff
- TypeScript `strict: true` + eslint
- 비교표 평: *"mypy strict는 에이전트 개발에서 특히 값지다 — 잘못된 수정이 실행 전에
  걸린다. 65는 로컬에서만 돌아 이점이 절반만 실현된다."* → **CI에서 강제한다.**

### 8.2 architecture 테스트 (`tests/architecture`)

기계가 검사할 것:

1. `matcore/**`가 `sqlalchemy` · `fastapi` · `app.*`를 import하지 않는다 ← 최우선
2. `app/modules/A`가 `app/modules/B`를 직접 import하지 않는다 (`shared` 경유)
3. R1: 백엔드 모듈명 집합과 프론트 모듈명 집합의 대응 (R2·R3 예외 목록은 명시적으로 관리)
4. R5: `workbench/`에 도메인 API 호출이 없다
5. 모든 목록 엔드포인트에 서버 강제 상한이 있다 (`le=100`)

### 8.3 개발 지침 (`AGENTS.md` / `CLAUDE.md`)

비교표 F-3이 65의 누적 부채 원인을 정확히 짚었다 — 지침이 *"change only the missing
bounded scope"*만 말하고 **예외가 없어서**, 새 기능을 루트에 새 파일로 추가하는 것이
규율상 가장 안전한 선택이 되었고 436커밋이 쌓여 프론트 122파일 평면이 됐다.

우리도 AI로 개발하므로 지침에 다음을 명시한다.

> 범위는 좁게 지킨다. **다만 기존 배치가 이 계획서의 규칙과 어긋나면 작업 스코프 안에서
> 바로잡는다.** 스코프를 넘는 재배치가 필요하면 backlog에 `구조 정리` 항목으로 남긴다.

추가 규약: 명시적 join으로 N+1을 구조적으로 차단(65가 견고한 이유), 목록 상한 서버 강제,
오류는 구조화 코드(`MNX-TESTS-0001` 형식) + 로깅 동반.

### 8.5 프론트 검증 — 65의 재작업 44건이 여기서 나왔다

복잡도가 아니라 **시각 검증 자동화 부재**였다. 픽셀 회귀 0건 + 시각 게이트 비활성 상태라
어긋남을 사람이 눈으로 발견하는 것이 유일한 경로였다.

- **jsdom은 CSS 레이아웃을 계산하지 않는다.** 요소 존재는 잡아도 겹침·잘림·넘침은 못
  잡는다. 65는 Vitest 18.4k줄을 쓰고도 못 잡았다. → 존재 검증은 최소로, **Playwright
  픽셀 회귀를 주력**으로 한다. baseline 스크린샷이 곧 승인 기준이다
- 주요 화면별 렌더 스모크(65는 화면 29개에 spec 5개뿐이었다)
- **번들 예산 검사** — entry/lazy 청크별 바이트 예산. RA는 plotly+three.js를
  manualChunks 없이 들고 있다. 우리도 곡선 라이브러리를 넣으므로 처음부터
- **도메인 콘텐츠 컴포넌트 레이어** — shadcn은 프리미티브만 준다. 65는 폼·테이블·차트
  공용 컴포넌트가 없어 워크벤치당 1,200줄을 다시 썼다. `shared/components`에
  데이터 테이블 · 필터 폼 · 곡선 차트 래퍼 · 단위 표시를 만들고 화면은 조립만 한다
- 반응형·고DPI 정책(밀도 전환 + 기준 해상도 캡처)은 65 방식을 가져온다
- Storybook은 콘텐츠 컴포넌트 레이어와 함께 도입

## 9. 운영 절차

### 9.1 Day 0 신규 설치 — 원본에 없어서 새로 쓴다

52의 `DEPLOY_WINDOWS.md`는 *"이미 돌고 있는 설치를 새 버전으로 갱신하는 절차"*이며
신규 구축을 명시적으로 제외한다. 65는 compose 한 줄뿐이고 도커가 없으면 성립하지 않는다.
**차용할 원본이 없는 유일한 영역이다.**

`scripts/deploy/install.ps1`이 다음을 순서대로 수행한다.

1. `precheck.ps1` — Python 3.12 · PostgreSQL 접속 · 포트 · 디스크 여유 · 쓰기 권한
2. DB·역할 생성 (앱 계정과 소유자 계정 분리 — 나중의 RLS 도입 여지)
3. Alembic `upgrade head`
4. **설치 시드**만 주입 (§9.2)
5. `.env` 생성, 방화벽 규칙, 로그 폴더
6. 헬스체크로 기동 확인

각 단계는 멱등하고, 중단 후 재실행이 항상 같은 결과를 낸다. 65는 *"부분 주입 상태로
남아 화면 일부만 동작해 원인 추적이 어려움"*이었다.

### 9.2 시드 분리

- **설치 시드**: 초기 관리자(강제 비밀번호 변경) · 기본 부서 · 단위 · 기본 시험종류 정의
- **데모 시드**: 합성 재료·시험 데이터. 운영 설치에 들어갈 이유가 없다
- 둘 다 DB 직접 주입(API 경유 금지)이며 멱등

### 9.3 로그 — D9의 필연적 부작용

콘솔 실행을 택했으므로 로그가 콘솔에만 남으면 창을 닫는 순간 증거가 사라진다.
비교표 C-5(*원격 접근 없는 원인 파악*)가 통째로 공백이 된다.

- `logs/app-YYYYMMDD.log` 파일 출력 + 일자 로테이션 + 보존 기간
- 요청 ID를 오류 응답과 로그에 함께 실어 사용자 신고와 로그를 연결
- `except` 블록은 반드시 로깅을 동반 (§3-13)

### 9.4 백업 — 65·RA 양쪽 모두의 공백

정기 `pg_dump` + 파일스토어 스냅샷 + **복구 리허설**. Phase 1 종료 시점에 한 번 돌려
실제로 복구되는지 확인한다. 두 참고 플랫폼 모두 이걸 갖고 있지 않으므로 베낄 원본이 없다.

### 9.5 콘솔 상주의 대가 (D9)

- 재부팅·세션 종료 후 **수동 기동이 필요**하다. 서버 재기동 시 체크리스트를 운영 문서에
  둔다
- 자동 재시작이 없으므로 프로세스 사망을 감지할 수단(헬스 확인 루틴)을 둔다
- 필요해지면 작업 스케줄러(반입물 0) 또는 NSSM으로 승격한다. 승격 시 바뀌는 것은
  기동 방식뿐이며 앱 코드는 그대로다

## 10. RLS를 미루는 근거와 대비

비교표는 PostgreSQL RLS를 65의 최대 자산으로 평가했다(*"앱에 버그가 있어도 데이터가 새지
않는다"*). 초기 미도입은 복잡도 때문이며, 나중에 붙일 수 있도록 다음을 처음부터 지킨다.

- 모든 테넌트 소속 테이블에 `workspace_id` 컬럼을 둔다 (나중에 정책을 붙일 대상)
- DB 접속 역할을 소유자와 앱 계정으로 분리한다 (RLS는 소유자에게 적용되지 않는다)
- 가시성 필터를 각 쿼리에 흩뿌리지 않고 `shared/permissions.py`의 단일 지점에서 건다
- 부서 수가 늘 때 정책 평가 비용이 붙으므로, 도입 시 파일럿에서 부서 수를 늘려가며
  측정한다 (65도 이 측정을 하지 않았다)
