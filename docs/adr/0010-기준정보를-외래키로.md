# ADR 0010 — 기준정보를 외래키로

- 상태: 채택
- 날짜: 2026-08-19
- 관련: ADR 0004(재료 계층과 식별자 정책), ADR 0006(시험 종류를 부서가 만든다),
  ReportArchive `backend/app/modules/entities`

> **이름 (2026-08-22).** 화면과 문서는 이것을 **기준정보** 라 부른다. 코드 이름은
> `vocabulary` 그대로다 — 모듈·테이블·slug(`manufacturer`·`grade` …)·오류 코드
> (`MNX-VOCABULARY-*`)·경로(`/api/vocabulary`)는 **저장된 계약**이라 바꾸면 이미
> 쌓인 데이터와 어긋난다. 레시피 JSON 에 박힌 `linear_regression` 을 한국어로
> 안 바꾼 것과 같은 이유다(ADR 0011).

## 결정

사람이 타이핑하는 짧은 문자열 속성을 **기준정보 표로 올리고 외래키로 참조한다.**

```
vocabularies         축     manufacturer · grade · family · specimen_standard …
vocabulary_terms     값     (vocabulary_id, value)  UNIQUE (vocabulary_id, lower(value))
vocabulary_aliases   표기   '포스코(주)' → 포스코    UNIQUE (vocabulary_id, normalized)
```

`Material.grade` 는 `grade_id` 가 되고, `Sample.manufacturer` 는
`manufacturer_id` 가 된다. 축마다 **입력 정책**을 둔다 — `open` 은 사용자가
피커에서 즉석 추가할 수 있고, `closed` 는 관리자가 등록한 값만 고른다.

값을 만들 때 게이트를 지난다. **순서가 중요하다:**

```
1) 기존 값·별칭으로 찾아지면 그것을 돌려준다 (새로 안 만든다)
2) closed 축이면 사용자 추가를 막는다
3) 형식 검증
```

## 왜 지금인가

하루치 데이터에서 이미 드리프트가 보였다.

```
Family     'Metal'×82, 'Family'×1          ← 라벨을 값으로 입력
제조사       '포스코'×3, '???'×1, '현대제철'×1
시편 규격     'ASTM E8 subsize'×1, 'ASTM E8'×1
```

그리고 v0.4.0 에서 **제조사가 섞였는지 경고하는 기능**을 만들었다. 그 경고는
문자열 비교로 판정한다 — `'포스코'` 와 `'포스코 '` 를 다르다고 본다. 경고를
만들어 놓고 그 입력을 자유 텍스트로 두는 것은 앞뒤가 안 맞는다.

앞으로 재료가 수만 건, 기준정보가 수만 개가 된다는 전제다. **이 전제가 이 결정의
근거 전부다** — 기준정보가 열 몇 개로 끝난다면 문자열이 맞다.

## 결정한 것들과 근거

### 정규화만으로는 모자란다

처음에는 저장 전 정규화(NFKC·공백 정리·제로폭 제거)만 제안했다. 실측하면 눈에
같아 보이는데 DB 가 다르게 보는 여섯 가지가 전부 사라진다.

```
맥에서 붙여넣기(NFD 자모 분해) · 전각 'ＡＳＴＭ' · 논브레이킹 스페이스
끝 공백 · 가운데 두 칸 · 제로폭 문자
```

그런데 이것들은 **보이지 않는** 드리프트다. `'ASTM E8'` 과 `'ASTM E8 subsize'`
처럼 **사람이 일부러 다르게 적은 것**은 정규화로 못 잡는다. 그건 기준정보와 별칭의
일이다.

### 별칭은 청소가 아니라 예방이다

ReportArchive 의 `entity_aliases` 주석이 정확하다:

> 새 엔티티가 안 생기고, **사후 merge 필요성이 사라진다**

관리자가 `'POSCO'`·`'포스코(주)'` 를 미리 별칭으로 등록해 두면 게이트 1단계가
그것까지 뒤져서 애초에 중복이 안 생긴다.

### 병합하면 없어진 표기가 별칭으로 남는다

`src` 를 `into` 로 합칠 때 참조를 옮기고 끝내지 않는다. **`src` 의 값 자체를
`into` 의 별칭으로 등록한다.** 그래야 다음에 누가 옛 표기를 쳐도 자동으로
흡수된다 — 병합이 일회성 청소가 아니라 규칙이 된다.

### 문자열이 아니라 외래키인 이유

문자열로도 "다음부터 안 생기게" 는 된다(저장 시 정규 값으로 치환). 다른 것은
**이미 저장된 것을 소급해 묶는 것**이다.

```
FK   :  UPDATE samples SET manufacturer_id = :into WHERE manufacturer_id = :src
문자열:  전 행을 훑어 글자를 고친다 — 이건 병합이 아니라 일괄 치환이다
```

값 이름을 바꿀 때도 같다. FK 는 한 행, 문자열은 전 행이다.

대가는 변경량이다. 제조사 문자열을 쓰는 곳이 시료 폼·목록·섞임 경고·검색
필터·일괄 등록에 흩어져 있고, 전부 "번호로 받아 이름으로 보여 주기" 로 바뀐다.

### `grade` 를 기준정보로 두는 것이 최대 이득

`SECC` / `secc` / `S.E.C.C` 가 지금은 **서로 다른 재료 세 개**를 만든다. 통계도
카드도 셋으로 갈린다. 기준정보가 되면 입력 순간에 하나로 모인다.

대가: `grade` 는 `record_name` 을 만드는 값이라(ADR 0004) 기준정보 값 이름을 바꾸면
재료 이름이 전부 따라 바뀐다. 이미 있는 연쇄 이름 변경 경로를 그대로 쓴다.

### 기준정보는 전사 공용이다

제조사가 부서마다 다를 이유가 없다. ReportArchive 도 같은 판단을 했고,
필요해지면 컬럼 하나 추가라고 적어 뒀다. 시험 종류를 부서가 만드는 것(ADR 0006)
과는 다르다 — 그건 장비가 부서마다 달라서지, 기준정보가 달라서가 아니다.

### `closed` 는 만들어 두고 안 켠다

처음에는 Family·Category 를 `closed` 로 잡았다. `'Family'` 라는 값이 실제로
들어가 있었기 때문이다. 그런데 그 출처를 보니 **E2E 테스트가 넣은 것**이지 사람의
실수가 아니었다. 한 건짜리 인공물을 근거로 정책을 만드는 셈이다.

**막았을 때 사람이 어디로 가는지가 문제다.** 첫 발포재를 등록하려는데 `Foam` 이
목록에 없으면 관리자를 찾아가거나 — 더 흔하게는 `Metal` 로 대충 고르고 넘어간다.
그러면 분류가 지켜진 것이 아니라 **조용히 틀린 것**이다.

`closed` 가 값을 하는 자리는 **외부 시스템이 정본을 주는 축**이다(ReportArchive
는 모델·BOM 코드에 쓴다 — *"정형 마스터 축을 잠그는 데 쓴다"*). 거기서는 정본에
없는 값을 만드는 것 자체가 오류다. MatNexus 에는 아직 그런 축이 없다.

대신 관리 화면에 **「적게 쓰이는 것부터」** 정렬을 뒀다. 오타는 늘 `쓰는 곳 1` 로
생기는데 기본 정렬에서는 목록 끝에 묻힌다. 뒤집으면 검토할 것이 맨 위로 온다 —
축을 가리지 않고 듣는다는 점도 낫다.

메커니즘은 남긴다. Phase 6 에서 장비 커넥터가 붙어 정본이 생기면 그때 켠다.

### 이름 연쇄 변경이 시험까지 안 내려가고 있었다

강종을 붙이면서 실측으로 드러났다. `rename_descendants` 가 **시편에서 멈춰**
있었다 — 재료 이름을 바꾸면 시험만 옛 이름을 달고 있었고, 재료 수정 창은
*"시편·시험 이름이 전부 따라 바뀝니다"* 라고 약속하고 있었다.

기준정보와 무관한 기존 결함인데, 강종 축이 그 경로를 처음으로 실제로 밟아서 잡혔다.

### 분류는 사슬이다 — 축에 부모를 선언한다

Family·Category·Grade 를 평평한 세 축으로 두면 `Polymer + PP + SECC` 조합을
아무도 안 막는다. 그리고 강종이 수만 개일 때 **피커가 전체를 보여 준다** — Steel
을 골랐으면 후보가 수천으로 줄어야 한다.

실측이 계층을 뒷받침했다. 개발 DB 의 강종 86종 중 두 분류에 걸친 것은 **하나**
뿐이고, 그것도 쓰레기 분류(`Family/Category`)에 붙은 것이다. 실사용에서 강종 →
분류는 함수다.

```
vocabularies.parent_slug        축 수준의 계약   category 의 부모는 family
vocabulary_terms.parent_term_id 값의 부모        SECC 의 부모는 Steel
```

**계약을 축에 둔다.** 값마다 "이건 어느 축의 부모냐" 를 물으면 같은 답을 수만 번
저장하는 셈이고, 잘못된 축을 가리키는 값이 생긴다.

세 가지가 따라온다.

1. **피커가 좁힌다.** 규모에서 가장 큰 이득이다.
2. **새 값이 부모를 물려받는다.** Metal/Steel 을 고른 상태에서 `DP980` 을
   추가하면 부모가 `Steel` 로 붙는다 — **계층이 쓰면서 저절로 만들어진다.**
   관리자가 수만 개를 미리 잇는 일은 아무도 안 한다.
3. **부모는 비어 있어도 된다.** 부모 없는 값은 좁힌 목록에도 **함께 보여 준다** —
   초기에는 대부분 비어 있고, 감추면 좁히기를 켠 순간 아무것도 안 보인다.

백필은 데이터에서 부모를 추론한다(값마다 그 값을 쓰는 재료의 상위 분류). 갈리는
것은 **잇지 않는다** — 어느 쪽이 맞는지는 마이그레이션이 정할 일이 아니다.
개발 DB 에서 강종 85종이 이어졌고 `SECC` 하나가 갈려 로그로 남았다.

### 승인 대기 상태를 두지 않는다

`open` 축에서 사용자가 추가한 값은 **즉시 활성**이다. 승인을 기다리게 하면
피커가 멈추고, 그러면 사람은 시스템 밖에서 일한다. ReportArchive 가 같은 판단을
했고 이유를 적어 뒀다 — *"it would block the picker UX and the dataset is small
enough to clean up periodically."*

드리프트는 관리 화면의 병합으로 사후에 정리한다.

## 대안

**정규화만 한다.** 싸고 오늘 당장 값어치가 있다. 그러나 사람이 일부러 다르게 적은
표기를 못 잡고, 소급 병합이 일괄 치환이 된다. → 기준정보의 **일부**로 흡수했다.

**문자열 + 저장 시 resolve.** 마이그레이션이 작고 통계·카드 경로를 안 건드린다.
기준정보가 열 몇 개면 이쪽이 맞다. 수만 개라는 전제에서 탈락.

**ReportArchive 를 통째로 이식.** 온톨로지(객체 분류·시간 차원·관계 그래프)와
임베딩 기반 유사도(L1)까지 있다. 그건 보고서에 N축 태깅을 하는 시스템의 것이고,
물성의 1:1 속성에는 과하다. 병합 후보는 **L0(결정적 정규화 그룹핑)만** 가져온다.

## 결과

**얻는 것**

- 오타가 새 값이 되는 것이 구조적으로 불가능해진다(closed 축)
- 두 표기를 묶는 것이 `UPDATE` 한 문장이다
- 분류 목록이 재료 수와 무관해진다 — 지금은 화면을 열 때마다 전체를 `GROUP BY` 한다
- 제조사 섞임 경고가 문자열 흔들림에 안 속는다

**잃는 것 / 감수하는 것**

- 변경량이 크다. 축 11개 × (모델·마이그레이션·백필·폼·목록·필터)
- 백필에서 정규화 충돌이 나면 사람이 봐야 한다 — 운영 DB 사본에서 리허설한다
- `grade` 기준정보 값 이름 변경이 재료 이름 연쇄 변경을 부른다

**되돌릴 수 있게 한다.** 한 번에 바꾸지 않는다:

```
Expand   기준정보 표 + nullable FK 추가. 문자열 컬럼 유지, 쓰기는 양쪽에
Backfill 문자열 → term 생성 + FK 채움. 충돌은 로그
Contract 읽기를 FK 로 전환 → 한 릴리스 검증 → 문자열 컬럼 DROP
```

운영에 이미 배포한 뒤라 각 단계마다 롤백할 데가 있어야 한다.

`operator`(시험자)는 기준정보로 안 만든다. 시험을 돌린 사람이 **시스템 계정이 없을
수 있고**(협력사·타 부서), 계정과 이을지도 정해지지 않았다. 집계 축으로 쓸 계획이
없으면 기준정보를 만드는 비용이 더 크다.

`grade` 가 가장 크고 이득도 가장 크다. 지금은 `SECC`/`secc`/`S.E.C.C` 가 **서로
다른 재료 세 개**를 만든다.

## 단계

### 0단계 — 규모 대응 (v0.5.0 ✔)

기준정보와 독립이고 지금도 이득이라 먼저 했다. `pg_trgm` 인덱스, 검색 대상 정리,
피커의 서버 검색 모드. 실측은 아래 「실측」 절.

### 1단계 — 기준정보 3표 + 제조사 하나 (v0.6.0 ✔)

**축 하나로 전 경로를 관통한다.** 모델·마이그레이션·백필·폼·목록·통계 경고를
한 번씩 지나므로, 막히는 것이 있으면 나머지 열 축에 반복되기 전에 잡힌다.

제조사를 고른 이유: 작고, v0.4.0 의 섞임 경고가 이미 그 입력에 걸려 있어
**검증이 저절로 된다**(문자열 비교라 헛경고를 냈다).

곁들여: 관리 화면(값 고치기·감추기)을 4단계에서 당겨 왔다 — 기준정보를 켜 두고 고칠
데가 없으면 오타가 값이 되고, 그것을 고르는 다음 사람이 생긴다.

### 2단계 — 나머지 축

한 커밋에 다 넣으면 실패했을 때 어디가 문제인지 못 가린다. 넷으로 나눈다.

**2-1 (v0.7.0 ✔)** — `vendor`·`sales_type`·`specimen_standard`·`instrument`.
제조사와 같은 모양이라 위험이 낮다. 여기서 **바인딩 표**를 도입했다 —
`SAMPLE_BINDINGS` 같은 상수에 (축, 필드, FK 컬럼) 을 적고 라우트·`recount`·
`rename` 이 그것을 훑는다. 축마다 코드를 베끼면 그중 하나만 고쳐지는 날이 온다.

**2-2 (v0.8.0 ✔)** — `grade`. 혼자 한 덩어리다. 값 이름을 고치면 재료·시료·
시편·시험 이름이 전부 다시 만들어진다.

그 뒤처리를 **기준정보 모듈이 하면 안 된다** — 기준정보가 재료 서비스를 부르는 순간
모듈이 서로를 부르게 되고(`tests/architecture` 가 막는다), 축이 늘 때마다 기준정보가
새 도메인을 알아야 한다. 그래서 `shared/vocabulary_hooks.py` 에 훅 표를 두고
**쓰는 쪽이 자기 뒤처리를 등록한다.** 기준정보는 "이 축의 값이 바뀌었다" 만 알린다.

백필은 **표기를 바꾸지 않는다.** 정규화가 강종을 고치면 그 재료의 이름이 바뀌고
파급을 마이그레이션이 조용히 결정하는 셈이다. 표기가 갈린 것은 로그로 말하고,
정리는 관리자가 이름 변경으로 한다(연쇄 변경이 함께 돈다).

**2-3 (v0.9.0 ✔)** — `family`·`category`, 그리고 **계층**. `grade` 는 `record_name` 을 만드는 값이라 (ADR 0004) 기준정보 값 이름 변경이 재료
이름 연쇄 변경을 부른다 — 그 경로를 함께 잇고, 관리 화면이 "재료 N개와 그 아래
시료·시편·시험 이름이 전부 바뀝니다" 라고 말해야 한다.

**2-4 (v1.5.0 ✔)** — `product`·`part`(적용 제품·부위). 2단계의 마지막.

**부위를 제품 아래에 두지 않았다.** 계층은 값 하나에 부모 하나인데(`grade` 의
부모가 `category` 하나이듯) `이너 패널` 은 도어에도 후드에도 쓰인다. 붙이면 먼저
들어온 제품이 이기고 나머지는 조용히 틀린 곳에 매달린다 — 아무도 안 보는 곳에서
틀리는 쪽이 안 잇는 것보다 나쁘다.

백필의 잇는 방식을 바꿨다. 2-1 은 값을 `compare_key`(파이썬)로 만들고 잇기는
SQL `lower(btrim())` 으로 했는데, 그 둘은 같지 않다(NFKC·제로폭·연속 공백) —
눈에 안 보이는 문자가 든 값이 안 이어지고 경고만 남았다. **만든 키로 그대로
잇는다.**

### 3단계 — 별칭 · 병합 · 후보 탐지 (v1.0.0 ✔)

- 별칭 CRUD (관리 화면). **예방이다** — 등록해 두면 값을 만들 때 게이트가
  별칭까지 뒤져서 애초에 중복이 안 생긴다
- 병합: 참조를 옮기고 **없어진 표기를 별칭으로 등록**한다. 병합이 일회성 청소가
  아니라 규칙이 되는 지점. 자식들의 부모도 함께 옮긴다 — 부모가 사라지면 계층이
  끊긴다. 같은 축 안에서만 — 축을 넘는 병합은 값을 합치는 것이 아니라 **뜻을
  바꾸는 것**이다
- 후보 탐지 L0(구두점까지 지우는 강한 정규화로 그룹핑) + 기각 기록 + 사용 건수로
  생존값 추천. **임베딩(L1)은 안 가져온다** — 인프라가 없다
- **부모 편집.** 백필이 못 이은 값(부모가 갈렸던 것)을 사람이 정하는 자리다. 이게
  없으면 마이그레이션이 경고만 남기고 아무도 못 고친다 — 실제로 `SECC` 가 그
  상태였다
- 병합 기록(`vocabulary_merges`)은 스냅샷이다. 되돌리기는 안 한다 — 되돌리려면
  참조를 다시 갈라야 하는데 어느 행이 어느 쪽이었는지 알 수 없다. 다만 "무엇을
  무엇으로 합쳤나" 는 답할 수 있어야 한다

### 4단계 — Contract

`Expand → Backfill → Contract` 의 마지막. 둘로 나눈다.

**4-1 (v1.6.0 ✔)** — 어긋남 점검 + SQL 읽기를 FK 로.

**점검이 먼저다.** ADR 은 "읽기를 FK 로 → 한 릴리스 검증 → DROP" 이라고 썼는데,
검증할 도구가 없었다. 두 벌이 벌어져도 아무도 몰랐다 — 오늘 0 인 것도 스크립트를
따로 써서야 알았다.

만들자마자 개발 DB 에서 2건을 찾았고, 그것이 **결함 하나를 드러냈다.** 기준정보 값
이름을 고치면 재료·시료·시편·시험 이름 넷은 전부 따라 바뀌는데 **정작 그 값
자신은 옛 표기 그대로**였다. API 는 200 을 냈다.

원인은 `rename()` 의 `db.expire_all()` 이다. 이 세션은 `autoflush=False` 라
아직 안 쓴 `term.value` 변경이 세션에 남아 있고, `expire_all()` 이 그것을 버린다.
원시 SQL 로 쓴 문자열 컬럼만 살아남는다. `merge()` 는 `flush()` 를 먼저 해서
멀쩡했다 — **같은 함수 안에서 한 곳만 순서가 틀렸다.** 세 곳을 `_resync()` 하나로
묶어 순서를 잊을 수 없게 했다.

기존 시험이 못 잡은 이유: 재료 이름 넷이 따라오는 것만 봤지 **값 자신을 안 봤다.**

**읽기 전환의 모양이 정해져 있다.** 상관 서브쿼리로 쓰면 안 된다.

```sql
-- 안 된다: 인덱스 조건이 아니라 필터로 강등돼 BitmapOr 에 못 낀다
family_term_id IN (SELECT id FROM vocabulary_terms WHERE normalized ILIKE '%x%')
-- 된다: 값이 박힌 IN 은 btree 인덱스를 타고 다른 trgm 가지와 비트맵으로 묶인다
family_term_id IN ('...uuid...', '...uuid...')
```

좁은 검색(4건 일치)이 0.08ms → 90ms 로 갔다. **같은 함정에 세 번째다**(0단계의
6개 OR, 피커의 값+별칭 OR). `UNION` 도 시도했는데 더 나빴다 — `IN (UNION ...)`
이 머티리얼라이즈를 부른다(0.08→17ms, 나머지는 전부 40ms 대).

**축으로 좁히는 것이 이득의 전부다.** `materials.family` 는 5만 행인데 값은
5가지고, 기준정보 쪽 `family` 축은 5행이다. 그런데 `vocabularies` 와 조인해서
`slug IN (...)` 로 쓰면 플래너가 축 제한을 나중에 걸고 기준정보 23만 행을 훑는다 —
좁히려고 넣은 조건이 안 듣는다. **축 id 를 먼저 받아야 한다.**

    조인으로 축 좁히기   84ms
    축 id 를 먼저 받기   0.02ms   (2글자 검색어, trgm 을 못 타는 최악)

**4-1b (v1.7.0 ✔)** — 점검을 워커가 돌린다.

4-1 을 내고 보니 게이트에 구멍이 있었다. **점검이 사람이 누를 때만 돈다.** 그러면
일주일 뒤에 "계속 0이었나" 에 답할 수가 없다 — 눌렀을 때만 0 이었는지 내내
0 이었는지 알 방법이 없다. **지켜보는 게이트가 아니면 게이트가 아니다.**

그래서 셋을 더했다.

* 주기 작업(`app/jobs/schedule.py`). 지금까지 작업은 전부 요청이 넣었는데
  (업로드하면 파싱, 가입하면 알림) 저절로 돌아야 하는 것이 처음 생겼다. **메모리에
  시각을 안 들고 있는다** — 워커는 콘솔 앱이라 자주 껐다 켜지고, 메모리에 두면
  하루에 열 번 켠 날 열 번 돈다. 큐에 마지막으로 넣은 시각이 곧 상태다
* 점검 기록(`vocabulary_drift_checks`). `clean_since`·`clean_checks` 가 "언제부터
  몇 번 연속 0" 을 답한다. 한 번이라도 벌어지면 **거기서 다시 센다** — 고쳤더라도
  "내내 0 이었다" 는 더 이상 참이 아니다
* `GET` 은 기록을 읽고 `POST` 가 새로 잰다. 화면을 열 때마다 새로 재면 이력이
  **사람이 창을 연 횟수**가 되고, 게이트가 묻는 것이 그게 아니다

**`now()` 가 아니라 `clock_timestamp()` 다.** 포스트그레스의 `now()` 는 트랜잭션
시작 시각이라 한 트랜잭션에 넣은 두 줄이 같은 시각을 받는다. 고치기는 한 번에 두
줄을 남기므로(고치기 전·후) 순서가 사라지고 "마지막 점검" 도 "언제부터 0" 도 답이
틀린다. 시험이 잡았다.

**4-2 (다음)** — 문자열 컬럼 DROP.

조건은 하나다: **`clean_since` 가 한 릴리스를 덮는다.** 파이썬 속성
(`material.family`)은 관계를 읽는 프로퍼티로 바꾸고, `family`·`category` 의 trgm
인덱스도 함께 지운다(지금은 아무도 안 본다).

## 규모 대응 (이 결정과 함께 가는 것)

기준정보를 FK 로 올려도 **재료 검색은 그대로 느리다.** 별개로 해야 한다.

- `pg_trgm` + GIN 인덱스 — `ilike '%낱말%'` 이 인덱스를 타게 한다. 없으면 1만
  건에서 이미 체감된다
- 피커를 **서버 검색**으로 — 기준정보 2만 개를 브라우저로 보내지 않는다
- `usage_count` 캐시 — "쓰이는 분류만" 을 매번 `count(join)` 하면 풀스캔이다
- 「전체 보기」의 2000건 상한 — **걸리면 화면이 말한다**(v1.4.0 ✔). 재료·시험·기준정보
  목록 셋 다 몇 건에서 멈췄는지 적는다. 조용히 자르면 "다 봤다" 로 읽힌다

성능 목표는 재료 5만 + 기준정보 2만 합성 데이터에서 **목록 첫 페이지 300ms, 피커
검색 150ms**.

### 실측 — 4-1단계 Contract (합성 5만 건 + 기준정보 23만, `matnexus_bench`)

**보내는 코드로 쟀다.** 엔드포인트가 실제로 하는 일(첫 쪽 50건 + 총계) 기준.

| 검색어 | 맞는 행 | 문자열(옛) | 기준정보 FK(새) | |
|---|---|---|---|---|
| Metal | 10,055 | 24.3ms | **8.5ms** | ×0.3 |
| Zirconia | 5,114 | 14.4ms | 15.7ms | ×1.1 |
| DP368 (이름) | 4 | 1.3ms | 3.0ms | ×2.3 |
| PU (2글자) | 4,902 | 132.6ms | **73.9ms** | ×0.6 |
| Metal Zirconia | 0 | 141.9ms | 118.9ms | ×0.8 |

목표 300ms 안에 전부 든다. 두 낱말 검색이 양쪽 다 100ms 대인데, 이건 Contract 가
만든 것이 아니라 원래 그랬다(`count(*)` 가 지배한다). 고치려면 별도 작업이다.

목록 첫 쪽은 0.04→0.33ms(×8), 분류 집계는 17→47ms(×2.7). 배수는 크지만 절대값이
작고, 둘 다 조인 하나 값이다.

### 실측 — 0단계 (합성 5만 건, `matnexus_bench`)

| | 인덱스 전 | trgm + 검색 4개 컬럼 |
|---|---|---|
| 검색 1낱말 (SECC, 4674건) | 목록 92 + 개수 116 = **208ms** | 69 + 5 = **75ms** |
| 검색 2낱말 (DP 양산, 717건) | 27 + 122 = **149ms** | 20 + 92 = **112ms** |
| 검색 한글 (별칭, 5만건 전부) | 1 + 72 = **73ms** | 1 + 76 = **77ms** |
| 분류 목록 GROUP BY | **11ms** (17조합) | 11ms |

**배운 것 셋.**

1. **`OR` 가지 하나가 색인이 없으면 나머지 인덱스가 전부 무의미하다.** 처음에
   `record_name`·`alias` 둘만 색인했더니 208 → 214ms 로 **아무 변화가 없었다.**
   실행 계획을 보고서야 알았다 — 여섯 컬럼 OR 중 넷이 색인이 없어 Seq Scan.
   검색 대상을 넷으로 줄이고 그 전부를 색인하자 118ms → 4.6ms(25배).

2. **개수 세기가 목록보다 비싸다.** 목록은 `LIMIT 50` 에서 멈추지만 `count(*)`
   는 끝까지 센다. 그리고 그 비용은 행 수에 정비례한다.

### 실측 — 피커 (합성 기준정보 23만, `matnexus_bench`)

| 검색어 | `OR` | `UNION` |
|---|---|---|
| 네 글자 `secc` (많이 맞음) | 124ms | 126ms |
| 한글 `포스코` | 109ms | **71ms** |
| 여섯 글자 `secc12` | 94ms | **1.1ms** |
| 여덟 글자 `secc1234` | 97ms | **0.4ms** |

**같은 함정을 두 번째로 밟았다.** 값과 별칭을 `OR` 로 묶으면 별칭 가지가 값 표의
인덱스로 못 좁혀서 **전체를 훑는다.** `UNION` 으로 나누면 가지마다 자기 trigram
인덱스를 탄다.

30,000개에서는 21ms 대 24ms 로 **차이가 안 보였다** — 순차 훑기가 그 크기에서는
싸기 때문이다. 실행 계획을 안 봤으면 "충분히 빠르다" 로 넘어갔을 것이고, 기준정보가
20만이 된 뒤에 느려졌을 것이다. **시간이 아니라 계획을 봐야 한다.**

검색어가 짧으면(`secc`) 둘 다 느리다. 이건 인덱스로 못 푼다 — 표의 절반이 맞는
검색은 그만큼 읽어야 한다. 화면이 디바운스 200ms 를 두는 이유이기도 하다.

3. **상한 있는 개수(`LIMIT 1001` 후 세기)는 안 넣었다.** 재 보니 득실이 갈린다 —
   비선별 검색은 70 → 2ms 로 좋아지는데 **선별적 검색은 5 → 20ms 로 나빠진다.**
   흔한 쪽이 후자다. 5만 건에서 최악이 112ms 로 목표 안이므로 복잡도를 안 늘린다.
   재료가 50만을 넘으면 다시 잰다.

## 값이 속성을 갖는다 — 시편 규격 (2026-08-22, v1.30.0)

**규격은 이름이 아니라 치수 한 벌이다.** `ASTM E8 subsize` 는 게이지 길이 25 mm ·
평행부 폭 6 mm 를 뜻한다. 그걸 어디에도 안 적어 두면 사람이 규격서를 펴 놓고
시편마다 옮겨 적고, 그러다 한 건이 틀리면 응력이 통째로 어긋나는데 숫자는
그럴듯해 보인다.

### 처음에는 시험 종류에 매달았다 — 틀렸다

v1.28.0 은 치수 칸을 시험 종류가 선언하게 했다(인장 칸 7개, DMA 칸 5개). 쓰기
전에 물어서 다행이었다: *"인장시험도 시편 종류에 따라서 property 가 바뀌는 거
아닌가?"*

**바뀐다.** 실측으로 확인한 것:

  - **DMA 실파일 172개 전부**에 장비가 적은 `Geometry name` 이 `Length`·`Width`·
    `Thickness` 바로 옆에 있고, 155개가 `3 Point Bending Clamp` 였다. TA 장비의
    "Geometry" 가 곧 시편 홀더 구성이고 그것이 필요한 치수를 정한다 — 3점 굽힘은
    지지 간격이 필요하고 인장 필름 클램프는 필요 없다.
  - Zwick `.tra` 가 주는 것은 `a0`(두께)·`b0`(폭) 로 **평판형**이다. 환봉형은
    `d0`(직경) 하나이고 폭·두께가 아예 없다. ASTM E8 은 sheet·plate·round 를
    한 규격 안에 담는다.
  - 방증: `specimens` 표에는 지금도 직경 컬럼이 없다. **66 은 환봉 시편을
    표현하지 못한다** — 이 구멍은 이번에 생긴 것이 아니라 원래 있었다.
  - 65 는 참고가 안 됐다. 시편 치수를 아예 안 들고 `initial_gauge_length_m` 과
    `initial_cross_section_area_m2` 둘뿐이며 DMA 는 그마저 금지한다. 문제를 푼
    것이 아니라 피했다.

로컬 `.mtet` 107개가 전부 평판(`a0`/`b0`)인 것은 표본이 좁아서지 환봉이 없어서가
아니다.

### 결정 — 두 층

    시편 분류 (기준정보 축)   그 분류의 규격이면 **예외 없이** 갖는 기본 칸
    시편 규격 (그 아래 값)    거기에 **자기만의 칸**을 더한다

    vocabularies.attribute_source   `parent` — 기본 칸을 상위 값이 갖는다
    vocabulary_terms.parent_term_id 규격 → 분류 (축 계층 기계 그대로)
    vocabulary_terms.extra_fields   이 규격만의 칸
    vocabulary_terms.attributes     치수. **언제나 SI**
    specimen_fields                 분류가 선언한 기본 칸

**분류는 규격의 상위 값이다.** `grade` 의 부모가 `category` 인 것과 같은 기계를
쓴다 — v1.28.0 의 `kind` 컬럼은 같은 것을 두 방식으로 표현하는 것이라 지웠다.

칸을 읽는 규칙은 하나다.

    이 값이 직접 선언한 칸  +  상위가 선언한 칸  +  이 값의 추가 칸

분류는 첫째만, 규격은 둘째·셋째만 갖는다. 규칙을 갈라 두면 "이 값은 어느
쪽이냐" 를 부르는 곳마다 물어야 한다.

### 왜 형상 축이 아닌가

"평판형·환봉형" 같은 **형상**을 축으로 두는 안도 있었다. 쓰는 사람이 고른 것은
**분류**다 — 형상은 규격이 이미 함축하고 있고(`ASTM E8 R1` 은 환봉이다), 축을
하나 더 만들면 규격을 적을 때마다 형상까지 고르게 된다. 대신 분류의 기본 칸을
**최소로** 두고(인장은 게이지 길이·전체 길이뿐) 나머지는 규격이 더한다.

### 대안

**(가) 축을 둘로 나눈다**(`tensile_specimen_standard` · `dma_…`). "시편 규격"
이라는 개념이 둘이 되고, 시편 폼에서 어느 축을 물을지를 매번 정해야 한다.

**(나) 고정된 칸 목록 하나.** 절반이 늘 비고, 그 빈 칸이 "안 쟀다" 인지 "이
규격에 없는 값" 인지 **구별되지 않는다.**

**(다) 자유 JSON.** 오타 하나가 조용히 새 속성이 되고 아무도 못 찾는다.

### 지키는 것

- 스키마 밖의 키·숫자 아닌 값·0 이하·빈 필수 칸은 **서버가 거절한다.**
- **분류의 기본 칸과 같은 키는 규격이 못 쓴다** — 같은 키가 둘이면 어느 쪽이
  이기는지 사람이 알 방법이 없다.
- **값을 만들 때는 치수를 요구하지 않는다.** 치수를 모른 채 규격 이름부터 적는
  일이 실제로 있고, 그때 필수 칸을 요구하면 피커가 막힌다.
- **이미 있는 값의 치수를 덮어쓰지 않는다.** 피커는 이름만 치고 낙관적으로
  보낸다.
- **뺀 칸의 값은 안 지운다.** 스키마 밖이 되어 화면에서 사라질 뿐이고, 칸을
  되살리면 다시 보인다.
- **키는 계약이다.** 저장된 칸의 키는 화면에서 잠근다 — 이미 그 키로 치수가
  들어 있다.

## 시편이 규격에서 치수를 물려받는다 (v1.31.0)

    specimens.dimensions            이 시편에서 **잰** 값. SI. `{키: 값}`
    vocabulary_terms.cross_section  이 규격의 단면적 식(`circle`·`rectangle`…)

### 규칙 — 빈 칸만 채운다

    시편에 값이 있다   그 값을 쓴다        ← 사람이 실제로 잰 것
    시편이 비었다      규격의 공칭을 쓴다

**규격이 잰 값을 조용히 덮으면 안 된다.** 장비 파일의 치수를 시편에 채울 때와
같은 규칙이다 — 덮어쓰면 "이 두께가 실측인가 규격값인가" 를 나중에 답할 수 없다.

그래서 **규격의 공칭을 시편 행에 복사하지도 않는다.** 복사하면 그 순간 둘이 같아
보이고, 규격을 고쳐도 시편은 옛 값을 든 채 남는다. 실효 값은 읽을 때 합친다
(`app/shared/specimen_size.py`), 화면은 둘을 나란히 받는다 — 잰 값은 칸 안에,
공칭은 빈 칸의 흐린 자리표시로.

`gauge_length_m`·`width_m`·`thickness_m` 은 아직 함께 적는다(Expand). 읽는 쪽은
`dimensions` 를 먼저 보고, 없으면 옛 컬럼을 실측으로 친다.

### 단면적은 규격이 고른 식으로 낸다

`specimens` 에 직경이 없어서 환봉을 못 담던 문제가 여기서 풀린다. 칸은 규격이
정하므로(`ASTM E8 R1` 에는 직경 칸이 있다) 시편은 그 칸을 채우기만 하면 된다.

식은 계산이라 `matcore/specimen.py` 의 표에 있다 — 정의는 데이터, 계산은
플러그인(D7). 규격은 그 표의 **키**를 고른다.

    rectangle  폭 곱하기 두께      needs: width, thickness
    circle     원                  needs: diameter
    tube       고리                needs: outer_diameter, inner_diameter
    manual     사람이 잰 단면적    needs: area

**왜 시편 분류가 아니라 규격이 고르는가.** 분류에 두면 "인장 평판"·"인장 환봉"
처럼 분류를 모양별로 쪼개야 한다. 규격은 이미 자기 칸을 갖고 있어서, 식이 요구
하는 칸이 거기 있는지 **서버가 검사할 수 있다** — 없으면 고르는 자리에서
거절한다. 골라 봐야 늘 실패하고, 그러면 사람은 그 이유를 처리 화면에서 만난다.

### 지키는 것

- **어림값을 만들지 않는다.** 값이 모자라면 단면적은 `None` 이고, 무엇이 없는지
  말한다. 12.5 mm 환봉은 122.7 mm² 인데 평판 식으로 낸 수는 오류 없이 그럴듯한
  다른 값이고, 그 수로 나눈 응력은 자릿수째로 어긋난다.
- **0 을 안 받는다.** '쟀는데 0' 과 '안 쟀다' 는 다르다 — 안 쟀으면 칸을 비운다.
  0 으로 나눈 응력은 무한대다.
- **식을 안 고른 규격은 옛 규칙(폭 곱하기 두께)으로 돈다.** 지금까지 그렇게 돌던
  시편이 갑자기 못 돌면 안 된다.
- **규격에서 사라진 칸도 값이 남아 있으면 화면에 보인다.** 숨기면 지울 수 없는
  값이 된다.

## 규격표가 전제를 반증했다 (v1.32.0)

ASTM 인장시편 규격표와 DMA 시편 규격표를 이 스키마에 하나씩 대 봤다. 두 층
구조는 그대로 맞았지만 — ○/△/× 매트릭스가 곧 규격별 칸이다 — **세 가지가
틀렸다.**

### ① 기본 칸을 필수로 두면 안 된다

"그 분류의 규격이면 **예외 없이** 갖는다" 를 전제로 인장의 게이지 길이와 DMA 의
자유길이·폭·두께를 필수로 두었다. 그 전제가 깨진다.

    인장  D3039·D3518·D5766 은 게이지 길이를 시편에 새기지 않는다 — 그립 간
          거리가 곧 게이지다. D1708 은 표점 게이지를 두지 않고, D412 링은
          표점이 아니라 내부 원주로 초기 길이를 정의한다. D5083·D2290·D897·
          D2095 도 없다.

    DMA   자유길이·폭·두께 셋을 다 갖는 파트는 ISO 6721-4(인장) 하나뿐이다.
          -2·-3·-8·-10 은 자유길이가 없고, -6 전단·-10 평행판·-12 압축은 폭이
          없다(직경이다). ASTM D4065 는 "specimen size is not fixed by this
          practice" 라고 문장으로 못 박는다.

필수로 두면 그런 규격은 **저장 자체가 안 된다.** 기본 칸은 계속 두되 필수는
풀고(마이그레이션 `c3b71e94a0d2`), 필수 여부는 부서가 자기 규격을 보고 화면에서
정한다. 이 결함은 새 API 테스트를 쓰다가 우리 스스로 우회한 흔적으로 먼저
드러났다 — 테스트마다 게이지 길이를 채워 넣고 있었다.

### ② 치수가 길이만은 아니다

칸 편집 화면이 `dimension: 'length'` 로 박혀 있었고, 화면이 "길이만 다룹니다 —
다른 차원이 필요해지면 그때 늘립니다" 라고 적어 두었다. 그때가 왔다.

    각도    D3039 탭 베벨각 7° 또는 90°
    무차원  D5766 의 w/d, ISO 6721-10 의 D/d, ISO 6721-6 전단의 시편 2장
    면적    C1557 단섬유의 단면적 A, D897 접착면(면적이 정확히 1 in² 가 되도록
            직경을 1.129 in 로 정한 규격이다)

**면적이 특히 중요하다.** 단면적을 사람이 직접 재서 적는 칸(`manual` 단면 식)을
길이로 만들어 두면 화면이 mm 로 환산해 **10⁶ 배** 어긋난 값이 저장된다. 그래서
단위표에 `area` 차원을 더했다(`m2`·`mm2`·`cm2`, `mm²` 표기도 흡수).

차원과 저장 단위가 짝인지는 **서버가 검사한다** — 시험 종류 정의에서 이미 한
판단과 같다. 차원은 **단위표에 있는 것 전부**를 연다. 처음에는 길이·면적·각도·
무차원·질량 다섯으로 좁혔는데 좁힐 근거가 없었다 — 시편에 붙는 값이 그것으로
끝난다는 보장이 없고(ISO 6721-10 은 시료를 3~5 g 으로 준다), 좁혀 두면 필요해질
때마다 코드를 고쳐야 한다. 모르는 차원은 그대로 거절한다.

### ①-b 칸은 추가·수정·삭제가 다 돼야 한다

규격에서 칸을 지우고 저장한 뒤 다시 열면 **지운 칸이 되살아나 있었다.** 화면이
서버가 아니라 목록에서 들고 온 값 객체(`term.extra_fields`)에서 행을 만들었기
때문이다 — 그 객체는 저장 뒤에도 옛 값 그대로다. 이제 두 모드가 같은 식을 쓴다:
서버가 준 칸 중 **위에서 오지 않은 것**(`!inherited`).

그리고 **뺀 칸의 값이 다음 저장을 막고 있었다.** 값을 남기는 것은 의도인데
(칸을 되살리면 다시 보인다), 그 값이 스키마 밖이라고 `check_attributes` 가 422 를
내면 칸을 지운 사람이 그 규격에 아무것도 못 하게 된다. **이미 저장돼 있던 값과
같으면 통과시키고** 새로 들어온 스키마 밖 키만 거절한다 — 오타는 그대로 막힌다.

차원도 저장 뒤에 바꿀 수 있다. 대신 화면이 붉게 말한다 — **이미 적어 둔 숫자는
안 바뀌고 새 단위로 읽힌다.** 두께 0.001 을 면적으로 바꾸면 0.001 m² 가 된다.

### ③ 링은 단면이 둘이다

D412 Type 1·2 링과 D2290 스플릿디스크는 링을 두 핀에 걸어 당기므로 **하중이
걸리는 단면이 둘**이다. 평판 식으로 내면 면적이 절반이 되고 **강도가 두 배로
나온다** — 오류 없이. `ring` 식(폭 곱하기 두께 곱하기 2)을 표에 더했다.

## 칸이 숫자 말고도 담는다 (v1.33.0)

규격은 치수만 갖지 않는다.

    판(edition)   `D638-22`. ASTM 이 못 박는다 — *"규격 번호만으로는 부족하다.
                  판 연도와 시편 타입을 함께 지정해야 한다."* 판이 다르면 치수가
                  다르고, E8 과 E8M 은 환봉 게이지 길이가 4D 대 5D 라 **연신율을
                  직접 비교할 수 없다.**
    모드          이중 캔틸레버 · 3점 굽힘 · 전단 샌드위치 … **모드가 곧 시편
                  형상이다.** DMA 규격은 대개 치수를 안 정하고 모드만 정한 뒤
                  장비 클램프에 넘긴다.
    단부 형식     나사 · 숄더 · 평행 · 버튼헤드 (E8 환봉)

숫자 칸만 두면 이것들이 **값 이름에 섞인다.** 그러면 `D638 Type I` 과
`D638-22 Type I` 이 별개 값으로 갈리고, 애초에 풀려던 병이 되돌아온다.

    kind      number · text · choice
    choices   선택일 때 고를 값
    symbol    그 규격의 도면이 쓰는 글자

### 칸이 선언되는 자리가 하나 늘었다

    축이 선언     그 축의 값이면 무엇이든 갖는다     판(edition)
    분류가 선언   그 분류면 대개 갖는다             게이지 길이 · 모드
    값이 선언     그 값만 갖는다                    직경 · 단부 형식

**판을 왜 축에 두는가.** 분류마다 적으면 새 분류를 만들 때 빠뜨린다. 판은
인장이든 DMA 든 모든 규격이 갖는다 — `parent_slug`·`attribute_source` 를 축에
적는 것과 같은 판단이다(`vocabularies.base_fields`).

**모드를 왜 분류에 두는가.** DMA 규격이면 전부 갖는다. 그리고 모드를 안 적으면
그 시편이 무엇이었는지 나중에 알 수 없다 — 같은 규격·같은 재료라도 모드가
다르면 저장탄성률 절대값을 직접 비교할 수 없다.

**단부 형식을 왜 값에 두는가.** E8 환봉만 갖는다. 분류에 두면 평판 규격에도 빈
칸이 하나씩 쌓이고, 그 빈 칸이 "안 적었다" 인지 "이 규격에 없는 값" 인지
구별되지 않는다.

### 기호는 규격이 덮어쓴다

규격서와 도면은 뜻이 아니라 **글자**로 적혀 있고, 시편을 발주할 때 사람이 보는
것도 그 글자다. 그런데 **같은 글자가 규격마다 다른 뜻이다.**

    뜻              E8      D638            ISO 527-2
    게이지 길이     G       G               L₀
    전체 길이       L       LO              l₃
    직경            D       —               —
    그립 간 거리    —       D               L

`key` 는 **뜻**으로 짓는다(`diameter`·`grip_separation`) — 그래야 계산이 안
헷갈린다. 글자는 따로 담는다(`symbol`). 그리고 게이지 길이처럼 **분류가 선언한
칸의 글자는 규격마다 다르므로**, 규격이 `field_symbols` 로 덮어쓴다(실측이
공칭을 덮는 것과 같은 모양).

**글자로 값을 묶지는 않는다.** 계산이 잡는 것은 언제나 `key` 다 — `D` 로 묶으면
E8 의 직경과 D638 의 그립 간 거리가 같은 것이 된다.

### 시편 치수 화면은 숫자 칸만 그린다

판·모드는 **그 규격의 성질이지 이 시편을 잰 값이 아니다.** 시편 화면에 입력
칸으로 나오면 사람은 거기에 무엇을 적어야 하는지 알 수 없다.

## 규격이 비율 조건을 갖는다 (v1.34.0)

**규격이 치수를 안 주고 비만 주는 일이 흔하다.** DMA 시편 규격표에서 숫자를
실제로 주는 파트는 ISO 6721-2·-3·-10 셋뿐이고 나머지는 전부 비율이거나 장비
위임이다. 그 비를 담지 못하면 그런 규격은 이름만 남은 빈 껍데기가 된다.

    ISO 6721-3   L/h ≥ 50        저장탄성률 ±5 % 정확도 확보
    ISO 6721-4   Lₐ/b > 6        클램프의 횡수축 구속 영향 배제
    ISO 6721-6   h/L > 4         굽힘 성분 기여를 무시할 수준으로
    ISO 6721-12  h/D 1–2         프리로드 하 좌굴·배럴링 방지
    ISO 6721-10  D/d 10–50
    ASTM D7028   스팬/두께 > 10   전단 변형 기여 억제
    ISO 4664-1   변/두께 ≥ 4     단순 전단 상태·균일 가황

규격표에 나오는 것이 **전부 두 치수의 비**라, 규칙 하나가 `분자 칸 ÷ 분모 칸` 과
`최소·최대`다(`vocabulary_terms.ratio_checks`). 판정은 시편의 **실효 치수**로
한다 — 실측이 이기고 빈 칸은 규격의 공칭이다.

### 어겼다고 막지 않는다

**ISO 6721-4 는 클램프 간 50–100 mm 를 권하는데 어느 장비도 못 맞춘다** —
Netzsch 15 mm · Mettler 20 mm · TA 30 mm. 규격 조건을 저장 조건으로 쓰면 실제로
잰 데이터를 시스템에 못 넣게 되고, 그러면 사람은 시스템 밖에서 일한다(축 입력
정책을 `closed` 로 안 켠 것과 같은 판단).

대신 **어긴 채로 쟀다는 것이 눈에 보여야 한다.** 규격 번호만 적힌 보고서는
재현이 안 된다 — 그 문서가 직접 권고하는 바이기도 하다: *"규격 번호만이 아니라
모드·스팬·시편 치수·조임 토크를 함께 적어야 재현이 가능하다."*

### 못 잰 것과 어긴 것은 다르다

값이 없으면 **판정하지 않는다.** 없는 값을 0 으로 치면 모든 조건이 어긴 것으로
보이고, 그러면 경고가 소음이 된다 — 소음이 된 경고는 아무도 안 읽는다.

### 안 담기로 한 것

**파생 치수**(`G = 4D/5D`, `S = 16h`)는 사람이 규격서 값을 옮겨 적는다. 식을
데이터로 두면 요구 칸·순환 참조·재계산 시점을 다 정해야 하는데, E8 환봉 소형
4종처럼 표가 이미 있는 것은 그 값을 그대로 적으면 끝난다.

**공차**(`±0.2`, `±1 %`)도 안 담는다. **실측이 시편에 들어오기 때문이다** —
공칭을 이기는 값이 이미 있는데 공차를 또 두면 "그 값이 맞나" 를 묻는 두 번째
장부가 된다.

**한쪽 한계**(`R ≥ 25`, `오버행 ≥ 6.4`)도 안 담는다. 시편을 만들 때 지키는
것이지 데이터로 검사할 것이 아니다.

### 접힌 줄이 치수를 말한다 (v1.36.0)

접힌 줄은 두께·폭·게이지 셋을 **이름 없이** 늘어놓고 있었다(`1.0 / 12.5 / 50`).
환봉 시편은 거기서 `— / — / —` 로 보였다 — 직경을 갖고 있는데 "치수가 없다" 로
읽힌다.

이제 그 규격의 칸을 **전부**, **이름을 붙여** 적는다. 자리로 외울 수가 없기
때문이다 — 환봉 규격의 첫 값은 직경이고 평판 규격의 첫 값은 폭이다.

그리고 **규격에서 온 값은 흐리게** 그린다. 시편 화면이 이미 같은 규칙이다(빈
칸의 흐린 숫자가 공칭). 목록에서만 둘을 합쳐 보이면 사람은 전부 실측으로 읽고,
"이 두께가 잰 건가 규격값인가" 를 나중에 답할 수 없다.

**N+1 은 규격별 배치로 막는다**(`specimen_size.sizes_for`). 시편 하나의 치수를
알려면 규격 값과 그 분류의 기본 칸을 봐야 하는데, 한 시료의 시편은 대개 같은
규격이다 — 시편이 20개여도 규격이 2종이면 조회는 2종분이다.
