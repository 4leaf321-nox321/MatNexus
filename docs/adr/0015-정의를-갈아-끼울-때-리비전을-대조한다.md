# ADR 0015 — 정의를 갈아 끼울 때 리비전을 대조한다

- 상태: 채택 (v1.58.0)
- 관련: [ADR 0001](0001-오류만-엔벨로프.md) · [ADR 0007](0007-레시피는-가변-결과는-불변.md)

## 배경

계획서 Phase 2 목록에 ✗ 로 남아 있던 항목이다.

> **편집 잠금** — 코드에 `heartbeat`·`RevisionMismatch` **0건**. 지금은 혼자
> 써서 안 드러난다. 사람이 둘 되면 뒤에 저장한 쪽이 앞을 덮는다.

파일럿 부서로 가면 사람이 둘 이상 된다. 그리고 이 문제는 **v1.56.0 에 고친
`max_upload_bytes` 버그와 뿌리가 같다** — 화면이 받지 못한 값을 되돌려 보낼 수
없어 저장 한 번에 한도가 사라졌다. 관리자 둘이면 채널 정의 전체가 그렇게 된다.

## 결정

**`PUT /test-types/{key}` 와 `PUT /processing/recipes/{key}` 에만** 낙관적
잠금을 건다. 요청에 `expected_revision` 을 **필수**로 받고, 저장된 값과 다르면
409 로 거절한다. 저장에 성공하면 `revision` 을 1 올린다.

## 근거

### 왜 이 둘만인가

이 둘이 **정의를 한 벌 통째로 갈아 끼운다.** 뒤에 저장한 쪽이 앞을 덮는 것이
아니라 **자식(채널·조건·단계)까지 통째로 지운다.**

나머지 8개 변경 엔드포인트는 `PATCH` 이고 `exclude_unset` 을 쓴다 — **안 보낸
필드는 안 바뀐다.** 서로 다른 필드를 고치는 두 사람은 애초에 안 부딪히고, 같은
필드를 고치면 그건 덮어쓰기가 아니라 그냥 나중 값이다.

처음에는 재료·기준정보에도 걸려고 했다가 이 차이를 보고 좁혔다. **넓게 거는
것이 안전해 보이지만, 부딪히지 않는 자리에 건 잠금은 사람을 훈련시켜서
409 를 습관적으로 무시하게 만든다.**

### 임대(`heartbeat`)가 아니라 대조

계획서에는 `heartbeat` 로 적혀 있었다. 바꿨다.

| | 비관적 (임대) | **낙관적 (대조)** |
|---|---|---|
| 새로 생기는 상태 | 잠금 테이블 · 만료 · 워커 | 컬럼 하나 |
| 브라우저를 닫으면 | 만료까지 남이 못 고침 | 아무 일 없음 |
| 실패 시점 | 열 때 | 저장할 때 |

- 지금 문제는 *"둘이 동시에 편집하면 불편하다"* 가 아니라 **"조용히 지워진다"**
  다. 대조가 정확히 그것을 막는다
- 임대는 **살아 있는 상태**를 만든다. ADR 0007 이 *"화면은 늘 최신을 본다"* 로
  잡아 둔 결의 반대다
- 부서 하나에 관리자 두셋이다. 충돌이 잦지 않으므로 **막는 것보다 알아채는
  것**이 값이 크다

### `updated_at` 이 아니라 `revision`

`updated_at` 이 이미 있으니 그것을 쓰면 마이그레이션이 0 이다. **재 봤더니 못
쓴다**(2026-08-24).

    ① 처음                17:38:20.239452
    ② 자식(채널)만 바꿈     17:38:20.239452   ← 안 움직였다
    ③ 부모를 바꿈          17:38:20.265544

`onupdate=func.now()` 는 **부모 행이 더러울 때만** 걸린다. 채널 라벨만 고치는
것은 흔한 편집인데, 그때 `updated_at` 은 그대로다 — 그 위에 세운 잠금은
**바뀐 것을 안 바뀐 것으로 보고 통과시킨다.**

정수 리비전은 서비스가 **명시적으로** 올린다. 자동(ORM 이벤트)으로 만들 수도
있었지만, 그러면 *무엇이 바뀌면 올릴 것인가* 가 코드에서 안 보인다 — 자식만
바뀐 경우를 놓친 것이 `updated_at` 이 못 쓰게 된 이유다.

### 선택이 아니라 필수

선택으로 두면 안 보내는 클라이언트가 조용히 검사를 지나간다. **빠뜨린 것이
사고가 난 뒤에야 드러난다** — 이 저장소가 반복해서 데인 모양이다.

대가: 시험 13곳과 화면 2곳을 고쳤다. 매번 먼저 읽어야 하는데, **그게 실제
순서다** — 사람도 화면을 열어서 본 뒤 고친다.

### 거절 메시지가 무엇을 해야 하는지 말한다

```
409  MNX-TESTS-0030
이 시험 종류가 그사이 바뀌었습니다 (열었을 때 7, 지금 9).
홍길동 이 2026-08-24 17:30 에 고쳤습니다 — 감사 기록에서 무엇이 바뀌었는지
볼 수 있습니다. 새로 고쳐서 다시 여세요 — **지금 저장하면 그 변경이
지워집니다.** 이 정의는 한 벌 통째로 갈아 끼우므로 덮는 것이 아니라 지우는
것입니다.
```

**누가·언제를 감사 기록에서 가져온다**(v1.52.0). 409 만 던지면 사람은
새로고침하고 자기 작업을 **다시** 잃는다. 그리고 *"지금 저장하면 지워진다"* 를
적지 않으면, 새로고침 후 다시 저장하는 것이 맞다고 생각하게 된다.

## 결과

    마이그레이션    1개 (컬럼 2개, server_default="1")
    백엔드          app/shared/revision.py 109줄 + 라우트 2곳
    프론트          편집기 2곳
    시험            백엔드 6건 + 프론트 3건, 기존 13곳 수정

### 자동으로 못 하는 것을 시험이 지킨다

`test_자식만_바꿔도_리비전이_오른다` 가 핵심이다. 부모 필드를 하나도 안 건드리고
채널 라벨만 고쳤을 때 리비전이 오르는지 본다 — **`updated_at` 이 못 하던 바로 그
자리**이고, 앞으로 누가 `bump()` 를 자동화하려 들면 여기서 걸린다.

### 남은 것

- **화면이 409 를 특별히 다루지 않는다.** 서버가 적어 보낸 말이 그대로 뜨는데,
  그것으로 충분한지는 사람이 실제로 부딪혀 봐야 안다. "새로 열기" 단추를 붙일
  자리는 있다
- **`PATCH` 는 안 건다.** 위 근거대로다. 기준정보 이름 변경처럼 넓게 퍼지는
  것이 문제가 되면 그때 다시 본다 — 지금은 감사 기록이 두 번의 변경을 다 남긴다
- 부서에 관리자가 여럿인 상태로 **실제로 부딪혀 본 적이 없다.** 파일럿에서
  확인할 것
