# ADR 0003 — 윈도우 무도커 배포

- 상태: 채택 (2026-08-14)
- 관련: 개발계획 D2(GitHub 릴리스)·D9(콘솔 실행)·D11(출하 경로 먼저), §9.1 Day 0 설치

## 배경

도커를 쓰기 어려운 윈도우 서버가 대상이다. 52_DigitalTwinPortal 이 같은 제약에서
검증된 경로를 갖고 있어 그것을 이식하되, **원본에 없는 것과 원본이 틀린 것**이
리허설에서 드러났다.

## 결정

**1. 52의 골격을 따른다.** GitHub Actions(windows) → 코드 + SPA + wheel 번들 zip →
서버에서 `deploy.ps1`. `pip install --no-index --find-links=packages` 라 배포 중
네트워크를 쓰지 않는다. venv 는 앱 폴더 바깥(`_venvs`), 직전 버전은 `_prev`.

**2. 운영 데이터를 앱 폴더 바깥(`_data`)에 둔다 — 52와 다르다.**

52는 배포마다 `backend\uploads` 를 복사해 옮긴다. CAE 시험 데이터는 GB 단위이고
장비 파이프라인이 붙으면 계속 늘어나므로 그 방식은 성립하지 않는다. `_data\`에
`filestore`·`logs` 를 두고 `.env` 가 그 경로를 가리키면, 배포는 코드만 교체하고
데이터는 복사조차 하지 않는다. 백업 대상도 "DB + `_data`" 로 분명해진다.

**3. 폴더 교체는 `[System.IO.Directory]::Move` 로 한다 — 52의 잠재 결함 수정.**

실측: 앱이 떠 있는 상태에서 `Move-Item` 이 **부분 이동**을 해 `_prev` 에 복사본이
생기고 운영 폴더는 반쯤 지워진 상태로 남았다. `Directory.Move` 는 원자적 이름
변경이라 실패하면 아무것도 바뀌지 않는다.

**4. 잠금 탐지는 실제 연산으로 한다.** 52는 앱 루트에 파일을 써 보는데,
`run_server.ps1` 이 작업 디렉터리를 `backend` 로 옮기므로 **루트 쓰기는 성공하고
폴더 이동은 실패하는** 상태가 생긴다. 그래서 폴더 이름 바꾸기를 실제로 시험하고
되돌린다.

**5. Day 0 설치 절차를 새로 쓴다.** 52의 문서는 신규 구축을 명시적으로 제외하고,
65는 compose 한 줄이라 도커 없이 성립하지 않는다. `install.ps1` 이 환경 점검 →
코드 배치 → `_data` → `.env`(JWT 난수) → DB 생성 → 마이그레이션 → 설치 시드 →
방화벽을 멱등하게 수행한다.

## 리허설에서 드러난 것 (모두 반영됨)

| 증상 | 원인 | 대응 |
|---|---|---|
| `.ps1` 이 구문 오류로 멈춤 | PowerShell 5.1 은 BOM 없는 스크립트를 CP949 로 읽는다. 한글 주석이 깨지며 따옴표가 어긋남 | 모든 `.ps1` 을 UTF-8 BOM 으로. `tests/architecture/test_scripts_encoding.py` 가 검사 |
| 배포된 앱이 **개발 모드**로 뜸 | `Set-Content -Encoding utf8` 이 `.env` 에 BOM 을 붙여 첫 줄 `APP_ENV` 가 무시됨 | 읽기는 `utf-8-sig`, 쓰기는 BOM 없이. 회귀 테스트 추가 |
| 정상 설치가 실패로 뒤집힘 | `ErrorActionPreference='Stop'` 에서 alembic 의 stderr INFO 가 종료성 오류가 됨 | `Invoke-Native` 헬퍼 — 성공 여부를 종료 코드로만 판정 |
| 방화벽 실패인데 성공 로그 | CIM cmdlet 이 5.1에서 `Stop` 을 따르지 않음 | `-ErrorAction Stop` 명시 + 수동 명령 안내 출력 |
| 앱 프로세스가 폴더를 잡아 배포 실패 | 셸만 종료하고 앱 프로세스가 남음. venv python 은 `ExecutablePath` 가 기본 파이썬으로 보여 명령줄 필터에 안 잡힘 | 잠금 탐지가 먼저 막고, 원인 프로세스를 찾는 명령을 오류 메시지에 포함 |

## 대안

- **Apptainer SIF(RA 방식)**: 리눅스 전용이라 해당 없음.
- **윈도우 서비스 등록(NSSM)**: 반입물이 늘어 D9에서 콘솔 실행을 택했다. 승격해도
  바뀌는 것은 기동 방식뿐이라 나중에 결정해도 비용이 낮다.
- **배포마다 venv 재생성**: 40초가 매번 붙고 오프라인에서 이득이 없다. 해시 비교로
  requirements 가 바뀔 때만 다시 만든다.

## 결과

`scripts/ci/{package_deploy,run_server_template}.ps1`,
`scripts/deploy/{install,deploy,rollback,venv_sync,precheck}.ps1`,
`.github/workflows/{ci-windows,release-windows,auto-tag}.yml`.

리허설로 확인한 것: 신규 설치 → 기동 → 로그인 → 갱신 배포(5초, venv 재사용) →
앱 실행 중 배포 거부 → 롤백 → 재설치 멱등성.
