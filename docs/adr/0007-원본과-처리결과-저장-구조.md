# ADR 0007 — 원본과 처리 결과를 어떻게 관리하는가

- 상태: 채택
- 날짜: 2026-08-16
- 관련: ADR 0004(불변/가변 분리), ADR 0005(저장 전 시험)

## 결정

시험 데이터를 **5층**으로 둔다. 그중 가변은 **하나**뿐이다.

```
① 원본 파일     TestRun.storage_path        불변 ─ 장비가 준 것 그대로
② 측정 곡선     Curve                       불변 ─ 읽기의 결과. 다시 읽으면 새로
③ 처리 결과     ProcessingResult            불변 ─ 레시피의 결과. 여러 벌
                        ↑
④ 채택         TestRun.adopted_result_id   ★ 유일한 가변. 포인터 하나
                        ↓
⑤ 요약값       TestSummary                 ①과 ④의 투영. 장비 값과 나란히
```

규칙은 두 줄이다.

- ①②③ 은 **절대 덮어쓰지 않는다.** 다시 하면 새로 만든다.
- 바뀌는 것은 ④ **포인터 하나**뿐이다. ⑤ 는 파생이라 채택을 바꾸면 다시 만들어진다.

## 배경 — 무엇이 불명확했나

처리를 붙이고 나서 실제 DB 를 보니 이렇게 돼 있었다:

```
TestSummary  340행 — 전부 'instrument' (장비 값)
             'matnexus' 0행 ← 모델엔 있는데 아무도 안 씀
ProcessingResult 2행 — 우리가 계산한 값은 여기 JSONB 에만
```

세 가지가 어긋나 있었다.

**1. 저장된 결과가 전부 동등했다.** 돌릴 때마다 새 행이 쌓이는데, 그중 무엇이
"이 시험의 물성" 인지 아무 데도 안 적혀 있었다. 통계·비교·내보내기는 시험당 값
하나가 필요한데 고를 근거가 없었다.

**2. 같은 성격의 값이 두 곳에 있고 둘이 서로를 몰랐다.** `TestSummary.source` 를
`instrument`/`matnexus` 로 나눈 이유가 바로 그 비교였는데(모델 주석에 그렇게
적혀 있다), 처리가 그 자리를 안 쓰고 자기 JSONB 에만 값을 뒀다. 화면 아래
요약값 표에는 장비가 계산한 항복강도가, 처리 패널에는 우리가 계산한 항복강도가
있고 둘이 만나지 않았다.

**3. 화면이 세로로 이어졌다.** 정보 → 곡선 → 처리 → 요약값 순서라, 처리하는
동안 원본 곡선이 위로 사라지고 결과는 또 아래에 있었다.

## 대안

### A. 최신 결과가 곧 대표

포인터 없이 `created_at` 이 가장 늦은 것을 쓴다.

기각: **실험 삼아 마지막에 돌린 것이 대표가 된다.** 탄성 구간을 극단으로 넣어
보고 화면을 닫으면 그 값이 이 시험의 물성이 되고, 아무 표시도 남지 않는다.
이 프로젝트가 가장 비싸게 겪는 "조용히 틀린 성공" 계열이다.

### B. 저장이 곧 확정 (시험당 결과 하나)

저장하면 앞의 것을 덮어쓴다.

기각: **시행착오를 남길 수 없어 방법 간 비교가 불가능해진다.** 회귀로 잰 E 와
현으로 잰 E 를 나란히 두고 고르는 것이 이 도메인의 정상 작업이다. 게다가
덮어쓰기가 생기면 "예전 결과를 열었더니 값이 달라졌다" 가 가능해진다.

### C. 처리 결과를 `Curve` 로 저장 (`kind='processed'`)

별도 테이블 없이 곡선 테이블에 파생 곡선으로 넣는다.

기각: 곡선 목록이 **시도로 오염된다.** 곡선 선택기(종류 → 벌 → 축)는 "이 파일에
무슨 곡선이 있나" 를 답하는 자리인데, 여기에 시도 열두 벌이 섞이면 그 질문에
답할 수 없게 된다. 다만 Phase 3 의 곡선 비교가 측정 곡선과 처리 결과를 겹쳐
봐야 하므로, **"어느 곡선인가" 를 가리키는 공통 방법**은 그때 필요해진다.

### D. 명시적 채택 (채택안)

시도는 자유롭게 쌓이고, 대표는 사람이 한 번 정한다.

## 결과

### 얻은 것

| 질문 | 답하는 곳 |
|---|---|
| 이 시험의 항복강도는? | 채택된 결과 (`adopted_result_id`) |
| 장비 값과 얼마나 다른가? | 요약값 표에서 나란히 |
| 그 값은 어떻게 나왔나? | 결과의 단계 스냅샷 + 근거 |
| 다른 방법으로도 해 봤나? | 시도 목록에 그대로 |
| 20개 중 뭐가 남았나? | 목록의 `처리` 열 — 없음 / 시도 N / 채택됨 |

실제로 붙이자마자 값 하나가 드러났다. 같은 시험에서

    장비   proof_stress_02  159.98 MPa
    우리   proof_stress     249.5 MPa   (탄성 구간 R²=0.47)

56% 차이다. 나란히 두지 않았으면 둘 다 그럴듯해 보였을 것이다. **이 비교가
검증 장치라는 것이 `TestSummary.source` 를 나눈 원래 이유였고**, 이제야 그
설계가 실제로 작동한다.

### 구현상 걸린 것

**순환 FK 다.** `test_runs → processing_results → test_runs` 라 한쪽을 테이블
생성문 안에 넣으면 어느 것을 먼저 만들어도 상대가 없다. `use_alter=True` 로
별도 ALTER 에 미룬다. 이것 없이 만들었더니 `create_all` 은 통과하는데
`drop_all` 이 "없는 제약을 지우려" 해서 **테스트 DB 정리가 통째로 깨졌다.**

**요약값 투영은 갱신이 아니라 삭제 후 삽입이다.** 갱신으로 하면 예전 채택에만
있던 키가 남아 두 계산이 섞인 표가 된다 — 그 표는 그럴듯해 보인다.

### 화면 — 탭 셋

세로로 이어 붙이지 않는다.

```
원본 │ 처리 │ 결과 (N)
```

계획서의 워크벤치(`Data → Process → Stats → Fit → Export`)와 같은 구조라,
나중에 여러 시험을 다루는 워크벤치로 그대로 넓어진다.

### 곁가지로 바로잡은 것 — `processing` 을 진짜 모듈로

프론트에 `modules/processing` 을 만들자 경계 테스트가 잡았다: 백엔드에 같은
이름의 모듈이 없다(백엔드는 `tests/processing.py` 였다). 규칙대로 백엔드에도
`app/modules/processing/` 을 만들고, 모듈 간 직접 호출을 막는 규칙 때문에
공유 부분을 `shared` 로 올렸다:

- `shared/curvedata.py` — 저장된 곡선을 `matcore.Frame` 으로. 통계·적합·
  내보내기가 곧 같은 것을 필요로 한다. 각자 자기 버전을 가지면 "처리는 이
  단위로 읽는데 통계는 저 단위로 읽는" 어긋남이 생기고, 숫자로만 드러난다.
- `shared/permissions.visible_runs`·`get_run` — 시험 가시 범위. 재료 가시
  범위가 이미 거기 있는 것과 같은 이유다.

**검사가 없었으면 이 정리는 안 일어났다.** 65가 프론트 122파일 평면이 된 경로가
정확히 "규율상 가장 안전한 선택이 새 파일을 아무 데나 두는 것" 이었다.

### 남은 것 · 열려 있는 것

- **장비 키와 우리 키가 대응하지 않는다.** `proof_stress_02` 와 `proof_stress`
  는 같은 것을 뜻하지만 표에서 다른 줄에 선다. 나란히 놓고 차이를 보여 주려면
  키 대응표가 필요하다. 지금은 사람이 눈으로 찾는다.
- **배치 적용이 없다.** 시편 20개를 하나씩 처리하는 것은 현실적이지 않다.
  "이 레시피를 선택한 시험 전부에" 와 일괄 채택이 다음에 온다. 위 모델은 그대로
  확장된다 — 시험마다 결과를 만들고 포인터를 걸면 끝이다.
- **처리가 동기다.** 지금 곡선은 수만 행이라 견디지만, 계획서대로 DB 큐 워커로
  옮겨야 한다. 미리보기는 성격상 동기로 남는다.
