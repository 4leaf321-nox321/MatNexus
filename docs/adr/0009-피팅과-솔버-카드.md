# ADR 0009 — 피팅과 솔버 카드

- 상태: 채택
- 날짜: 2026-08-17
- 관련: ADR 0007(불변 결과와 채택), ADR 0008(반복 시편 통계), 65 `modules/exporting`

## 결정

대표 곡선에 경화식을 맞추고(`matcore/fitting`), 그 결과를 **물성 카드**로 남기고,
카드를 솔버 텍스트로 내보낸다(`matcore/export`).

```
앙상블 대표 곡선 → 여러 식을 나란히 적합 → 사람이 고름 → 카드(초안)
                                                    → 확정(부서 관리자)
                                                    → Abaqus / OpenRadioss / 중립 JSON
```

## 결정한 것들과 근거

### 어느 식이 맞는지 고르지 않는다

Voce · Swift · Hockett-Sherby 를 같은 데이터에 맞춰 **나란히 주고 상대 RMSE 로
정렬만** 한다.

이유는 시험으로 확인했다 — 같은 데이터에 맞춘 Voce 와 Swift 가 적합 구간
(소성변형률 0.2)에서는 5% 안에서 같은 값을 내는데, 1.5 로 외삽하면 갈린다.
Swift 는 계속 올라가고 Voce 는 포화한다. **어느 쪽이 맞는지는 데이터에 없다.**
큰 변형까지 쓸 것인지가 선택을 바꾸고, 그것은 해석하는 사람이 안다.

그래서 적합 구간(`strain_min`·`strain_max`)을 결과와 카드에 박아 두고, 근거에
"이 식은 적합 구간 밖에서 검증되지 않았습니다" 를 언제나 남긴다.

### 절대 RMSE 가 아니라 상대값으로 견준다

재료마다 응력 크기가 달라 절대값으로는 식끼리 비교가 안 된다. 잔차도 평균 응력으로
나눠 푼다 — 안 하면 큰 응력 구간이 적합을 지배해서 **항복 근처가 크게 어긋나도
RMSE 는 작게 나온다.**

### 경계와 초기값을 결과에 남긴다

비선형 최소제곱은 초기값과 경계에 따라 다른 답에 수렴한다. 같은 데이터로 두 번
돌려 다른 값이 나오면 그 값은 근거가 아니다. 파라미터마다 `lower`·`upper`·`initial`
을 함께 저장하고, 값이 경계에 붙으면 *"그 값은 데이터가 정한 것이 아니라 경계가
정한 것"* 이라고 근거에 적는다.

`scipy.optimize.least_squares` 를 쓴다. 경계 있는 적합을 직접 짜면 조용히 틀린
답에 수렴하는 쪽이 훨씬 위험하다.

### 표는 언제나 저장하고, 식은 골랐을 때만 넣는다

많은 솔버가 식보다 표를 그대로 받는다(Abaqus `*PLASTIC`, OpenRadioss LAW36 둘 다
표다). 식이 안 맞는 재료에서는 표가 더 정확하다. 그래서 **카드의 본체는 표**이고
경화식은 참고로 함께 적힌다 — 덱에는 표가 나가고, 어떤 식으로 봤는지는 주석에
남는다.

### 적합도를 카드에 함께 저장한다

파라미터만 남기면 그 값이 데이터와 얼마나 맞는지 다시 알 수 없고, 그러면 카드를
믿을 근거가 사라진다. `rmse`·`relative_rmse`·`r_squared`·`max_residual` 과 쓴
시험 목록·표본 수를 카드 안에 박는다. **카드가 자기 근거를 들고 있어야 한다** —
통계가 지워지거나 시험이 늘어도.

### 상태 플래그만 두고 리뷰 큐는 두지 않는다 (D8)

`draft → published → deprecated`. 승인자·리뷰어·큐는 만들지 않는다 — 운영 규칙이
보이기 전에 절차를 만들면 그 절차가 일을 정의해 버린다.

- **만드는 것은 누구나, 확정은 부서 관리자만**(D12). 초안은 아직 아무 해석에도
  안 들어간다. 만드는 데까지 권한을 걸면 실제로 시험한 사람이 자기 데이터로 카드를
  못 만든다.
- **확정된 카드는 지워지지 않는다.** 그 값으로 해석이 돌았을 수 있다. 내리기만
  된다.
- 전역 재료의 물성은 시스템 관리자만 확정한다(ADR 0006 의 소유 모델과 같다).

### 단위를 환산하지 않는다 — 선언한다

전부 SI(kg·m·s·Pa) 그대로 쓴다. 환산 계수는 1.0 이다.

mm·ton·s 로 푸는 사람이 있지만, 우리가 환산해서 내보내면 **그 덱의 다른 재료가
SI 인지 확인할 길이 없다.** 단위계가 섞인 덱은 오류 없이 1000배 틀린 답을 낸다.
대신 단위를 선언한다 — OpenRadioss 는 `/UNIT/1` 블록으로, Abaqus 는 단위 키워드가
없으므로 `** Consistent units: kg, m, s, Pa` 주석으로.

65도 같은 판단이었다. Decimal 34자리 변환 엔진이 있는데도 익스포트 경로에 두지
않고, 정본이 아닌 단위가 들어오면 `CMP-UNIT-0006` 으로 거부했다.

### 없는 값을 만들지 않는다

푸아송비가 없으면 0.3 을 넣지 않고 **거부한다.** `*ELASTIC` 은 값 두 개를 받는
키워드라 하나를 비울 수 없고, 0.3 을 넣으면 그것이 측정값인지 우리가 채운 값인지
덱만 봐서는 알 수 없다. 밀도도 같다 — OpenRadioss LAW36 은 `RHO_I` 가 자리 있는
필드라 거부하고, Abaqus 는 `*DENSITY` 가 선택 키워드라 **빼되 왜 뺐는지 덱 주석에
적는다.**

형식마다 필요한 값을 `Format.requires` 로 선언해 목록 API 가 함께 준다 —
내려받기를 누른 뒤에 "푸아송비가 없습니다" 를 보는 것은 늦다.

### 표를 조용히 고치지 않는다

솔버는 표에 규칙을 요구한다: 첫 점의 소성변형률이 0, 변형률은 순증가, 응력은
감소하지 않음. 어기면 **고쳐서 내보내지 않고** 무엇이 문제이고 무엇을 하면 되는지
말한다. 특히 응력이 떨어지는 표를 눕혀서 내보내면 그 덱은 실제와 다른 재료가 되고
아무도 그 사실을 모른다 — 보통 네킹 뒤 구간이 섞인 것이라 `tensile.necking_candidate`
로 잘라 다시 처리하라고 안내한다.

**유일한 예외**는 탄성 구간을 0 으로 자른 자국이다. `tensile.true_plastic` 의
`clip_zero` 가 소성변형률 0 인 점을 여러 개 남기는데, 그것은 값이 아니라 자국이다.
한 점으로 모으되 **마지막 것**을 남긴다 — 첫 점을 쓰면 응력이 0 에 가까운 곳을
항복강도라고 적게 된다. 모았다는 사실과 남긴 항복응력을 근거에 적는다.

### 쓴 뒤에 다시 읽는다

키워드가 빠진 덱은 솔버가 **오류 없이 무시하기도 한다** — 그러면 해석은 도는데
재료가 안 들어간 채로 돈다. 형식마다 필수 키워드를 선언해 두고 렌더링 직후 확인한다.
65의 `validate_neutral_elastoplastic_solver_card` 와 같은 자리다.

## 대안

**가장 잘 맞는 식을 서버가 골라 준다** — 편하지만 위에서 본 대로 적합 구간 밖에서
갈리고, 그 선택은 데이터가 아니라 용도가 정한다. 기각.

**푸아송비를 0.3 으로 채운다** — 금속에서는 대개 맞다. 하지만 덱만 보면 그것이
측정값인지 알 수 없고, 알 수 없는 숫자가 해석에 들어가는 것이 이 프로젝트가 막으려는
바로 그것이다. 기각.

**mm·ton·s 로도 내보낸다** — 실무 수요가 있다. 다만 환산한 값을 우리가 내보내면
덱의 나머지가 같은 단위계인지 확인할 방법이 없고, 그 불일치는 오류 없이 틀린 답이
된다. 실제 요청이 오면 그때 **단위계를 파일 이름과 주석에 크게 박아** 넣는다. 보류.

**65처럼 mapping-report 다이제스트를 카드에 박는다** — 손실 매핑을 호출자가 명시적으로
인정해야 내보낼 수 있게 하는 장치다. 지금은 매핑이 단순해(표 그대로) 인정할 손실이
없다. 손실이 생기는 형식(고무·점탄성)이 붙을 때 다시 본다. 보류.

**LS-DYNA 를 함께 만든다** — 65에도 없었고(`ls_dyna` 는 거부 시험에만 나온다),
실제 덱을 대조해 본 적이 없다. 형식을 짐작으로 적으면 그 덱이 조용히 틀리게 읽힌다.
쓰는 부서가 확인되면 그때 실제 덱 한 벌을 받아 맞춰 넣는다. 보류.

## 결과

### 얻은 것

- 재료 상세에 'CAE 카드' 탭. 대표 곡선 → 식 견주기 → 카드 → 덱 내려받기가 한
  화면에서 이어진다.
- **한 바퀴가 실제로 돌았다.** 시험 파일 3건을 올려 처리·채택하고, 대표 곡선을
  Voce 로 맞춰 카드를 만들고, Abaqus `.inp` 와 OpenRadioss `.rad` 를 받아 키워드와
  칸까지 확인했다(`tests/api/test_fitting.py`).
- 파라미터 복원 검산: 답을 아는 Voce 곡선에서 `sigma_0`·`q`·`b` 가 상대오차
  1e-9 로 되돌아온다.

### 답을 아는 산포 데이터로 검산했다 (2026-08-17)

처음 붙였을 때는 시편 15개가 전부 같은 18점 파일이라 CV 가 1e-14% 였다 —
**통계도 적합도 "돌아간다" 밖에 증명하지 못했다.** 그래서 참값을 알고 만든 데이터로
한 바퀴를 다시 돌렸다(`tests/api/test_scatter_loop.py`).

넣은 것: E 200 GPa ±2% · σ₀ 340 MPa ±2.5% · Q 180 MPa · b 15 · TD 는 σ₀ +8% ·
MD 한 시편은 σ₀ −12%(다른 코일). 2000점, 네킹과 로드셀 잡음 포함.

돌아온 것:

| | 넣은 값 | 나온 값 |
|---|---|---|
| MD 항복강도 평균 | 333.8 MPa | 337.9 MPa (0.2% 오프셋이라 조금 위) |
| MD 항복강도 CV | 5.28% | 5.23% |
| 탄성계수 | 200 GPa | 199.9 GPa |
| TD/MD 비 | 1.08 | 1.098 |
| 이상치 | MD_06 | MD_06 |
| Voce σ₀ | 333.8 (시편 평균) | **333.7** |
| Voce Q · b | 180 · 15 | 177.7 · 14.85 |

R² 0.99998, 상대 RMSE 0.040%.

이 과정에서 결함 셋이 나왔고 전부 고쳤다.

1. **적합에 탄성 구간이 섞여 있었다.** `clip_zero` 가 남긴 x=0 점이 120점 중
   34점인데, 그 34점의 응력이 133~341 MPa 로 흩어져 있으니 어떤 단조 함수도 못
   맞춘다. R² 0.42 가 나왔는데 **식이 안 맞아서가 아니었다.** 걷어내니 0.99998.
2. **진소성변형률 축에서 앙상블이 안 맞았다.** 공칭 축에서 재샘플해도 진소성은
   시편마다 σ/E 를 뺀 값이라 격자가 어긋난다. 그런데 그 축에서 재샘플하려면
   쌓인 x=0 을 먼저 접어야 하는데 그 방법이 없었다 — `curve.sort_unique` 에
   `last`(마지막 점만 남김)를 넣었다. **마지막이 항복점**이다.
3. **첫 점이 정확히 0 이 아니었다.** 소성축 재샘플의 공통 시작이 2e-6 처럼 나온다.
   격자 간격보다 네 자릿수 작아 응력은 항복점 그대로라, 1e-4 이하면 자리만 0 으로
   맞추고 그 사실을 적는다. 그보다 크면 항복점이 진짜로 빠진 것이라 거부한다.

**설계대로 거부한 것도 확인했다.** 네킹을 포함해 처리한 표는 84번째 점에서 진응력이
493.42 → 493.41 MPa 로 떨어지는데, 내보내기가 그것을 잡아 거부하고 어디서 자르라고
안내했다. 자른 뒤에 덱이 나왔다.

### 남은 위험

**"솔버에서 읽힌다" 는 아직 우리 검사다.** 형식은 65의 골든 픽스처와 대조해
맞췄지만, 실제 Abaqus·OpenRadioss 로 덱을 돌려 본 것은 아니다. 파일럿 부서에서
덱 한 벌을 돌려 봐야 이 수용 기준이 진짜로 닫힌다.

**합성 데이터로 검산했지 실측으로 한 것이 아니다.** 위 표가 보이는 것은
"우리 계산이 우리가 넣은 물리 모델을 되찾는다" 이다. 실제 재료가 Voce 를 따르는지,
실제 장비 파일에 우리가 모르는 성질이 있는지는 **파일럿 부서 실데이터**가 있어야
안다. 지금 있는 실파일은 여전히 18점 발췌본이다(ADR 0008 과 같은 한계).

**이상치 검출은 표본 수를 탄다.** MAD 기반이라 표본이 적으면 MAD 가 이상치 쪽으로
끌려간다 — 실측으로 **n=5 에서는 −12% 시편을 못 잡았고**(modified z 2.63 < 3.5)
n=8 에서 잡혔다. 결함이 아니라 성질이지만, 5개만 뜨는 시험에서는 임계값을 낮춰
봐야 한다는 뜻이다.

**덱 안의 재료 번호는 파일 안에서만 유일하다.** 카드 UUID 에서 만든다. 덱을 합칠
때 겹치면 사람이 바꿔야 한다 — 전역 번호를 관리하기 시작하면 그 번호를 어느 덱에
썼는지도 관리해야 한다.
