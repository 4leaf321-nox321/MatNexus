# ADR 0002 — 인증·세션·토큰

- 상태: 채택 (2026-08-14)
- 관련: 개발계획 D3(자체 로컬 계정), D12(역할 모델), 구조결정 9(PAT)·12(refresh 폐기 목록)

## 배경

65는 외부 OIDC 전용이고 로그인 화면조차 없어(#215) 사내 배포가 성립하지 않았다.
RA는 자체 인증으로 즉시 배포 가능하지만 refresh 토큰이 stateless 라 폐기 목록이
없다. 비교표는 *"자체 인증을 새로 만든다면 DB 폐기 목록을 처음부터 넣을 것
(RA의 실수를 반복하지 말 것)"* 이라고 적었다.

## 결정

**1. access 는 JWT, refresh 는 불투명 난수 + DB 행.**

refresh 까지 JWT로 만들면 발급 후 되돌릴 수 없다. refresh 를 `refresh_tokens`
한 행으로 두면 `revoked_at` 을 채우는 것만으로 즉시 무효가 된다. 원문은 저장하지
않고 sha256 해시만 둔다 — DB가 새어도 세션을 탈취할 수 없어야 한다.

**2. refresh 는 회전(rotation)한다.** 한 번 쓰면 폐기하고 새로 발급하며, 폐기된
토큰이 다시 쓰이면 탈취로 보고 **그 사용자의 모든 세션을 끊는다**(`MNX-AUTH-0005`).
회전이 없으면 탈취된 토큰이 30일간 유효하다.

**3. refresh 는 httpOnly 쿠키로만 오간다. access 는 응답 본문 → 프론트 메모리.**

localStorage 에 두면 XSS 한 번에 탈취된다. 배포는 백엔드 한 프로세스가 SPA까지
서빙하므로 동일 출처이고, 개발 중에도 Vite 프록시를 거쳐 브라우저에게는 같은
출처다. 쿠키 `path=/api/auth`, `SameSite=Lax`. `Secure` 는 설정값이며 기본은
false다 — 사내망 http 배포에서 true 면 브라우저가 쿠키를 버려 로그인이 유지되지
않는다.

새로고침하면 access 가 사라지므로 앱 기동 시 `/auth/refresh` 를 한 번 호출해
세션을 되살린다. 사용자 눈에는 "로그인이 유지되는" 것으로 보인다.

**4. PAT(개인 액세스 토큰)를 지금 넣는다.** Phase 6의 장비 파이프라인이 어떤
자격으로 API를 부를지가 정해져 있어야 토큰 체계가 둘로 갈라지지 않는다. 사람
세션(refresh)과 기계 자격(PAT)은 수명·폐기 방식이 달라 테이블을 나눴고, 인증
지점은 `shared/auth.py` 하나로 합쳤다 — 권한 판정이 갈리면 "사람은 되는데
파이프라인은 안 되는" 어긋남이 생긴다.

**5. 로그인 이메일에 `EmailStr` 을 쓰지 않는다.**

실측: 초기 관리자 `admin@matnexus.local` 이 422로 막혔다. email-validator 는
`.local` 같은 특수 용도 도메인을 문법 단계에서 거부하는데, 폐쇄망 사내 계정은
그런 주소를 흔히 쓴다. 형식 검증으로 얻는 것보다 로그인이 성립하지 않는 손해가
크다. 길이 제한만 둔다.

**6. bcrypt 앞에 sha256 을 건다.** bcrypt 는 입력을 72바이트에서 자르는데 한글
비밀번호는 글자당 3바이트라 24자를 넘으면 뒤가 조용히 무시된다. passlib 을 쓰지
않는 이유는 RA가 겪은 버전 호환 문제(passlib 1.7.4 ↔ bcrypt 4.x)를 반복하지
않기 위해서다.

**7. 역할은 시스템 2종 + 부서 2종**(D12). `reviewer` 는 D8에서 리뷰 큐를 미뤘으므로
두지 않는다. 물성 `published` 전환 권한은 부서 `manager` 가 갖는다.

## 대안

- **refresh 도 JWT (RA 방식)**: DB 조회가 없어 빠르지만 폐기가 불가능하다.
- **access 를 localStorage 에**: 새로고침에 강하지만 XSS 한 번에 털린다. 기동 시
  갱신 1회로 같은 사용성을 얻을 수 있으므로 이득이 없다.
- **PAT 를 Phase 6에 미루기**: 그때 가서 넣으면 인증 지점과 토큰 테이블을 다시
  설계해야 한다. 지금이 가장 싸다.

## 결과

- `refresh_tokens` · `personal_access_tokens` 테이블, 첫 마이그레이션에 포함
- `POST /api/auth/{login,refresh,logout,change-password}`, `GET /api/auth/me`,
  `POST|GET|DELETE /api/auth/tokens`
- 프론트 `AuthProvider` + `ProtectedRoute`(강제 변경 우회 차단 포함)
- `tests/api/test_auth.py` 8건 — 특히 폐기·회전·재사용 탐지를 검증한다
