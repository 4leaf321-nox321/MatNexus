# ADR 0017 — 옛 데이터는 파서가 아니라 프로파일로 읽는다

- 상태: 채택 (2026-08-26)
- 관련: ADR 0005(장비 파일 읽기 — 형식 프로파일), ADR 0004(재료 계층과 식별자)
- 코드: `matcore/readers/json_tables.py`, `matcore/readers/profile.py`,
  `app/modules/tests/legacy_profiles.py`, `backend/scripts/import_legacy.py`

## 배경

옛 앱(`MaterialAppVer2`)과 그 뒤 DB화 시도로 **JSON 으로 쌓인 시험 데이터**가
있다. 한 파일이 곡선 하나이고, 전부 인장이며, 재료·시료 식별자가 일정하다.
이것을 MatNexus 에 넣어야 한다.

두 갈래가 있었다.

1. **파서 플러그인을 만든다** — `matcore/parsers/legacy_json.py` 를 추가하고
   `@register` 한다.
2. **형식 프로파일로 읽는다** — 코드를 안 고치고 관리 화면에서 형식을 만든다.

처음에는 ①을 골랐다. 근거는 "프로파일은 표(tabular) 파일 전용이고 JSON 은 그
앞단을 통과하지 못한다" 였다. **그 근거가 틀렸다.**

## 관측

실제로 돌려 봤다.

```
readers.tabular.sniff( JSON )
  {"meta": ..., "curve": [ {...}, {...} ]}   → 표 1개 · 메타 키-값     읽힘
  [ {...}, {...} ]                            → 표 1개                  읽힘
  {"a": [1,2,3], "b": [4,5,6]}                → 표 1개                  읽힘
  JSONL(줄마다 객체)                          → ReadError               안 읽힘
```

리더는 이미 JSON 을 안다(`matcore/readers/json_tables.py`). 그것이 우연이
아니라는 증거는 저장소 안에 있었다 — **`.mtet` 을 읽는 기본 프로파일이 이미
들어 있고**, 실파일 107개로 검증돼 있다(`legacy_profiles.py`).

즉 ①은 이미 있는 것을 다시 만드는 일이었다.

## 결정

**옛 데이터는 형식 프로파일로 읽는다.** 새 파서를 만들지 않는다.

파일 형식의 지식은 프로파일 한 곳에만 둔다. 이관 스크립트
(`scripts/import_legacy.py`)는 파일을 해석하지 않고, 프로파일이 읽어 준 메타에서
식별자를 가져다 재료·시료·시편에 줄을 세운다.

**S-S 곡선은 안 받는다.** 옛 파일에 응력-변형률 곡선이 함께 있어도 F-D 만
올리고, S-S 는 시편 치수와 함께 이 시스템이 계산한다(`tensile.engineering`).

## 근거

- **배포가 필요 없다.** 형식이 조금 다른 폴더가 나올 때마다 관리 화면에서
  프로파일을 하나 더 만들면 된다. 파서였다면 그때마다 배포다 — 이관은 한 번에
  끝나지 않고, 폴더마다 조금씩 다르다는 것이 옛 데이터의 성질이다.
- **한 군데만 안다.** 파서와 스크립트가 둘 다 열 이름을 알면, 형식이 바뀔 때
  두 곳을 고쳐야 하고 한쪽만 고쳐지는 날이 온다.
- **남이 계산한 곡선을 원본 자리에 앉히지 않는다.** 옛 앱의 S-S 는 어떤 게이지
  길이와 단면적으로 나눈 것인지 파일에 안 적혀 있다. 그것을 원본으로 들이면 그
  뒤로는 어느 것이 측정이고 어느 것이 계산인지 못 가른다. 장비가 계산해 준
  곡선을 **버리지 않고** 갖고 오려면 프로파일의 `tables.derived` 에 적는다 —
  버리지도 섞지도 않는 자리가 이미 있다.

## 이 결정이 드러낸 것 — 프로파일이 단위를 못 적었다

옛 파일 하나를 끝까지 넣어 보다가 잡았다. 프로파일의 **시편 치수 규칙**은
`"열 이름": "저장할 키"` 로 이름만 바꿀 수 있었다.

```
"specimen": {"Specimen thickness a0 (mm)": "specimen_thickness"}
```

그런데 이 파일은 **단위를 열 이름 안에만** 갖고 있다. 값 옆에는 `0.986` 뿐이다.
읽는 쪽은 숫자만 있고 단위를 모르면 포기한다(`app/shared/curvedata.py` —
mm 라고 가정하면 m 로 적힌 파일에서 1000배 틀린 시편이 만들어지고, 그 뒤 응력이
통째로 어긋나는데 숫자는 그럴듯해 보인다).

**그래서 이미 배포된 기본 프로파일이 시편 치수를 하나도 못 채우고 있었다.**
오류는 안 난다. 치수가 조용히 비고, 세 단계 뒤 처리 1단계의 `@specimen_area`
가 그제서야 "그 값이 없습니다" 로 멈춘다.

시험이 못 잡은 이유가 분명했다 — 시험이 **메타에 값이 들어간 것까지만** 보고,
그 값이 시편에 닿는지는 안 봤다.

그래서 규칙이 단위를 가질 수 있게 넓혔다. 글자 하나면 예전과 같고, dict 면
단위까지 정한 것이다.

```
"Thickness":      "specimen_thickness"                        # "0.989 mm"
"Thickness (mm)": {"key": "specimen_thickness", "unit": "mm"} # "0.986"
```

**파일이 선언을 이긴다.** 값에 단위가 붙어 오면 그쪽을 쓴다 — 선언은 힌트이고
파일이 증거다. 소프트웨어 설정을 바꿔 단위가 달라진 파일이 왔을 때, 프로파일에
적힌 옛 단위로 읽으면 안 된다.

## 결과

- 옛 JSON 이관에 **코드 배포가 필요 없다.** 관리 화면에서 형식을 만들고
  스크립트를 돌린다.
- 이미 깔린 `.mtet` 프로파일은 마이그레이션(`e4a9b70d5c31`)이 고친다. 다만
  **처음 시드한 모양 그대로일 때만** 고친다 — 관리자가 손댔으면 그 판단을
  덮지 않는다.
- 이관 스크립트는 `--apply` 를 줘야 넣는다. 기본은 미리 보기다.
- 같은 파일은 두 번 안 올린다. 판단은 내용 해시로 한다 — 이관은 다시 돌게
  되어 있고, 그때마다 곡선이 한 벌씩 붙으면 통계가 **조용히 두 번 센다.**

## 안 하기로 한 것

- **MCP 로 재료·시료·시편·곡선을 넣는 도구를 만들기.** 처음 제안한 것 중
  하나다. 곡선을 API 로 직접 꽂으면 파싱·치수·처리를 건너뛰게 되어, 그렇게 들어온
  데이터는 **실제 흐름을 한 번도 안 지난다.** 화면에서 어디가 비는지 알 수
  없고, 이름 규칙·채번·기준정보 연결이 전부 그 길 위에 있다.
- **JSONL 을 읽기.** 리더가 거절한다. 필요해지면 리더에 붙일 일이고, 지금
  가진 파일에는 없다.
