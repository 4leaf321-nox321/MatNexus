# ADR 0004 — 재료 계층과 식별자 정책

- 상태: 채택 (2026-08-15)
- 관련: 개발계획 §6 Phase 2, 구조결정 1(조직 식별자를 내부 키로 감싼다)
- 코드: `matcore/naming.py`, `app/modules/materials/models.py`,
  `app/modules/tests/models.py`, `tests/unit/test_material_scope.py`

## 배경

기존 자산이 둘 있다. 65_MaterialCenter 와 `002_Material/MaterialAppVer2`(Electron
데스크톱 앱). 후자가 실제 현장에서 쓰이던 것이라 파일 형식과 ID 규칙을 읽었다.

MaterialAppVer2 는 `.mtd`(재료) → `.mtet`(인장) → `.mdss`(DMA) → `.mepd`(탄소성)
의 파일 계층을 갖고, 각 파일이 상위 파일의 ID 를 `Data Information` 블록에
복사해 계보를 잇는다. **문자열이 곧 참조 키**다.

ID 생성 규칙은 `resource/option.json` 의 `idGenerationRules` 에 설정으로 빠져
있고, 실제 조합은 `mainscript.js` 의 `generateIdFromLabels`(24줄)이 한다.

## 기존 규칙에서 확인한 결함

코드와 실제 생성된 값을 함께 읽고 확인한 것. 이 목록이 아래 결정의 근거 전부다.

**무결성을 깨는 것**

1. **빈 값이 자리를 남기지 않고 사라진다.** `values.filter(v => v)` 한 줄이다.
   두께를 비우고 등록하면 `SECC_MDOI_MD`, 나중에 채우면 `SECC_MDOI_1.0_MD`.
   그런데 그 이름은 하위 시험 ID 에 통째로 복사돼 있어 계보가 끊어진다. 칸 수가
   다른 이름들이 한 이름공간에 섞이므로 서로 다른 재료가 같은 문자열을 가질
   여지도 생긴다.

2. **`Record Name` 과 `Data ID` 가 규칙이 같은데 값이 다르다.** `option.json`
   에서 두 규칙의 `prefix`·`fields`·`timestamp` 가 완전히 동일한데 난수를 각자
   뽑는다. 실제 파일에서
   `TensileTest_3_4_5_6_1_20250619180337_316791` 과
   `TensileTest_3_4_5_6_1_20250619180337_666427` — 같은 시험을 가리키는 두 값이
   다르다. 문자열 비교로 참조 무결성을 확인할 수 없다.

3. **타임스탬프+6자리 난수 때문에 멱등하지 않다.** 같은 파일을 다시 등록하면
   다른 ID 가 생기고, 중복인지 ID 로 판정할 수 없다. 장비 자동 수집에서
   재전송·재시도가 그대로 중복이 된다.

4. **측정값이 식별자에 들어간다.** `Sample Type ID` 의 첫 필드가 `Poisson Ratio`
   다. 0.3 을 0.28 로 정정하면 시료 ID 가 바뀌고 하위 시험이 고아가 된다. 같은
   화면의 Density 는 ID 에 없어서 기준도 없다.

5. **ID 가 화면 상태의 함수다.** `$scope.find('label').filter(...).next('input')`
   로 DOM 에서 라벨 텍스트를 찾아 읽는다. 화면 없이 ID 를 만들 수 없어 서버
   배치·파이프라인에서 재사용이 불가능하고, 탭이 안 그려졌으면 값이 조용히 빠져
   1번으로 이어진다. `startsWith` 매칭이라 `"Strain"` 이 `"Strain at break"` 를
   잡는다.

**운영에서 걸리는 것**

6. **정제가 `trim()` 뿐이다.** 생산일이 `2025/06/19` 형식이라 ID 에 슬래시가
   들어간다(`SampleType_8_9_10_11_12_13_14_2025/06/19`). 파일 경로로 못 쓴다.

7. **단위가 라벨 문자열에 박혀 있다.** `"Spec Thickness (mm)"` — 그런데
   `idGenerationRules.fields` 가 이 라벨 문자열을 참조한다. 라벨·단위·식별자가
   한 문자열에 묶여, 단위를 고치려면 라벨을 고쳐야 하고 라벨을 고치면 ID 가
   깨진다.

8. **저장 단위가 `tonne/mm³`** — Abaqus 단위계다. export 대상 솔버에 맞춘 단위로
   원본을 저장하고 있어, 다른 솔버를 붙이면 어디서 변환됐는지 추적이 안 된다.

## 결정

### 1. 키와 이름을 분리한다

| 역할 | 컬럼 | 성질 |
|---|---|---|
| 참조 | `id` (UUID) | 불변. 모든 FK 가 이것을 가리킨다 |
| 표시·중복방지 | `record_name` | 값에서 결정적으로 조합. 유니크 |
| 사람이 부르는 이름 | `alias` | 자유. 유니크 아님. 언제든 바뀜 |
| 옛 앱 매칭 | `legacy_id` | 보관만 |

**`alias` 를 `record_name` 에 덧붙이지 않는 것이 핵심이다.** 덧붙일 수 있으면
`SECC_MDOI_1.0` 과 `SECC_MDOI_1.0_재시험용` 이 둘 다 통과해 같은 재료가 두 개
생긴다 — 유니크 제약을 두는 이유가 사라진다. 같은 규격인데 진짜로 구분해야 하면
`details` 에 넣는다. `details` 는 이름의 한 칸이라 자동으로 반영된다.

이름은 `matcore/naming.py` 의 순수 함수가 만든다. 빈 칸은 `-` 로 채워 칸 수가
변하지 않고(결함 1), 난수·타임스탬프가 없어 결정적이며(결함 2·3), 값에서 `_` 와
경로 금지문자를 없앤다(결함 6). DB·HTTP·화면을 모르므로 배치·파이프라인에서
그대로 쓴다(결함 5).

### 2. 계층 — 재료 → 시료 → 시편 → 시험

```
Material   SECC_MDOI_1.0                    규격 (Grade·Details·스펙두께)
Sample     SECC_MDOI_1.0__02                실물 한 덩이 (로트·벤더·생산일)
Specimen   SECC_MDOI_1.0__02__MD_03         잘라낸 조각 (방향·실측치수)
TestRun    SECC_MDOI_1.0__02__MD_03__TEN_01 시험 한 번 (조건·회차)
```

**두께는 재료축, 방향은 시편 속성.** 판단이 갈렸던 지점이라 근거를 남긴다.

- 두께: 0.45t 와 1.0t 는 실무에서 별도 자재로 구매·관리되고 압연 이력이 달라
  물성이 다르다. 조건으로 내리면 시편 편차 통계에 두께가 섞인다.
- 방향: MaterialAppVer2 는 Orientation 을 재료 식별자에 넣었다. 그런데 r값(수직
  이방성)은 `.tra` 결과부에 이미 있는 값이고 **방향별 시험을 비교해야** 나온다.
  Hill48 같은 이방성 항복함수도 MD/TD/DD 를 한 재료의 파라미터 한 벌로 적합한다.
  방향이 재료축이면 그 계산의 입력을 표현할 수 없다. 물리적으로도 방향은 시편을
  자를 때 정해진다.

**시료 계층을 두는 이유**는 시료 편차 분석이다. 묶는 축이 세 개가 된다 — 로트 /
시료 / 시편. 로트번호는 관리하는 팀도 안 하는 팀도 있어서 **이름은 재료별 자동
채번 일련번호로 짓고 로트는 속성으로 둔다.** 로트를 이름에 넣으면, 시료를 먼저
등록하고 로트를 나중에 확인할 때 이름이 바뀌어 결함 1과 같은 상황이 된다.

시료 채번은 **재료 단위**다. 부서 단위로 채번하면 전역 재료 밑에서 두 부서가
각자 01 을 받아 같은 이름이 두 개 보인다.

### 3. 전역 승격 — 컬럼 하나를 NULL 로

`materials.owner_workspace_id` 가 nullable 이고 **NULL 이면 전역**이다. 승격은
`UPDATE materials SET owner_workspace_id = NULL` 한 줄이고, 테이블이 움직이지
않으므로 FK·이력·참조가 하나도 안 바뀐다.

이것이 성립하려면 **하위(시료·시편·시험)가 항상 워크스페이스 소속**이어야 한다.
전역 재료 밑에 여러 부서의 시료가 공존해야 하기 때문이다. 그래서 승격할 때
하위는 손댈 일이 없다.

```sql
UNIQUE NULLS NOT DISTINCT (owner_workspace_id, record_name)
```

`NULLS NOT DISTINCT` 가 없으면 Postgres 는 NULL 끼리를 중복으로 보지 않아
**전역 재료끼리 같은 이름이 허용된다.** PG15+ 기능이고 서버는 17.5.
`tests/unit/test_material_scope.py::test_전역_재료끼리도_같은_이름을_막는다` 가
이것을 검사한다 — 옵션을 빠뜨리면 그 테스트가 깨진다.

**승격 절차와 방향 규칙**(기능 자체는 필요해질 때 만든다):

- 이름이 겹치면 사람이 "같은 재료인가"를 판정한다. 기계는 못 한다 — 부서마다
  Details 표기 습관이 다르다. 같으면 하위를 이관 후 병합하는데, 그 이관은
  `shared/dependents.py`(Phase 1-2)가 이미 하는 일이다.
- 강등(전역 → 부서)은 **하위 데이터가 한 워크스페이스에만 있을 때만** 허용한다.
  여러 부서가 데이터를 쌓았으면 내릴 곳이 정해지지 않는다.
- 전역 재료는 관리자만 수정한다. 아니면 A부서가 이름을 바꿔 B부서 데이터의
  맥락이 사라진다.

지금 구현한 것은 **nullable 컬럼과 "내 부서 + 전역" 조회 전제** 둘뿐이다. 나중에
NOT NULL 에서 바꾸려면 마이그레이션에 더해 모든 조회 코드를 고쳐야 한다.

### 4. SI 저장, 단위계 변환

저장은 SI 기본단위(m·kg·s·Pa·K), 입력·표시는 실무 단위(mm·MPa·℃), export 는
솔버 단위계. 변환은 `matcore` 한 곳에서만 일어난다(결함 8).

컬럼마다 단위 컬럼을 두면 스키마가 두 배가 되므로, 사람이 입력할 때 쓴 단위는
`input_units` JSONB 한 칸에 모은다(`{"spec_thickness": "mm"}`). 파일에서 온 값의
단위는 `TestChannel.si_unit` 정의와 곡선 메타데이터가 기록한다.

단위는 라벨과 분리해 `TestChannel.si_unit` 컬럼에 둔다(결함 7). 필드 참조도
라벨이 아니라 안정된 `key` 로 한다(결함 5).

### 5. 시험 종류를 데이터로 — 수준 2

세 수준 중 가운데를 택한다.

| 수준 | 무엇이 데이터인가 | 새 시험 추가 비용 |
|---|---|---|
| 1 | 없음 | 코드 수정 + 배포 |
| **2 (채택)** | 종류·채널·단위·조건 항목 | 관리 화면 입력 + 파서 플러그인 1개 |
| 3 (기존 앱·65) | 화면 레이아웃·탭·ID 규칙까지 | 없음 |

수준 3 을 피하는 이유: 화면이 동적 생성기가 되면 검색·검증·화면이 전부 "무엇이
있을지 모르는" 상태로 짜여야 한다. 65 는 관리자 정의 JSON Schema 를 도입한 뒤
검색 텍스트 추출기를 스키마마다 만들 수 없게 됐다(비교표 8-3).

`TestSummary.source` 로 **장비가 준 값**과 **우리가 계산한 값**을 나눈다. `.tra`
결과부에는 장비 계산값이 이미 들어 있는데, 한 칸에 섞으면 나중에 계산식을 고쳤을
때 무엇이 바뀐 값인지 알 수 없다. 나란히 두면 검증도 된다.

값 없음은 NULL 이다. `.tra` 에는 `"Unknown"` 문자열이 실제로 오는데, 그대로
숫자 칸에 두면 집계에서 하나의 값으로 잡혀 통계가 오염된다.

## 결과

- 이름이 틀려도 데이터가 안 깨진다. Grade 오타 정정이 `UPDATE` 한 줄이 된다.
- 같은 파일을 다시 올리면 같은 이름이 나온다 — 중복 판정이 가능해진다.
- 이름 생성이 서버에서 일어나므로 장비 파이프라인(Phase 5)이 같은 코드를 쓴다.
- 대신 **이름이 참조 키가 아니라는 것을 사람이 이해해야 한다.** 기존 앱 사용자는
  ID 로 파일을 찾던 습관이 있다. 화면에서 이름과 함께 검색이 되도록 해야 한다.
- 기존 `.mtd`/`.mtet` 흡수는 `legacy_id` 매칭으로 한다. 파일이 많지 않아
  일회성이다.

## 대안

- **자연키를 진짜 키로**(기존 앱 방식) — 오타 정정과 필드 보완이 불가능해진다.
  결함 1·2·4 가 여기서 나온다.
- **방향을 재료축에** — 이름이 기존 앱과 완전히 같아진다는 이점이 있지만, r값과
  이방성 항복함수의 입력을 모델로 표현할 수 없게 된다. r값·Hill48 을 쓰지 않을
  것이라면 이쪽이 단순하다.
- **재료를 전역 마스터로** — 중복 등록은 확실히 막지만 부서 간 명명 충돌이
  생기고, 파일럿 단계에서 그것을 조정할 조직적 수단이 없다. 부서 소속으로
  시작해 승격 경로를 열어 두는 쪽을 택했다. 반대 방향(전역 → 부서)이 훨씬 어렵다.
- **수준 3(화면까지 데이터)** — 위 표 참조.
