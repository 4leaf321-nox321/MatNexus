# 0072. 문헌 재료 상세는 벌의 점을 싣지 않는다 — 점은 벌마다, 값 검색은 벌마다 한 줄

상태: 채택

## 배경

수집기가 공개 피로 묶음 9개를 개발 DB 에 들인 뒤(새 재료 306 · 값 4,131 · 벌 3,534 · 점 57,621) 화면 API 를 쟀다.
목록 · 찾기 · 요약은 그대로였고 **점이 많은 재료에서만** 느렸다.

| 무엇 | 시간 | 크기 |
| --- | ---: | ---: |
| 상세 Ti-6Al-4V (L-PBF) — 값 9,743 중 벌의 점 9,105 · 벌 555 | 1,606 ms | 16 MB |
| 상세 AlSi10Mg (L-PBF) | 729 ms | 6.9 MB |
| 비교(적층 3종) | 1,351 ms | |
| Ashby 피로강도 × 인장강도 | 1,069 ms | |
| 값 검색 「피로한도」 50줄 | 418~475 ms | 15개 재료, 한 재료가 12줄 |

원인은 하나다 — ADR 0067 이 점을 **낱값**으로 두었고(값 검색 · 물성 지도가 고치지 않고 읽게), 상세는 낱값을 전부
실었다. 점마다 출처(33 %) · 조건(21 %) · 갈리는 조건(18 %)을 되풀이했고, 대표를 고르는 계산이 S-N 점 수천 개를
훑었다. 산점의 점은 대표가 될 수 없는데도(ADR 0068) 읽혔다.

## 결정

1. **상세는 곡선 · 산점의 점을 싣지 않는다.** 대표로 뽑힌 곡선 점만 값 목록에 온다(그 물성의 대표값이니
   요약 · 사내 반영이 그것을 써야 한다). 산점의 점은 아예 안 읽는다. 계수 묶음의 항은 그대로 싣는다.
2. **대표는 숨긴 점까지 넣고 고른다** — 다만 곡선은 **벌마다 앞선 점 하나**만 넣는다(`representative.leaders`).
   같은 벌의 점은 출처 · 등급 · 방법이 같아, 그 안에서 앞서지 못한 점은 무리 전체에서도 못 이긴다(순위는 차례
   비교라 옮아간다). 빼고 고르면 상세의 대표가 비교 · 덱 · Ashby 의 대표와 갈린다. 후보 수(`n_candidates`)는
   낱값 + 곡선 벌마다 하나 — 비교 표의 후보 수도 같은 규칙으로 센다.
3. **점 수 · 범위는 벌 머리에** — 열마다 `count` · `low` · `high`, 벌의 `x_min` · `x_max`. 요약 화면이 점을 받지
   않고 「값 수 · 조건 범위」 를 쓴다. 산점만 있는 물성도 요약에 한 줄로 선다(대표 없이).
4. **점은 벌마다 따로**: `GET /catalog/series/{id}/points` — 머리 + 축 차례의 점(x · 값 · 줄 조건). 화면은 앞의 네
   벌만 펼쳐 받고, 나머지는 펼칠 때 받는다. 벌은 20개씩 세운다. MCP 는 `get_catalog_series`.
5. **값 검색은 한 벌의 점을 한 줄로** — 점 수(`count`) · 범위(`low`~`high`) · 벌 이름(`series`), 값은 기준에
   가장 가까운 점(기준이 없으면 가장 작은 점). 낱값은 그대로 한 줄씩.
6. **비교 · Ashby 도 산점의 점을 안 읽고 곡선은 벌마다 앞선 점만** — 대표가 같아서 결과는 그대로다.

## 대안

- **점을 상세에 두되 가볍게**(출처 · 갈리는 조건 빼기): 16 MB → 2~3 MB 지만 대표 계산과 직렬화는 그대로라 1 초 가까이
  남는다. 화면은 펼친 벌의 점만 쓰는데 555벌을 다 실을 까닭이 없다.
- **재료 단위로 점을 한꺼번에**(`GET /catalog/materials/{id}/points`): 곡선 탭을 열 때 한 번 — 요청 수는 적지만 벌이
  555개인 재료에서 펼치지도 않은 9,000점을 받는다.
- **값 검색을 재료 단위로 묶기**: 한 재료가 1점짜리 벌 수백 개를 가질 때(수집기 묶음이 그렇다) 벌 단위로 묶어도 한
  재료가 20줄을 차지한다. 그러나 벌은 출처 · 조건이 다른 실험이라 재료 단위로 섞으면 「어느 시험의 값인가」 가
  사라진다. 벌 단위로 두었다.

## 결과

개발 DB 다시 잼(2026-10-24, 같은 스크립트):

| 무엇 | 전 | 후 |
| --- | ---: | ---: |
| 상세 Ti-6Al-4V (L-PBF) | 1,606 ms · 16 MB | 316 ms · 2.0 MB |
| 상세 AlSi10Mg (L-PBF) | 729 ms · 6.9 MB | 126 ms · 1.0 MB |
| 상세 316L (L-PBF) | 416 ms · 5 MB | 101 ms · 0.96 MB |
| 비교(적층 3종) | 1,351 ms | 639 ms |
| Ashby 피로강도 × 인장강도 | 1,069 ms | 125 ms |
| 벌 하나의 점(50점) | — | 15 ms · 10 KB |
| 값 검색 「피로한도」 100~600 MPa | 50줄 = 낱 점 | 50줄 중 49줄이 벌(점 320개) |

- 남은 2 MB 는 벌 머리 555개(메모 · 출처 · 조건)와 값 639개의 메모 · 출처다. 출처를 한 번만 싣는 일은 응답 모양을
  바꾸는 일이라 따로 본다.
- **값 검색의 시간은 줄지 않았다**(0.4~0.5 초) — 값 질의는 31 ms 이고 나머지는 물성 이름을 푸는 임베딩 호출이다.
  키를 그대로 줘도 「뜻으로 찾기」 를 부른다(`property_names.resolve` — 글자로 찾은 후보가 다섯보다 적으면).
  이 결정의 범위 밖이다.
- 값 검색에서 한 재료가 여전히 여러 줄일 수 있다 — 벌이 여럿이면 벌마다 한 줄이다(위 대안 셋째).
- 사보타주 4/4: 곡선 벌의 앞선 점을 후보에 안 넣기 · 벌마다 맨 뒤 점 · 낱값 질의가 벌의 점도 내기 · 가까운 점 대신 늘
  아래쪽.
