# ADR 0026 — 복합 물성: 구성체·추정 물성·시험법을 둔다 (초안)

- 상태: **제안** (2026-09-05) — TF 킥오프(2026-09-07) 전 스키마 합의용
- 과제: 「AX 툴 기반 평가 체계 및 CAE 품질 협업 모델 구축 (물성 해석 연계 신뢰성
  예측 고도화)」. 추진 방향 셋 — ① 실물 시험–해석 상호 검증 AX 시스템, ② 불필요한
  시험·해석 최소화, ③ 사업부 간 물성 DB 공유·활용. 지원 범위 — 물성 측정(온습도·
  DMA·피로)·평가 데이터 등록 포맷 표준화, AX 기반 공유 연결 체계.
- 관련: ADR 0004(재료 계층), 0006(시험 종류를 부서가 만든다), 0007(원본과 처리결과),
  0009(피팅과 솔버 카드), 0010(기준정보를 외래키로), 0016(시험이 주지 않는 물성은
  선언한다), 0020(여러 시험을 묶는 자리)
- 역할: 플랫폼 개발 **GTR 디지털트윈사무국** · 지그·비교 규칙 등 시험 조건 제반
  **GTR 개발디지털트윈** · 역공학으로 판별 기준·시뮬레이션 기준 **MX CAE 그룹** ·
  규격 안에서 시험을 만들고 운영 **MX 신뢰성 그룹**
- 짝: [플랫폼-요구사항-MX확인요청](../../플랫폼-요구사항-MX확인요청-2026-09-07.md) —
  이 스키마의 빈칸을 채우려면 무엇을 물어야 하는지. **A·B 절 답이 오기 전의 이
  문서는 짐작이다.**
- 코드: 아직 없음. 이 문서가 먼저다.

## 배경

과제가 다루는 「물성」은 재료 본연의 성질이 아니다 — 과제에서는 이것을
**「복합 물성」** 이라 부른다. 디스플레이 적층처럼 **여러 재료가 결합된 부품
단품**에서

- 층별 물성을 따로 잴 수 없어 **복합체를 시험하고 역공학으로 층 물성을 추정**한다
- **층 하나만 바뀌었을 때** 거동의 어떤 특징이 갈라지는지 판별한다
- **시장 불량을 재현하는 부품 단품 시험법**을 개발하고 그 데이터를 모은다
- 그것을 **시뮬레이션으로 재현하는 방법론**을 만든다

지금 MatNexus 의 계층 `재료 → 시료(로트) → 시편 → 시험` 은 재료 하나가 대상이라는
전제 위에 있다(ADR 0004). 그 계층은 옳고 그대로 둔다 — 다만 그것만으로는 위
넷 중 어느 것도 담기지 않는다.

| | 재료 물성 (지금 체계) | 복합 물성 (이 ADR) |
| --- | --- | --- |
| 대상 | 재료 하나 | 층·재료가 결합된 구성체 |
| 값 | 측정값 | **추정값** — 어느 역공학에서, 무엇을 가정하고 |
| 정체성 | 재료·로트·시편 번호 | **구성체 + 변형체(무엇이 다른가)** |
| 시험 | 확립된 규격 | **시험법 자체가 개발 대상** — 초안 → 검증 → 규격 |
| 시뮬레이션 | 물성을 입력으로 | **방법론이 산출물** |

## 결정

### D1. 구성체는 재료와 **나란한** 두 번째 뿌리다 — 재료에 욱여넣지 않는다

재료는 「선언하는 곳은 하나」 규칙으로 정리해 온 체계다. 구성체를 재료의 한
종류로 만들면 층·변형체·추정값이 재료 속성에 섞이고, 그 규칙이 깨진다.

### D2. 다형성은 **시료(로트)** 에서 갈라진다

부품도 로트로 온다(제조 배치·입고분). 그러므로 `Sample` 이 재료에도, 구성체에도
붙을 수 있게 한다. **그 아래 시편·시험·처리·결과·카드는 한 줄도 안 바뀐다.**

    Material ─┐
              ├─ Sample ─ Specimen ─ TestRun ─ (처리·결과·카드: 그대로)
    Stack ────┘

대안 「시편에서 갈라진다」는 시편·시험 코드 전부가 두 뿌리를 알아야 해서 버렸다.
대안 「구성체 전용 계층을 따로 만든다」는 파서·처리·카드를 두 벌로 만들게 되어
버렸다.

### D3. 추정값은 측정값과 **다른 칸**이다

값 하나에 「어느 실행에서 나왔는지·무엇을 고정했는지·불확실성·유효 범위」 가
붙는다. 밀도의 `Inherited(value, source, reason)` 패턴(ADR 0016)을 넓힌 것이다.
측정값 칸에 추정값을 넣으면 나중에 어느 것이 잰 값인지 알 수 없게 된다.

### D4. 시험법은 시험 종류 **위의** 개념이다 — 합치지 않는다

- **시험 종류**(ADR 0006) = 데이터의 모양. 채널·조건 칸·파서·처리.
- **시험법** = 그 종류로 **무엇을 어떻게** 하는가. 목적(불량 모드)·시나리오·지그·
  판정·성숙도·개정.

하나의 시험 종류에 시험법이 여럿이다. 인장 시험 종류 하나에 「규격 인장」 과
「적층 시편 박리 후 인장(초안)」 이 같이 산다.

### D5. 시험은 시험법 **버전**에 묶인다

시험법이 개정되면 이전 시험의 근거가 바뀌면 안 된다. 버전은 불변이다.

## 스키마 초안

새 테이블은 「비우고 시작」 이고, 기존 테이블에는 **nullable 열만** 더한다.
기존 데이터는 한 줄도 안 바뀐다.

### 기준정보 (vocabulary 에 slug 추가, ADR 0010)

| slug | 뜻 | 비고 |
| --- | --- | --- |
| `failure_mode` | 시장 불량 모드 (결로, 박리, 얼룩…) | 시험법·시험이 참조 |
| `product` / `part` | 제품·부품 코드 | 지금 재료의 `applied_products/parts` 는 자유 입력 — 기준정보로 올린다 |
| `layer_role` | 층 역할 (기판, 접착, 편광, 커버…) | 층 정의가 참조 |
| `fixture` | 지그 | 시험법이 참조. 개발디지털트윈 산출물 |

### 구성체 — `stacks` 모듈 (백엔드·프론트 같은 이름)

```
Stack                          구성체
  id, record_name              -- 이름 규칙은 naming.py 에 추가. 예: DISP-OLED-6.7_v1
  code            text         -- 사람이 부르는 코드
  part_id         FK vocab     -- 어느 부품
  parent_id       FK Stack?    -- 변형체면 부모
  variant_note    text?        -- 「무엇이 다른가」 사람 말
  classification  enum         -- public / division / strategic   (등급, D3 참고)
  workspace_id, created_by, created_at, note

StackLayer                     층
  id, stack_id FK
  position        int          -- 순서 (위→아래)
  role_id         FK vocab     -- layer_role
  material_id     FK Material? -- 아는 재료면 참조. 모르면 NULL + label
  label           text         -- 재료를 모를 때 부르는 이름 (「업체 A OCA」)
  thickness_m     float?       -- SI. 표시는 units.ts
  bond            text?        -- 접합 방식
  process_note    text?
  UNIQUE(stack_id, position)

StackDiff                      변형체가 부모와 다른 점 — 판별의 질문이 되는 자리
  id, stack_id FK (변형체), layer_position int
  what            enum         -- material / thickness / bond / added / removed
  before, after   jsonb        -- 구조화된 전후 값
```

**변형체 정체성:** `parent_id` 가 있으면 `StackDiff` 가 1건 이상 있어야 한다.
「다른 게 없는 변형체」 는 만들지 못한다 — 서비스에서 막는다.

### 시료가 두 뿌리에 붙는다 — `materials` 모듈, 기존 테이블

```
Sample
  material_id     FK Material?   -- 지금은 NOT NULL → nullable 로
  stack_id        FK Stack?      -- 새 열
  CHECK ((material_id IS NULL) <> (stack_id IS NULL))   -- 정확히 하나
```

- `record_name` 규칙에 구성체 가지를 더한다(`naming.py`).
- 시편의 치수 3층 해석(시험 실측 → 시편 → 규격 공칭)은 구성체 시편에서
  「규격 공칭」 대신 **층 두께 합**을 셋째 층으로 쓴다(`specimen_size.py`).
- 삭제 사슬(`delete_tree`)·일괄 등록·목록·워크벤치는 「뿌리가 무엇인가」 를 안다.
  이것이 이 변경의 실제 크기다 — 스키마보다 화면이 크다.

### 데이터 출처·등급 — 기존 테이블에 열 추가

```
TestRun.origin        enum   internal / supplier / literature   (기본 internal)
Sample.origin         enum   같은 값. 시료가 어디서 왔는가
Material.classification, Stack.classification
                      enum   public / division / strategic       (기본 division)
```

`supplier` 시험은 **등재를 막는 게 아니라 격리 표시**한다 — 막으면 사람이
`internal` 로 거짓 입력한다. 대신 통계·카드·내보내기가 기본으로 제외하고, 포함할
때는 명시한다. `strategic` 은 열람에 계정의 서약 플래그를 요구한다.

**사업부 간 공유(추진 방향 ③)는 이 등급 위에 선다.** 지금 워크스페이스는
부서 가시성만 안다. `public` 은 전 사업부 열람, `division` 은 소속 사업부, `strategic`
은 서약자 — 공유 범위가 등급 하나로 정해져야 사업부마다 다른 규칙이 생기지
않는다. 기본값 `division` 은 「공유하려면 올린다」 는 뜻이다.

### 시험 종류 확장 — `backend/extensions/`

과제가 이름 붙인 측정 셋 중 **DMA 는 있다**(`matcore/processing/dma.py`). 온습도와
피로는 없다 — 각각 확장 폴더 하나로 붙인다(ADR 0013). 온습도는 시간–조건 곡선이
고 피로는 사이클–하중 곡선이라 처리의 결이 인장과 다르지만, 읽기(형식 프로파일)·
조건 칸·카드는 그대로 쓴다. **등록 포맷 표준화는 이 확장이 요구하는 채널·조건
칸을 시험 종류로 선언하는 것**이다 — 별도 표준 문서가 아니다.

### 시험법 — `methods` 모듈

```
TestMethod                     시험법 (머리)
  id, code            -- 예: TM-CND-001
  name
  test_type_key       FK 시험 종류      -- 데이터 모양 (D4)
  failure_mode_id     FK vocab?         -- 재현하려는 불량. 규격 시험이면 NULL
  target_part_ids     FK vocab[]        -- 적용 부품 종류
  status              enum   active / retired
  workspace_id, created_by, created_at

TestMethodVersion              버전 — 불변 (D5)
  id, method_id FK, version_no int
  maturity            enum   draft / pilot / validated / standard
  derived_from        jsonb  -- {kind: external_standard|method_version, ref, note}
  scenario            jsonb  -- 조건 프로파일. 아래 「시나리오」
  fixtures            FK vocab[]         -- 지그
  measurements        jsonb  -- 기록할 채널·스칼라·관찰 항목
  acceptance          jsonb  -- 판정 규칙. 아래 「판정」
  procedure_md        text   -- 사람이 읽는 절차
  evidence_note       text?  -- 승격 근거 요약
  created_by, created_at
  UNIQUE(method_id, version_no)

TestRun (기존)
  method_version_id   FK TestMethodVersion?   -- 새 열
  reproduced          enum?  yes / no / inconclusive   -- 불량이 재현됐는가
  judgement           jsonb? -- 판정 결과와 근거 (acceptance 를 어떤 값으로 평가했나)
```

**시나리오** — 자유 문장이 아니라 **세그먼트 목록**이다. 장비 프로그램으로도,
시뮬레이션 경계조건으로도 내보낼 수 있어야 「시험법–방법론 규격 쌍」 이 실체가
된다.

```json
[
  {"kind": "ramp",  "channel": "temperature", "from": 25, "to": 60, "unit": "degC", "duration_s": 600},
  {"kind": "hold",  "channel": "humidity",    "at": 90,  "unit": "%RH", "duration_s": 3600},
  {"kind": "cycle", "repeat": 10, "segments": [ ... ]},
  {"kind": "load",  "channel": "force", "profile": "triangular", "peak": 5, "unit": "N", "rate": 0.1}
]
```

채널 이름과 단위는 시험 종류의 조건 칸(ADR 0006)과 같은 표를 쓴다 —
`matcore/units.py` 로 차원을 검사한다.

**판정** — 규칙도 데이터다. 처리 결과의 스칼라 이름을 참조한다.

```json
{
  "rules": [
    {"scalar": "delamination_area_ratio", "op": "<", "value": 0.05, "severity": "fail"},
    {"scalar": "haze_delta",              "op": "<", "value": 2.0,  "severity": "warn"}
  ],
  "reproduction": {"scalar": "condensation_onset_s", "op": "exists"}
}
```

`reproduction` 은 「이 시험법이 불량을 재현했는가」 의 기준이다 — 시험법 자체의
검증에 쓰인다. `TestRun.reproduced` 는 이것을 평가한 결과다.

**성숙도 승격은 증거로 한다.** `pilot → validated` 는 「이 버전으로 수행한 시험
N건 이상, 재현율 r 이상」 을 서비스가 검사한다. 숫자는 워크스페이스 설정이다
(가변 — 리비전을 찍지 않는다). `validated → standard` 는 사람이 승인한다
(ADR 0022 의 핸드북 승인 흐름을 재사용).

### 추정 물성·역공학 — `inverse` 모듈

```
SimulationRecipe               시뮬레이션 방법론 (머리)
  id, code, name, stack_id FK?  -- 특정 구성체용이면. 일반 방법론이면 NULL
SimulationRecipeVersion        버전 — 불변
  id, recipe_id, version_no, maturity (draft/validated/standard)
  modeling           jsonb   -- 요소 종류·접촉·대칭 등 구조화된 선택
  bc_mapping         jsonb   -- 시나리오 세그먼트 → 경계조건 매핑 규칙
  assignment         jsonb   -- 층 position → 재료 모델 (피팅 family, ADR 0009)
  deck_template      text?   -- 솔버 덱 정의 (ADR 0023 과 같은 방식)
  validated_by       FK TestRun[]   -- 어느 시험 집합으로 검증됐나
  procedure_md, created_by, created_at

InverseRun                     역공학 실행 — 불변
  id, stack_id FK, recipe_version_id FK
  input_run_ids      FK TestRun[]      -- 맞추려는 시험 집합 (ADR 0020 의 묶음 재사용)
  free_params        jsonb   -- {layer_position, property, bounds}
  fixed              jsonb   -- {layer_position, property, value, source}  ← 가정
  status             enum   queued / running / done / failed
  fit                jsonb   -- 적합도 지표
  residual_curves    → 곡선 저장 (ADR 0007 과 같은 자리)
  created_by, created_at

EstimatedProperty              추정 물성
  id, inverse_run_id FK
  target_kind        enum   layer / stack        -- 층 물성인가 등가 물성인가
  layer_position     int?
  property_key       text   -- 예: youngs_modulus
  value_si           float, dimension text
  uncertainty        jsonb? -- {kind: interval|stdev, ...}
  valid_range        jsonb? -- {temperature: [..], rate: [..]}
  classification     enum   -- 업체 층이면 기밀 여부에 따라 (확인 사항)
```

**추정값은 재료 속성에 쓰지 않는다.** 재료 카드가 추정값을 보이려면 「추정
(역공학 #123, 가정 3건)」 배지를 달고 `EstimatedProperty` 를 참조한다.

### 시료 배분 — 추진 방향 ②. 지금은 자리만

「해석으로 리스크를 도출하고 제한된 실물 시료를 의미 있는 시험에 배분한다」 는
**시험 계획**이라는 새 개념이다 — 어느 구성체를, 어느 시험법으로, 몇 개, 왜.
해석 결과(`InverseRun`·방법론 검증)가 「왜」 의 근거가 된다. 스키마는 첫 파일럿
에서 실제로 시료를 나눠 본 뒤 정한다. 지금 넣으면 계획 도구가 아니라 양식이 된다.

### 판별 — 2단계 후반. 지금은 자리만

기준 구성체 vs 변형체의 처리 결과 스칼라를 나란히 놓고 **어느 특징이 갈라놓는가**
를 남기는 `ComparisonRule`. `grouping`·`statistics` 위에 얹는다. 스키마는 첫
파일럿 데이터를 본 뒤 정한다 — 지금 정하면 짐작이다.

## 시험법을 DB 로 만드는 방식 — 제안

시험법은 문서이면서 데이터다. 둘을 가르는 기준은 **기계가 읽어야 하는가**다.

1. **구조화 코어 + 문서 본문.** 시나리오·측정 항목·판정·지그·불량 모드는 구조화
   (위 jsonb). 절차·주의사항·사진은 마크다운 본문. 검색·비교·내보내기는 코어로,
   사람의 실행은 본문으로.
2. **시험이 곧 증거다.** 시험을 시험법 버전에 묶으면 「이 시험법으로 몇 건, 재현율
   얼마」 가 **자동으로** 쌓인다. 별도 검증 보고서를 쓰지 않는다. 성숙도 승격의
   근거가 데이터에서 나온다.
3. **시나리오는 내보내기가 되는 형식이다.** 세그먼트 목록은 장비 프로그램(온습도
   챔버·UTM)으로도, 시뮬레이션 경계조건으로도 변환된다. 「시험법–방법론 규격 쌍」
   은 이 하나의 시나리오를 둘이 공유하는 것으로 실현된다.
4. **계보를 남긴다.** 시험법은 외부 규격(ASTM·IEC·JIS)에서 파생되거나 이전 시험법
   에서 파생된다. `derived_from` 과 버전 간 diff 가 「왜 이렇게 바꿨나」 를 든다.
5. **외부 규격도 같은 틀에 넣는다.** 참고한 외부 규격의 시나리오·측정 항목을 같은
   구조로 등재하면(본문은 저작권상 요약만) **우리 시험법과 나란히 비교**된다. AI 가
   「이 불량 모드에 쓸 시험법 후보」 를 뽑을 때 비교 근거가 된다 — 신뢰성 그룹의
   「AI 로 시험법 발굴」 이 여기서 데이터를 얻는다.
6. **성숙도는 상태가 아니라 게이트다.** draft 는 누구나, pilot 은 시험 1건 이상,
   validated 는 N건·재현율 r, standard 는 승인. 게이트 조건이 워크스페이스 설정이라
   부서마다 다르게 둘 수 있다.
7. **판정 규칙은 처리 결과 스칼라를 가리킨다.** 새 이름을 만들지 않는다. 결로
   시험법의 판정이 `condensation_onset_s` 를 보려면 결로 확장(`extensions/결로/`)의
   처리가 그 스칼라를 내야 한다 — 시험법과 확장이 같은 이름표를 쓴다.
8. **사진·관찰은 측정 항목이다.** 육안 판정(얼룩·박리)이 많은 분야다.
   `measurements` 에 `{"kind": "photo", "at": "after_cycle_10"}` 처럼 넣고 파일스토어에
   붙인다. 나중에 이미지 판정 모델의 학습 데이터가 된다.

## 결과

- **기존 재료 체계는 한 줄도 안 바뀐다.** `Sample` 에 열 하나, `TestRun` 에 열
  셋, 등급 열 둘 — 모두 nullable 또는 기본값.
- 새 모듈 셋: `stacks` · `methods` · `inverse`. 모듈 간 직접 호출 금지 규칙은
  그대로 — 시험법이 시험을 알아야 하면 `shared` 를 거친다.
- **화면이 스키마보다 크다.** 목록·일괄 등록·삭제 사슬·워크벤치·피커가 「뿌리가
  둘」 을 알아야 한다. 1단계 일정의 대부분이 여기다.
- 마이그레이션은 만든 자리에서 올린다(AGENTS.md).

## 열린 것 — 킥오프에서

- 역공학으로 추정한 **업체 층의 물성**이 업체 기밀에 해당하는가.
  `EstimatedProperty.classification` 의 기본값이 이것에 달렸다.
- 구성체 정의를 PLM/BOM 에서 받을 수 있는가. 받을 수 있어도 **1단계는 손으로**
  넣는다 — 연계는 AX POC 의 표준을 기다린다.
- 성숙도 게이트의 숫자(N, r)의 초기값.
- **기존 시험 데이터 체계와의 정렬.** 이 문서의 `Stack`·`TestMethod`·판정 구조는
  요청 목록 A·B 절의 답으로 **확정되거나 고쳐진다.** 특히 A1(식별 체계)·A10(판정)·
  B3(재현 사례)는 스키마를 바꿀 수 있는 답이다.
- 등록 포맷 표준화의 대상 — 온습도·DMA·피로 셋으로 시작하되, 「평가 데이터」 가
  시험 곡선 외에 무엇을 뜻하는지(판정표·사진·보고서) 는 신뢰성 그룹에 묻는다.
