# 0083. 처리 결과는 레시피의 판과 단계 지문을 남기고, 사용 중지된 레시피로는 일괄 처리를 안 돌린다

날짜: 2026-11-14
상태: 채택
관련: 처리 레시피 계보(2026-10-03, 이슈 #2 — `recipe_key` · 「(단계 고침)」)

## 배경

VOC 45:

- 일괄 처리(`POST /processing/batch`)는 `steps` 가 필수라 `recipe_key` 만 주면 422 였다. MCP 는 레시피를 읽어
  단계를 직접 채워 보냈다 — 그 사이에 레시피가 바뀌면 다른 판으로 돌았고, MCP 의 미리보기는 서버를 안 부르고
  건수만 셌다.
- 결과에는 레시피 키 · 이름과 그때의 단계만 남고 **몇 번째 판이었는지**는 없었다. 「같은 레시피로 돌린 결과들」
  을 견줄 때 중간에 레시피가 바뀌었는지 알 수 없었다.
- 사용 중지(비활성)된 레시피로도 일괄 처리가 돌았다.

## 결정

1. **단계를 안 보내면 서버가 레시피의 지금 단계로 돈다** — 한 건 저장 · 미리보기 · 일괄 모두. 둘 다 없으면
   422(`MNX-PROCESSING-0023`). MCP `run_batch_processing` 은 키만 보내고 미리보기도 서버에 맡긴다.
2. **결과에 판 번호(`recipe_revision`)와 단계 지문(`steps_hash`)을 둘 다 남긴다**(마이그레이션 `d2a8f4c61b37`).
   판 번호는 사람이 읽기 좋고, 지문(빈 옵션을 뺀 단계의 sha256)은 레시피가 지워지거나 키가 다시 쓰여도
   「단계가 정말 같은가」 를 기계적으로 견준다. 판 번호는 그 레시피 그대로 돌렸을 때만 적는다. 옛 결과는
   둘 다 비어 있다(모름).
3. **사용 중지된 레시피로는 일괄 처리를 안 돌린다**(409, `MNX-PROCESSING-0022`). 한 건 처리는 막지 않는다 —
   옛 결과를 다시 내 보는 자리다.

## 대안

- **판 번호만** — 더 단순하지만 레시피를 지우거나 키를 다시 쓰면 견줄 근거가 약해진다.
- **사용 중지 레시피도 경고만** — 끈 뜻이 「쓰지 말라」 라서 일괄로 수십 건이 그 판으로 쌓이면 되돌리기가 크다.

## 결과

- 결과 목록의 레시피 표지에 「n판」 이 선다(지문은 표지 위에 마우스를 대면).
- `run_processing`(MCP 한 건)은 단계를 손에 쥐어야 구간 넓혀 다시 돌리기를 하므로 지금처럼 레시피를 읽어 채운다.
