# 0051. 사용 현황은 행이 아니라 수로 센다 — MCP 도구는 서버가 직접 알린다

날짜: 2026-10-02
상태: 채택
관련: 접근 로그(`shared/access_log.py`, 사람 지원용) · `X-Client` 표식(`shared/request_context.py`) ·
[ADR 0035](0035-보기는-모두에게-고치기는-사람에게.md)

## 배경

요청(2026-10-02): 「사용 현황 집계, 조회 집계 등 다양한 사용 현황을 관리자 페이지로. 특히 MCP 로 연결해
쓰는 숫자는 집계돼야 한다. 가입자도 포함해서 — 실제로 얼마나 잘 쓰고 있는지 볼 수 있게.」

있던 것으로는 답이 안 됐다.

- **접근 로그는 쓰기와 로그인만 남긴다** — 조회(GET)는 양이 많고 지원에 가치가 낮다는 판단이었다. 그래서
  「얼마나 쓰나」 의 대부분인 조회가 0 으로 보였다.
- **MCP 로 왔는지가 안 남았다.** MCP 서버는 `X-Client: mcp` 를 보내고 백엔드는 감사 기록에만 그것을 썼다.
- **도구 수는 요청 수로 셀 수 없다.** 도구 하나가 백엔드를 여러 번 부르고(`property_coverage`), 백엔드를
  안 부르는 도구도 있다(`get_guide`).

## 결정

1. **행이 아니라 수로 센다.** 날 · 사람 · 길(화면 / MCP) · 메서드 · 라우트 틀마다 한 줄을 두고 같은 줄이 오면
   더한다(`usage_daily`). 조회까지 다 세도 표는 요청 수만큼 자라지 않는다 — 하루에 「사람 · 라우트」 줄이
   전부다. 접근 로그는 그대로 둔다(목적이 다르다).
2. **라우트 틀로 센다** — `/materials/{material_id}`. 주소 그대로면 재료마다 줄이 갈린다. 상세 조회 다섯(재료 ·
   문헌 재료 · 시험 · 카드 · 가이드 문서)은 **무엇을 봤는지**도 센다(`usage_views_daily`).
3. **로그인한 요청만, 폴링은 빼고.** 알림 배지가 30초마다 묻는 것까지 세면 「얼마나 쓰나」 가 「얼마나 켜
   두나」 가 된다. 맞는 라우트가 없는 주소(SPA 폴백 · 없는 API)도 안 센다.
4. **MCP 도구는 MCP 서버가 직접 알린다** — 도구가 끝날 때마다 `POST /usage/mcp-calls`(도구 · 성공 여부 ·
   걸린 ms), 그 토큰의 주인 몫으로(`mcp_tool_daily`). `@mcp.tool()` 을 감싸서 91개를 하나하나 고치지 않고,
   새 도구도 빠지지 않는다. 오류(`{"error": …}`)나 예외로 끝나면 실패로 센다. 보고가 실패해도 도구의 답은
   나간다. 이 보고 요청은 요청 집계에서 뺀다(두 번 세지 않게).
5. **사용자 열에 외래키를 안 건다.** 계정을 지워도 그 사람이 쓴 양은 남아야 한다 — 「지난 분기에 몇 명이
   썼나」 는 지금 계정 수와 다른 물음이다.
6. **요약 한 장(`GET /usage/summary?days=`)을 시스템 관리자만 연다** — 사람마다의 사용량이 실린다. 쓴 사람
   (화면 / MCP / 둘 다 · 하루 평균) · 요청(조회 · 쓰기 · 오류 · 기능별) · MCP(도구별 · 사람별 · 실패 · 걸린
   시간 · 토큰 · AI 경유 기록) · 많이 본 것 · 가입 · 로그인 · 만든 자료 · 사람별 활동. 숫자는 서버가 세고
   화면은 그리기만 한다.
7. **세기 전 날짜는 0 이 아니라 「안 셌다」 로 보인다** — `measured_since`(계량이 쌓이기 시작한 날)를 싣고,
   화면이 그 앞 기간이면 그렇다고 말한다. 가입 · 로그인 · 만든 자료 · AI 경유 기록은 원래 표에서 세므로
   그 전 기간도 맞다.

## 대안

- **접근 로그에 GET 까지 남긴다.** 행이 요청 수만큼 늘어 지원용 조회가 느려지고, 보존 정책도 갈라진다
  (집계는 오래 두고 싶고 접근 로그는 몇 달이면 된다). 기각.
- **MCP 요청 수로 도구 수를 짐작한다.** 도구 하나가 요청 여러 개라 수가 부풀고, 백엔드를 안 부르는 도구는
  빠진다. 요청에 도구 이름 헤더를 붙여 첫 요청만 세는 길도 있지만 「첫 요청」 을 가르는 상태가 백엔드에
  필요하다. 기각 — 서버가 끝날 때 한 번 알리는 쪽이 정확하고 단순하다.
- **메모리에 모았다가 몰아서 쓴다.** 요청마다 쓰는 비용을 줄이지만, 워커가 여럿이거나 재시작하면 수가
  사라진다. 사내 사용량에서는 요청마다 upsert 한 번이 부담이 아니다. 필요해지면 연다.
