# 0069. 장비 자산은 TestScope 가 정본이다 — 보유 장비를 지우고, 연결 설정은 화면에서

날짜: 2026-10-23
상태: 채택(1~4 · A · C) · 제안(B)
관련: TestScope `backend/app/modules/equipment` · `properties` · `search` · `shared/secretbox`

## 배경

MatNexus 「보유 장비」(2026-09-07)는 장비 한 대 한 대의 위치 · 상태 · 교정 · 부속을 적는 장부였다. 개발 DB 로
확인하니 어디에도 이어지지 않았다.

- 시험의 「장비」 칸은 기준정보 값(모델 이름 「Zwick Z100」)이고, 보유 장비와 같은 값을 쓸 뿐 그 고리를 따라가는
  화면 · API 가 없었다. 같은 모델이 1호기 · 2호기 둘이라 값이 같아도 어느 대인지 모른다.
- 측정법 화면 · MCP `how_to_measure` 의 「보유」 는 보유 장비가 아니라 원본(MaterialTwin) 장비 카탈로그의
  `owned` 를 봤는데, 218종 모두 거짓이었다 — 모든 물성에 「보유 장비 없음 — 외주하거나 문헌값」 이라고 말했다.
- 보유 장비를 장비 모델에 잇는 칸은 API 에만 있고 화면에 없어 6대 중 0대가 이어져 있었다.

TestScope 는 같은 일을 온전히 한다 — 장비 제품군 → 기종 → 사양값, 보유 장비(자산번호 · 자리 · 상태), 교정 이력,
그리고 **물성(같은 MaterialTwin 키) → 시험 항목 → 시험법 → 장비** 사슬. 사용자 판단(2026-10-23): 「장비 관련
정보는 TestScope 에서 다룬다. 여기 있을 필요가 없다」. 운영에는 등록된 보유 장비가 없다(사용자 확인).

## 결정

1. **보유 장비를 지운다** — 화면 · API · MCP `list_equipment` · 표 셋(`equipment_units` · `_parts` ·
   `_calibrations`, 마이그레이션 `b0fb5b052995`). 온톨로지의 「장비 정의의 개체」 · 「이 장비를 가진 조직」 관계,
   소유 이관 · 권한 판정 · 기준정보 집계에서도 뺀다. 시험의 「장비」 칸(모델 이름)은 남긴다 — 장비 파일을 읽는 일과
   시험 기록에 필요하다.
2. **측정법은 「보유」 를 말하지 않는다.** 화면의 보유 타일 · 열 · 피커 수와 MCP 의 「보유 장비가 없다」 를 뗐다.
   원본의 `owned` 칸은 남아 있지만 근거로 쓰지 않는다.
3. **외부 연동 설정은 화면에서 넣는다**(`integrations`, 「관리 › 외부 연동」, 시스템 관리자). `.env` 에 두면
   서버 파일을 고치고 재기동해야 바뀐다(사용자 요청). 한 시스템에 한 줄(`integration_connections`, 마이그레이션
   `2b126b605270`) — API 주소(서버가 부름) · 화면 주소(사람이 여는 링크) · 봉인한 토큰 · 마지막 연결 확인.
4. **토큰은 봉인하고 다시 보이지 않는다.** Windows DPAPI(기계 범위) + `JWT_SECRET` 보조 엔트로피
   (`shared/secretbox`, TestScope 와 같은 방식 · 다른 접두라 서로의 값은 못 푼다). 응답 · 감사에는 「설정됨」 ·
   「바뀜」 · 「지움」 만 남는다. **빈 칸으로 저장하면 토큰을 그대로 둔다** — 칸이 늘 비어 보이므로 빈 칸을 지우기로
   읽으면 주소만 고쳐도 토큰이 사라진다. 지우기는 `clear_token`. 주소 · 토큰을 바꾸면 지난 연결 확인을 지운다.
   연결 확인은 `GET /auth/me`(토큰 주인) · `GET /properties`(시험 항목이 이어진 물성 수)를 실제로 부른다.

## 다음 — TestScope 에서 읽어 오기(A · C 채택 2026-10-23, B 보류)

복사해 두지 않고 **그때 묻는다**(read-through, 짧은 캐시). 장비 사본을 두면 이번에 지운 것과 같은 「어긋난 두 벌」 이
다시 생긴다. 남기는 것은 **시험이 가리킨 장비의 id 와 그때의 이름표**뿐이다(이력은 TestScope 가 바뀌어도 남아야
한다).

- **A. 측정법 · MCP — 「이 물성을 잴 우리 장비」**: 물성 키 → `GET /properties`(물성 키 → TestScope 물성 id, 한 번에
  받아 캐시) → `POST /search/test-items {property_term_id}` → 장비 · 자산번호 · 부서 · 위치 · 상태 · 교정 만료 ·
  조건 판정. 연결이 없거나 못 닿으면 「모름」 — 「없음」 은 시험 항목이 이어졌는데 장비가 0일 때만.
- **B. 시험 ↔ 장비 한 대**: 시험에 TestScope 장비 id 와 이름표 사본. 장비 커넥터에 장비 한 대를 지정하면 그 커넥터의
  파일이 자동으로 채운다. 시험 상세에 「그때 교정이 유효했나」(TestScope 교정 이력 대조).
- **C. 측정 의뢰**: 받는 부서 고르기에 「이 물성을 잴 장비가 있는 부서」 를 앞세운다.

**A · C 를 만들었다**(사용자 결정: A · C 지금, B 는 TestScope 장비 · 교정 데이터와 추적성 요구를 본 뒤).

- 묻는 곳은 `shared/testscope.py` 한 곳이다 — 주소 · 토큰 · 클라이언트 · 물성 표(10분 캐시)를 연결 확인 · 측정법 ·
  의뢰가 같이 쓴다. 답은 상태가 먼저다: `off`(설정 없음) · `error` · `unlinked`(**모름** — TestScope 에 그 물성의 시험
  항목 연결이 없다) · `none`(**없음** — 이어졌는데 가동 중 장비가 0) · `found`. 장비마다 TestScope 화면 링크
  (`{화면 주소}/equipment/{id}`)를 붙인다.
- A: `GET /metrology/by-property/{key}/owned` — 측정 지도와 따로 읽어 TestScope 가 느려도 지도는 선다. 측정법 상세의
  「우리 장비 (TestScope)」 칸, MCP `how_to_measure` 의 `owned`.
- C: `POST /commissions/lab-suggestions` — 의뢰 항목에는 물성 키가 없어(시험 종류 · 물성 이름 글자) TestScope
  `/resolve` 로 시험 항목 · 물성을 풀고 장비를 묻는다. 시험 종류는 이름 · 「시험」 뗀 이름 · 약어 · 키 차례로
  묻는다(「인장시험」 ↔ TestScope 「인장」). **여럿으로 풀리면 고르지 않고** 「추천에서 빠진 항목」 으로 말한다. 부서는
  이름(띄어쓰기 · 대소문자 무시)으로 잇되 MatNexus 에 하나로 정해질 때만 누를 수 있게 준다.

**TestScope 개발 서버로 실측**(2026-10-23, v0.64.0, 임시 확인용 토큰 — 끝나고 지움):

- 응답 모양은 가정과 같았다. 물성 175개가 시험 항목에 이어져 있고 **연결 256개가 전부 기계 제안**이다 — 인장강도가
  「리브(반발) 경도」 로도 펼쳐지고 박리강도의 첫 장비가 염수분무기다. 화면 · MCP 가 「기계 제안」 을 말하는 것이
  꾸밈이 아니다. 유리전이온도는 연결이 없어 「모름」, 밀도 · 활성화에너지는 「없음」(카탈로그에는 36계열).
- 인장강도 하나에 장비 109대 — 측정법 · MCP 는 앞의 30대와 전체 대수(`equipment_total`)를 싣고 나머지는 TestScope
  링크로 보낸다.
- `/resolve` 는 「DMA」 를 후보 하나(「DMA (동적기계)」, 이름에 포함)로 준다. **후보가 하나이고 글자 근거(정확히 같음 ·
  별칭 · 이름에 포함)면 받는다.** 「뜻이 가까움」(의미 검색)은 하나여도 안 받는다 — 「고온 탄성계수」 에 「초탄성 계수」
  가 온다.
- 시험 종류 「박리 · 이탈력」 은 통째로 물으면 의미 검색 후보만 온다 — 「·」 「/」 로 나눠서도 묻는다(「박리」 정확).
  기본 시험 종류 8개 중 7개가 풀렸고 「레오미터 유동」 은 후보 셋(용융지수 · 회전 유변 · 모세관 유변)이라 빠진다.
- 읽기 전용 토큰도 `/resolve` · `/search/` POST 를 쓸 수 있다(TestScope `_READ_ONLY_POSTS`).
- 개발 서버의 TestScope 부서(「파일럿 재료시험팀」 · 「본사」)는 MatNexus 개발 DB 에 없어 추천을 누를 수 없었다 —
  운영은 부서 CSV 를 같이 쓰므로 이어질 것이나, 배포 뒤 확인한다.

## 대안

- **`.env` 에 주소 · 토큰**(SP 코어 연결 방식, ADR 0063): 사용자가 화면을 원했다. SP 코어도 같은 화면으로 옮길 수
  있다(이번에는 하지 않았다).
- **TestScope 장비를 밤마다 복사**: 못 닿아도 보이지만 사본이 늙고, 두 벌이 어긋나는 문제가 그대로 돌아온다.
- **보유 장비를 남기고 TestScope 와 맞추기**: 같은 장비를 두 곳에서 고치게 된다.

## 하지 않은 것

- 기준정보 축 「장비 유형」 · 「장비 제조사」 · 「시험실」 은 남겼다 — 「장비」 축(시험이 씀)이 「장비 유형」 을 부모로
  둔다. 셋 다 이제 쓰는 곳이 없으므로 B 를 할 때 함께 정리한다.
- 토큰 범위(읽기만인가)는 TestScope `/auth/me` 가 알려 주지 않아 검사하지 않는다 — 화면이 「읽기 범위만」 을 안내한다.

## 결과

- 지움: `app/modules/equipment` · `frontend/src/modules/equipment` · MCP `list_equipment`(도구 124개).
- 더함: `app/shared/secretbox.py` · `app/modules/integrations` · `frontend/src/modules/integrations` · 감사
  `integration.updated` · 운영 핸드북 「TestScope 연결」.
- 시험 DB 정리: 모델에서 뺀 표가 시험 DB 에 남아 `drop_all` 을 막던 것을 `conftest` 가 지운다.

## 후속 (2026-10-25)

의뢰 받는 부서 추천(C)이 화면에만 있었다. MCP `create_commission` 의 미리보기가 `lab_suggestions` 를 싣고, `lab` 을
비우면 추천과 함께 거절한다. 고른 부서가 추천에 있는지(`lab_is_suggested`)는 TestScope 에 물었을 때만 참 · 거짓이고
못 물었으면 모름(None)이다 — 판단은 `mcp_server/lab_choice.py`(시험 `test_mcp_lab_choice.py`).

## 후속 (2026-10-26) — 장비 기준정보 축

보유 장비를 지운 뒤 아무도 안 가리키게 된 기준정보 「장비 제조사」(instrument_maker) · 「시험실」(lab) 축을
걷었다(마이그레이션 c4e8a1d7f203). 바깥에서 가리키는 값(외래키 칸 · SP 연결)이 있으면 그 축은 남긴다. 「장비」 ·
「장비 유형」 은 시험이 파일에서 읽은 장비 이름을 가리키므로 남는다 — 시험을 TestScope 장비 한 대에 잇는 일(B)은
그대로 보류다.
