# ADR 0005 — 장비 파일을 읽는 방식: 형식 프로파일

- 상태: 채택 (2026-08-15)
- 관련: D7(정의는 데이터, 계산은 플러그인), ADR 0004, 개발계획 §6 Phase 2
- 코드: `matcore/readers/tabular.py`, `matcore/readers/profile.py`,
  `app/modules/tests/formats.py`, `tests/api/test_format_profiles.py`

## 배경

장비 종류가 늘 때마다 파서를 코딩하면 두 가지가 막힌다.

1. **개발 비용** — 장비 하나에 파서 하나
2. **왕복** — 이게 더 크다. 현장 파일이 개발자에게 오지 않는다. 폐쇄망이면 더
   그렇다. 파일을 받아야 파서를 만들고, 만들면 배포해야 하고, 그동안 데이터는
   안 들어온다.

그런데 실측해 보니 장비 파일들의 **구조가 놀랄 만큼 비슷하다.** Zwick 인장기와
TA DMA850 은 만든 회사도 측정하는 물리량도 다른데, 파일은 둘 다 이 모양이다.

    키,값                    ← 메타 블록
    [마커]                   ← 있을 수도 없을 수도
    표 이름                  ← 있을 수도 없을 수도
    채널,채널,채널            ← 헤더
    단위,단위,단위            ← 있을 수도 없을 수도
    숫자,숫자,숫자            ← 데이터 (표가 반복될 수도)

## 결정

**구조는 코드가 한 번 읽고, 의미는 사람이 한 번 매핑한다.** 세 층으로 나눈다.

```
파일 (무한히 다양)
   ↓  층 1  범용 리더        ← 코드. 한 번만 만든다
구조 (인코딩·구분자·표·헤더·단위)
   ↓  층 2  형식 프로파일     ← 데이터. 화면에서 만든다
채널 키 (displacement, storage_modulus …)   ← 유한한 정의 집합
   ↓
곡선 · 요약값
```

### 층 1 — 범용 리더 (`matcore/readers/tabular`)

장비별 지식을 **하나도** 넣지 않는다. 자동으로 알아내는 것:

| | 방법 |
|---|---|
| 인코딩 | UTF-8 → CP949 → CP1252. 첫 시도가 아니면 경고 |
| 구분자 | `,` `;` `\t` `\|` 중 열 수가 가장 일관된 것 |
| 데이터 블록 | 모든 칸이 숫자인 줄이 2행 이상 이어지는 곳 |
| 단위 줄 | 데이터 바로 위 줄의 칸 중 아는 단위 비율이 60% 이상 |
| 헤더 줄 | 단위 줄이 있으면 그 위, 없으면 데이터 바로 위 |
| 표 이름 | 헤더 위의 한 칸짜리 줄 (`[step]` 마커는 건너뜀) |
| 메타 | 첫 표 앞의 키-값 줄. 키가 빈 줄은 앞 값에 이어 붙임 |

**실측 결과** (장비별 코드 0줄):

| 파일 | 결과 |
|---|---|
| Zwick `Example.tra` | UTF-8 · `,` · 메타 15쌍 · 표 1개(18행 3열) · 단위 3/3 |
| TA `Example.csv` | UTF-8 · 메타 16쌍 · 표 1개(`Strain Sweep - 2`) · 단위 8/8 |
| TA `FreqTemp.csv` | 표 **8개** 전부 · 열 구성이 표마다 달라도 각각 정확 |
| TA `FreqTemp3.csv` | **CP949** 자동 감지 + 추측 경고 · 표 10개 |

단위 줄 판정은 네 파일 모두 **100%** 였다.

#### 그다음 실파일 131개에 돌려 보고 셋을 고쳤다

픽스처 4개는 너무 적었다. `002_Material` 의 고유 파일(내용 해시 기준) 131개 —
사본까지 647개 — 에 돌리자 셋이 나왔다. **셋 다 성격이 같다. 틀렸는데 성공했다.**
실패는 사람이 보지만 조용히 잘못된 성공은 아무도 못 본다.

**① JSON 을 표로 착각했다 — 131개 중 59개.** 기존 앱의 `.mtet`·`.mdss`·`.mdft`
는 JSON 인데, 배열 안의 숫자 줄이 연달아 나와 "표 93개" 로 잡혔다. 열 이름은
전부 비어 있었다.

    name= 'Tensile Test Raw Data": {'   header= ('', '')   rows= 17

→ **이름 있는 열이 하나도 없으면 표를 찾은 게 아니다.** 거절한다.

**② 엑셀 패딩이 헤더를 한 줄 밀어냈다.** 엑셀이 내보낸 CSV 는 빈 칸으로 줄 끝을
채운다. 실측 파일은 67칸 중 4칸만 채워져 있었다.

    ,,,,,,,,,,, …                     ← 엑셀 패딩
    ,strain,stress,fine strain, …     ← 진짜 헤더
    ,2.93E-09,1.58266399,0,0,, …      ← 데이터

빈 칸을 "단위다움"에 세고 있어서 헤더 줄의 점수가 63/67 = **0.94** 가 됐다.
헤더가 단위 줄로 오인되고, 그 위 빈 줄이 헤더가 되어 **열 이름이 통째로
사라졌다.** → 빈 칸을 분모에서도 뺀다. 회귀 없음(Zwick 3/3, DMA 7/7 여전히 1.0).

**③ 칸 수가 어긋난 파일에서 이름을 지어낼 뻔했다.** `Example.csv` 구버전은 헤더
8칸·데이터 7칸인데, **빠진 것이 마지막이 아니라 6번째**(`Tan(delta)`) 였다.
앞에서부터 맞춰 붙이면 손실탄성률 데이터에 `Storage modulus` 라는 이름이 붙는다.
**틀린 이름은 이름이 없는 것보다 나쁘다** — 그럴듯해 보여서 아무도 못 잡는다.
→ 붙이지 않고 거절하되, **오류에 진짜 헤더를 실어** 사람이 `Tan(delta)` 가 빠진
것을 알아보게 한다(단위 줄이 아니라 헤더가 보여야 한다).

고친 뒤: 장비 원본 8개 전부 통과(`.tra` 3 · DMA `.csv` 5, `.TRA` 대문자 포함),
엑셀 패딩 CSV 도 열 이름을 살려 읽는다. 거절한 것은 JSON·요약표·바이너리다.

### 층 2 — 형식 프로파일 (`FormatProfile` 테이블)

자동으로 안 되는 것은 하나뿐이다 — **`Storage modulus` 가 우리의 어느 채널인가.**
그것을 사람이 한 번 정해 저장한다.

```json
{
  "match":   {"extensions": [".csv"], "header_any": ["Angular frequency"]},
  "tables":  {"mode": "all", "include": "^Temperature Sweep"},
  "columns": {"Storage modulus": {"channel": "storage_modulus"}},
  "specimen":{"Thickness": "specimen_thickness"},
  "summary": {"Force maximum": {"key": "tensile_strength"}}
}
```

`definition` 을 JSONB 로 두는 이유: 규칙 항목이 장비를 겪으면서 늘어난다. 컬럼으로
쪼개면 새 규칙마다 마이그레이션을 해야 하고, 그러면 **배포 없이 대응한다는 목적이
무너진다.**

### 층 3 — 특수 파서 (`matcore/parsers`)

바이너리·XML·독자 포맷처럼 층 1·2로 안 되는 것만. 파싱은 **프로파일이 먼저** 보고,
맞는 것이 없을 때만 플러그인으로 내려간다. `zwick_tra` 는 그대로 두었다 — 이미
동작하고 테스트가 붙어 있어 옮길 이유가 아직 없다.

## 65와 무엇이 다른가

65는 **화면·검색·검증까지** 동적으로 만들어 대가를 치렀다(비교표 8-3: 관리자 정의
JSON Schema 를 도입한 뒤 검색 텍스트 추출기를 스키마마다 만들 수 없게 됨).

여기서 동적인 것은 **읽기 규칙까지**다. 프로파일이 정규화 지점이고, 그 뒤 채널
키는 여전히 유한하고 정의돼 있다 — 곡선 뷰어도 축 선택도 Phase 3 계산도 그 유한
집합 위에서 돈다.

## 자동 감지를 믿지 않는 장치들

**자동 감지는 틀린다.** 실측: 같은 폴더의 `Example FreqTemp2.csv` 는 UTF-8 로 저장된
것을 CP949 로 읽어 다시 저장한 이중 손상 파일인데, 감지기는 CP949 로 "성공적으로"
읽는다. **글자만 깨지고 숫자는 멀쩡하다.**

그래서 셋을 둔다.

1. **미리보기** — 파일을 저장하지 않고 구조만 읽어 표를 보여 준다. 사람이 눈으로
   확인하는 단계가 없으면 조용히 잘못 읽는 것을 막을 방법이 없다.
2. **저장 전 적용** (`POST /formats/try`) — 프로파일을 저장하기 **전에** 그 파일에
   씌워 본다. 저장하고 나서 틀린 것을 아는 것과는 다르다.
3. **추측했다는 사실을 남긴다** — UTF-8 이 아니어서 다른 인코딩을 골랐으면 경고로
   드러낸다. 성공이 곧 정답이 아니다.

그리고 **지문 없는 프로파일을 거절한다.** 지문이 없으면 모든 파일에 맞아, 다른
장비 파일까지 그 규칙으로 읽혀 엉뚱한 곡선이 생긴다.

## 결과

**검증**: TA DMA850 을 파서 코드 한 줄 없이 읽어 곡선까지 만들었다
(`tests/api/test_format_profiles.py`). 시험 종류도 프로파일도 API 로 만들었고,
`matcore` 에 DMA 를 아는 코드는 없다.

- 온도 25°C → 298.15 K (오프셋 정확)
- 변형률 9.99711e-4 % → 9.99711e-06
- 각주파수 rad/s → 환산하지 않음
- `[step]` 8개 중 측정 6개를 곡선 6벌로, TTS 2개는 건너뛰고 **경고로 남김**
- 시편 두께가 `0.989 mm` 에서 값+단위로 갈려 나옴

**부수 효과 하나**: 프로파일을 고쳐도 이미 읽은 데이터는 안 바뀌지만, **원본을
보관하고 있으므로 다시 읽으면 된다.** 원본 보관의 두 번째 값이 여기서 나왔다.
그래서 시험 종류 정의와 달리 프로파일은 잠그지 않는다 — 프로파일이 틀렸다는 것을
나중에 아는 것이 정상이다.

**대가**:
- 의미 매핑은 여전히 사람이 한다(첫 1회)
- 바이너리·독자 포맷은 코드
- 손상된 파일은 못 고친다 — 경고하고 넘긴다

## 대안

- **장비마다 파서** — 지금까지의 방식. 왕복이 남는다
- **완전 선언형 DSL** — 규칙 언어가 결국 복잡해져 65의 길을 간다. 층 1을 코드로
  두고 층 2만 데이터로 둔 이유가 이것이다
- **자동 매핑까지** — `Storage modulus` 를 이름만으로 채널에 붙이는 것. 반반
  확률로 맞히는 것보다 한 번 묻는 편이 낫다. 잘못 매핑된 곡선은 그럴듯해 보인다

## 부산물: 차원 모델 정정

DMA 정의를 만들다 걸렸다. `1` 을 `strain` 차원에 두었더니 `tan δ`(무차원)와 같은
단위를 쓰면서 차원만 달라, 정의 검증이 서로를 거절했다. **변형률은 물리적으로
무차원이다** — 이름으로 구분하는 것은 의미이지 차원이 아니다. `1`·`%`·`mm/mm` 를
`dimensionless` 로 옮기고 `strain` 은 별칭으로 남겼다(`units.same_dimension`).
